### 0.1 破坏性变更（2026-10-08）：v1 的 HMAC 签名面已整体删除

> ⚠️ **这一小节是**历史记录**，不是用法说明** —— 照它写不出任何能通的东西。

2026-10-08 的「开放平台 v2」收口把**上一版（v1）的整套面整体删除**，删掉的是：

1. **入站 HMAC 签名认证**：三个签名请求头、待签串的构造规则、±300 秒时间窗、按来源 IP 的
   签名失败闸。⇒ 今天对外端点**只认** `Authorization: Bearer <令牌>`，拿旧签名头打任何一条
   对外路径都会回 `401` + `应用凭据无效`。
2. **应用自己的授权范围**：应用级权限节点（勾了才能查单）、游戏范围（单独勾选 / 全部游戏
   两种模式）、以及"零游戏范围会明说"那一档。⇒ 今天 **一个应用凭据 = 本租户全部业务数据**：
   没有节点门、没有游戏范围，也就**不存在**「凭据对但没授权」与「还没配游戏范围」这两档答复
   （那两句旧文案今天一个字都不会再返回）。
3. **那一版的示例签名代码**（Python / PHP / Node 三份）与它们的夹具。

> ⚠️⭐ **改准（2026-10-09，企微群码线；上面第 2 条的原文保留）**：第 2 条里那句
> 「**一个应用凭据 = 本租户全部业务数据**、不存在『凭据对但没授权』」今天**有一类例外** ——
> **锁定应用**（§1.4）：它是**唯一**带授权范围的一类凭据（只能读订单 + 只能写群聊二维码），
> 打白名单外的对外端点会拿到 **403**（§7.2 有逐条口径）。
> ⚠️ **通用应用一字未变**：本文档其余地方写那句口号时，说的都是通用应用。
>
> ⛔⭐ **同一处再改准（2026-10-09，企微群码线）**：上面那句「只能写群聊二维码」的**准确口径是
> 取票那一跳的限制**（取票端点只接受 `img_type=1`），⛔ 不是"这个凭据碰过的图一定是群码"——
> 票的图种由**取票那一跳**决定，而**认领端点不重判图种** ⇒ 有一条**存在但未修**的边界，

**对已经按签名接好的调用方**：这是一次**破坏性变更**，改法是
「换取令牌 → 每个请求带 `Authorization: Bearer <令牌>`」；其余请求形状（路径 / query /
响应信封 / `code` 语义）没有变。⚠️ 出站（我们推给你的回调）用的是**另一族**签名头
（`X-TT-Timestamp` / `X-TT-Delivery` / `X-TT-Signature`，§5.3），⛔ 别把两者当成同一件事。

旧版的协议正文（三个头怎么拼、待签串怎么算、时间窗多少秒）**不在本文档里保留**：
它是"照它实现会调不通"的内容，留在对外契约里只会误导。历史原文在 git 历史与
设计文档第 13.1 节。

## 1. 接入三步

### 1.1 第一步：换令牌（`POST /api/open/oauth/token`）

| 项 | 值 |
|---|---|
| 方法 / 路径 | `POST /api/open/oauth/token`（⚠️ 逐字，**⛔ 末尾没有斜杠**） |
| 请求头 | `Content-Type: application/x-www-form-urlencoded`（⛔ 不是 JSON） |
| 请求体（三个字段） | `grant_type=client_credentials`、`client_id=<AppKey>`、`client_secret=<AppSecret>` |
| 认证 | ⛔ **不需要**任何 `Authorization` 头（这个端点自己就是凭据入口） |

**成功（HTTP 200）**：响应体是**裸的三个键**（⛔ 不是本仓那个 `code` / `msg` / `data` 信封）：

```json
{"access_token": "<令牌>", "token_type": "Bearer", "expires_in": 7200}
```

| 键 | 说明 |
|---|---|
| `access_token` | 令牌本体。⚠️ 它是一个**不透明字符串**（形如 `base64url(payload).base64url(HMAC-SHA256(…))`）—— 按原样回传，⛔ 不要解析、不要改、不要拼格式 |
| `token_type` | 恒为 `Bearer`（放请求头时写 `Authorization: Bearer <令牌>`） |
| `expires_in` | 有效期**秒数**，恒为 **7200**（2 小时）。⚠️ 它是"从这一刻起还能用多久"，⛔ 不是绝对时刻 |

**失败（HTTP 401）**：响应体**恰好两个键**（⛔ 同样**没有** `code` / `msg` / `data`）：

```json
{"error": "invalid_client", "error_description": "应用凭据无效"}
```

| 情形 | HTTP | `error` | `error_description` |
|---|---|---|---|
| 密钥错 / 应用不存在 / 应用已停用 | **401** | `invalid_client` | `应用凭据无效`（⚠️ **三档逐字相同**，见下） |
| `grant_type` 不是 `client_credentials`（含没传、传空） | **401** | `unsupported_grant_type` | `仅支持 client_credentials` |
| 限流（见下） | **429** | `temporarily_unavailable` | `请求过于频繁，请稍后再试` |

- ⭐ **三档凭据失败共用同一句话是有意的**：否则就能用响应差异**枚举出哪些 `AppKey` 存在**
  （应用不存在与密钥错必须长得一样）。⇒ 排障时⛔ 不要指望从这句话里分出"是密钥错了"
  还是"这个应用没了"，请直接找租户核对 `AppKey` / `AppSecret`。
- ⭐ **校验顺序**：先判 `grant_type`，再判凭据。⇒ `grant_type` 写错时**不会**顺带告诉你
  凭据对不对（那一档不查库）。
- ⚠️ **体不是 form-urlencoded**（例如你发了 JSON 体）⇒ 字段被当成**缺失** ⇒ 你会拿到
  `401` + `unsupported_grant_type`。⛔ **不会**是 415 / 400，也⛔ **不是**本仓信封 ——
  这条端点的每一种答复都是 OAuth2 体。
- ⚠️ **限流是兜底**（⛔ 不是配额）：**每来源 IP 每 60 秒 600 次，含成功与失败**。
  正常业务碰不到它（令牌两小时才换一次）；它只为"失控 / 刷量"存在。
  ⚠️ 它与下一段那条"按来源 IP 的失败闸"共用**同一个** 429 答复（同一句话，
  ⛔ 从文案里看不出任何关于凭据的信息）。

**令牌的四条语义（逐条都是契约，⛔ 别照别的平台的习惯推断）：**

1. ⭐ **有效期到点即失效**：`expires_in` 一到，用它的请求一律 `401` + `令牌已过期`。
   ⇒ **没有"自动续期"**，到点就重新换一次（换令牌很便宜，成功了不写业务数据）。
2. ⭐ **轮换密钥 ⇒ 所有旧令牌立刻失效**：租户点一次「轮换密钥」（§1.2），
   该应用**已经发出去的每一颗令牌当场作废**（令牌的签名是用 `app_secret` 算的，
   换了密钥就验不过）⇒ 你正在跑的对接会**当场 401**。要靠**人工**协调换密钥的时机。
3. ⭐ **⛔ 没有 refresh token**：这个端点**只有** `client_credentials` 一种授权类型，
   ⛔ 没有 `refresh_token`、⛔ 没有 `grant_type=refresh_token`、⛔ 也没有续期接口。
   过期了就**重新换一颗**（拿同一对 `client_id` / `client_secret`）。
4. ⭐ **令牌不能单独吊销**：⛔ 没有一个"作废这一颗令牌"的端点。要立刻废掉一批令牌，
   只有两条路 —— 轮换密钥（废掉该应用**全部**令牌）或停用应用（§7.6）。
   ⚠️ 代价如实登记：**泄露一颗令牌 = 在它剩余有效期内拿着该应用的全部权限**。

⚠️ **令牌里不带租户标识**：租户上下文只来自你请求的**域名**。⇒ 拿 A 家工作室的令牌
去打 B 家的域名，一律 `401` + `应用凭据无效`。要给 N 家工作室对接，就是 **N 套密钥 + N 个域名**。

⚠️ **令牌是凭据**：⛔ 别把它放进 URL / query（会进反代与浏览器历史）、⛔ 别写进前端代码、
⛔ 别贴进聊天群或工单；它应当只出现在**服务端发出**的 `Authorization` 头里。

**`client_id` / `client_secret` 从哪里来**：租户（工作室）在团团通后台的
「开放平台 → 应用管理」页面上创建应用，页面把 `AppKey`（= `client_id`）与
`AppSecret`（= `client_secret`）显示出来（§1.2）。**第三方开发者不调创建应用那一步**。

#### 换令牌的可跑示例

§9.2 的 Python 段里有一个 `fetch_token()`，可以直接复制使用（它把 401 的
`error` / `error_description` 翻成一个异常，⛔ 不会把裸体当成令牌）。

### 1.2 第二步：租户侧的准备（第三方⛔ 不调这些端点）

这一节的端点**调用方是租户自己**（工作室的人在网页上操作，或用**自己的登录会话**调这些
内部端点）：它们走**会话认证**（cookie + CSRF），⛔ **不认** Bearer 令牌，
而且要求操作人的账号有 `system.pinduoduo_settings` 节点。

| 方法 | 路径 | 认证 | 说明 |
|---|---|---|---|
| `GET` | `/api/open/apps/` | 会话 + 节点 | 列表（⭐ 每行含**明文 `app_secret`**，见 §7.4） |
| `POST` | `/api/open/apps/` | 会话 + 节点 | 创建：入参 `{"name": "<应用名，≤50 字符，租户内唯一>"}`，可顺带给 `callback_url` / `callback_state` |
| `PATCH` | `/api/open/apps/<pk>/` | 会话 + 节点 | 改单个字段：`{"state": "disabled"}` / `{"state": "enabled"}` / `{"name": "新名"}` / `{"ip_allowlist": "1.2.3.4\n10.0.0.0/8"}` / ⭐ `{"callback_url": "https://…"}` / `{"callback_state": "enabled"}`；缺席 = 保持原值 |
| `POST` | `/api/open/apps/<pk>/rotate-secret/` | 会话 + 节点 | 换密钥：响应含**新**密钥；**旧密钥当场失效、没有宽限期**（§7.3），该应用**全部已发出的令牌立刻失效**（§1.1） |
| `GET` | `/api/open/apps/<pk>/deliveries/` | 会话 + 节点 | **推送台账**（最近在前；`page` / `page_size` / `status`（可选，`pending`·`done`·`failed`））。⛔ **不含报文原文**、⛔ 不含任何凭据 |
| `POST` | `/api/open/apps/<pk>/deliveries/<delivery_pk>/retry/` | 会话 + 节点 | **手工重投**一条推送：⛔ **只允许 `status=failed` 的行**（`done` 重投 = 对方收到两次 ⇒ `1000`；`pending` 已经在队列里 ⇒ 同样 `1000`） |
| ⛔ | **没有 `DELETE`** | —— | **只能停用不能删**（§7.6）：已认证且有节点的调用方对 `DELETE` 得到 **405** |

**应用行载荷的键（`GET` / `POST` / `PATCH` / 轮换四条共用一个装配出口）**：
`id` / `name` / `app_key` / ⭐ `app_secret`（明文）/ `state` / `state_text` / `ip_allowlist` /
`callback_url` / `callback_state` / `last_used_at` / `secret_rotated_at` / `created_at`。

⭐ **锁定应用（§1.4）那五条内部端点的行载荷与上面这份键集逐字相同** —— 它们走的是**同一个**
装配出口，所以「明文 `app_secret` 随时可取」这条口径在那一类应用上**一字不变**（§7.4），
⛔ 没有第二份字段表。

⚠️⭐ **本节这些端点只认「通用应用」**（2026-10-09 起）：列表里**看不到**锁定应用，
拿锁定应用的 `pk` 打 `PATCH` / 轮换 / 台账 / 重投 ⇒ `code=1000` + `应用不存在`；
`POST` 建出来的也**是**通用应用。⇒ 两类应用各有一个页面、各管各的（变更记录见 §11.1）。

⛔ **今天**没有**任何"授权范围"要配**：一个应用凭据 = 本租户**全部**业务数据
（§0.1 第 2 条）。新建的应用**建好、启用即可用** —— ⛔ 不存在"还要去勾权限 / 勾游戏范围"
这一步，也⛔ 不存在"没勾 ⇒ 403"。

> ⛔⭐ **改准（2026-10-09，企微群码线；上面那一句原文保留）**：「没有『授权范围』要配」
> 对**通用应用**仍逐字成立，但**不再覆盖全部** —— 本版多了一类**锁定应用**（§1.4）：
> 它的权限在**创建那一刻就写死了**（只能读订单 + 只能写群聊二维码），创建入口也**不在这一页**。
> ⇒ 「没勾 ⇒ 403」这一档**对锁定应用是存在的**：它打白名单外的对外端点会拿到 **403**（§7.2）。
>
> ⛔⭐ **再改准（2026-10-09 修复轮）**：上面那句「只能读订单 + 只能写群聊二维码」**要按"取票
> 那一跳"读** —— 它是**取票端点**的入参约束，⛔ 不是「这个凭据碰过的图一定是群码」那种
> 凭证级不变量（票的图种由取票那一跳决定，**认领端点不重判图种**）。逐条口径与那处
> **存在但未修**的边界见 **§1.4**。

⭐ **仍然要做的一步**：如果这个应用要接收**主动回调推送**，租户要填**回调地址**
（`callback_url`，**仅 https**、且必须解析到公网地址，见 §5.7）并把 `callback_state` 置为
`enabled` —— 这两件事合起来才让推送**产生**（§5.1）。

**推送台账每行的键**：`id` / `event` / `event_text` / `order_no` / `source_order_no` /
`status` / `status_text` / `attempts` / `reason` / `response_status` / `next_attempt_at` /
`created_at` / `processed_at`。⚠️ `reason` 是**截断后**的诊断文本（页面上限 200 字符，
超出加 `…`）。

### 1.3 第三步：带令牌调业务端点

```
GET  https://<租户域名>/api/open/v1/orders/<order_no>/
GET  https://<租户域名>/api/open/v1/orders/?source_order_no=<值>
GET  https://<租户域名>/api/open/v1/orders/?updated_since=<ISO 8601，必须带时区>&page=1&page_size=100
POST https://<租户域名>/api/open/v1/orders/            （写：还要带 Idempotency-Key）
```

请求头（**读端点只要第一个**）：

```
Authorization: Bearer <令牌>
Idempotency-Key: <8–128 个字符的随机串>     ← ⚠️ 只有写端点需要，见 §2.2
```

- ⚠️ **路径末尾的斜杠不能少**（除了 `/api/open/oauth/token` 那一条**没有**斜杠）：
  漏了会先拿到 **301 重定向**；请按 §2 那张全表逐字照抄。
- ⚠️ **域名是"哪一个"**：本平台**一个租户一个域名**，密钥与域名是**绑定的一对**
  （拿 A 家的密钥打 B 家的域名 ⇒ **401**）。

**`Idempotency-Key` 的长度契约是 8–128 个字符**（含两端）：缺失 / 长度不合规 ⇒ `code=1000`
（⛔ **不会**"默默放行"——放行就等于同一笔业务被执行两次）。
⚠️ 键值请用**随机串**（例如 UUID 去掉横线）；⛔ 别拿订单号 / 时间戳当键（那样重试时会变成新键）。

### 2.3 幂等四态（六个写端点共用同一份实现）

同一个 `Idempotency-Key` 在**同一个应用**下的四种状态：

| 状态 | 判据 | 答复 |
|---|---|---|
| **新键** | 这个键没见过 | 执行副作用 + 记下这一步的响应快照 |
| **同键同体** | 键见过、请求体**逐字节相同**、快照非空 | **回放上一次的响应**（HTTP 与信封逐字相同，⛔ 不会执行第二遍） |
| **同键异体** | 键见过、但请求体不同 | `code=1000` + `同一个幂等键配了不同的请求体` |
| **在飞** | 键见过、但上一笔**还在处理中**（快照为空） | `code=1001` + `同一个幂等键的请求正在处理中` |

- 缺失键 ⇒ `1000` + `缺少幂等键`；长度不在 8–128 ⇒ `1000` + `幂等键长度必须是 8–128 个字符`。
- ⭐ **业务失败（码非 0 且一行都没写）⇒ 这个键下次可以重试**（我方会把那一笔的内部记录
  整笔回滚，⛔ 不会让你永久卡在"正在处理中"）。
  ⚠️ 唯一的例外是「单已建好、后续动作没成」那两档（`1022` / `1023`，§4.4）：订单**已经落库**，
  重发会**回放那一句失败**（⛔ 不会重试后续动作，也⛔ 不会再建一张单）。
- ⚠️ **回放的是"上一次那次的响应快照"**，⛔ **不是**"拿库里现在的值重新渲染"：
  两次调用之间若那一单被别的路径改过，回放出来的仍是**上一次的载荷**。
- ⚠️ 幂等台账的保留期是 **30 天**（与 §2.4 的去重窗口同一个数）：超过窗口后同一个键
  会被当成**新键**。

### 2.4 来源单号去重（同一应用 + 同一来源单号 ⇒ 同一张单）

⭐ **来源单号**（`source_order_no`，**你自己**的单号）在录单时**必填且非空**。我方按它做
**第二道去重**：

| 你做的 | 服务端行为 |
|---|---|
| 同一个应用 + 同一个 `source_order_no` **再录一次** | **回放原来那张单**（`code=0`，`data.order_no` 与第一次**同一个**），⛔ **不建第二单**，⚠️ 一次副作用都不发生（连新的留痕都没有） |
| 换一套密钥（= 另一个应用）+ 同一个来源单号 | **不算重复**：去重按**应用**分桶 ⇒ 会**新建**一张单 |
| 超过窗口后再录同一个来源单号 | ⚠️ **会新建一张单**（见下面的窗口） |

- ⚠️⭐ **去重窗口 = 30 天**（我们自己的幂等台账保留期；两份台账都是 30 天）
  ⇒ **超过 30 天**之后再用同一个来源单号录单，会**再建一张单**。
  ⇒ 「同一个来源单号永远只对应一张单」这件事**只在 30 天窗口内成立**，
  ⛔ 不要把它当永久去重来设计你的对账逻辑（要永久只能靠你自己那边的单号管理）。
- ⚠️ 两道去重的**先后**：`Idempotency-Key` 先判（同键重发 ⇒ 回放**那一次**的响应），
  来源单号在后（换了键、同一个来源单号 ⇒ 回放**原单**的响应）。两道都生效，⛔ 不靠你自觉。
- ⛔ **不接受调用方关掉去重**：没有"忽略重复单号"这类开关（对标文档里有，我们**不照抄**，
  见 §4.4 的对标差异表）。

### 2.5 字段白名单是 fail-closed：表外的键 ⇒ `1000` 并点名

录单（§4.4）与改单（§4.6）都只接受**一张显式的字段表**；**表外的键一律被拒**：

- 答复是 `code=1000` + **一行都不落库**，`msg` 会**点名**是哪些键，
  例如 `请求里有本 API 不接受的字段：hours、gamePassword`；
- ⛔ **不是"忽略"**：我们不会收下一个字段然后悄悄丢掉它 —— 那样你会以为写进去了、其实没有，
  **而且没有任何信号**（"静默丢字段"比报错更贵）；
- ⚠️ 值是不是空的**不影响**这条判据：`""` / `null` 的未知键**照拒**；
- ⚠️ 表内的**可选**字段缺失**仍然照旧**（可选就是可选，⛔ 别读成"都要必填"）。

⇒ 照**对标文档**写的调用方会在**第一次调用**就看到 `1000`。差异逐条列在 §4.4 的对标差异表里。

## 4. 各端点的完整契约

### 4.1 `GET /api/open/v1/orders/<order_no>/` —— 按团团通订单号查一张单

- 路径**逐字**（**注意末尾斜杠**）：`/api/open/v1/orders/<order_no>/`
  ⇒ 完整 URL 形如 `https://<租户域名>/api/open/v1/orders/20261008120000000042/`
- `<order_no>` 是**路径段**，直接放在路径里（⛔ 不要对它做百分号编码）。
- 请求头：`Authorization: Bearer <令牌>`。无 query、无 body。
- 成功响应：`code=0`，`data` = **一张订单对象**（字段见 §3）。
- 查不到（不存在 / 不是本租户的单）：`code=1002` + `msg="记录不存在或已被删除"`（**HTTP 200**）。
  ⚠️ 这两种情况**故意不区分**（§7.2）。
- ⚠️ **同一条路径上还有一个 `PATCH`（改单）**（§4.6）：两条方法用**同一套** Bearer 令牌。

### 4.2 `GET /api/open/v1/orders/?source_order_no=<值>` —— 按来源单号查（可能多张）

- 路径**逐字**（**注意末尾斜杠**）：`/api/open/v1/orders/`
- ⚠️ query 的键名就是 `source_order_no`；值超过 **128 字符** ⇒ `code=1000`。
- 成功响应：`code=0`，`data = {"items": [ 订单对象, ... ], "total": <命中总数>}`。
- ⚠️ **`items` 最多 20 条**（按 `id` 升序 —— 那是订单的主键，不是订单号）。
- ⭐ **`total` 是"命中的总条数"，⛔ 不是"本页条数"**：命中 21 条时 `total=21` 而 `items`
  只有 20 条。要拿全就得换键（按订单号逐张查）。

**`source_order_no` 的三种取值语义（逐字冻结）：**

| 你发的 | 服务端行为 |
|---|---|
| **不带这个参数**（`/api/open/v1/orders/`） | `code=1000`，`msg` 说明缺参数。⛔ **不会**回全部订单 |
| **带空串**（`?source_order_no=`） | **按空串查**：通常命中 0 条 ⇒ `code=0`、`items=[]`、`total=0` |
| **带值** | 按值精确匹配（订单表上这一列**没有唯一约束** ⇒ 可能多张单） |

- 命中 0 条 **不是** 404：`code=0` + 空列表 + `total=0`（HTTP 200）。

> ⛔⭐ **改准（2026-10-09，企微群码线；上面那张表与那几行原文保留）**：这条路径今天**多了一个
> 合法的筛选参数**（`updated_since`，见下面 §4.2.1）⇒ 上面那句「**不带这个参数** ⇒ `msg` 说明
> 缺参数」多了一句新文案，而「`source_order_no` 是**必填**」这句话**不再成立**（它现在是与
> `updated_since` **二选一**）。逐条：
>
> - 两个参数**都没给** ⇒ `code=1000` + `msg` **逐字**：`缺少参数：source_order_no 或 updated_since`
>   （⚠️ 旧文案是 `缺少参数：source_order_no`，见 §11.1 的变更登记）；
> - 两个参数**都给了** ⇒ `code=1000` + `msg` **逐字**：`参数 source_order_no 与 updated_since 只能选一个`；
> - ⚠️ 对旧调用方**行为零变化**：只传 `source_order_no`（含只传空串那一档）时形状与语义**一字未动**；
> - ⛔ `page` / `page_size` 在**本档不生效**：它们只属于 §4.2.1 那一档（本档的输出上限仍是
>   `items` 的 20 条）。

#### 4.2.1 按时间**增量拉单**（`?updated_since=`）—— 本版新增的用法

```
GET https://<租户域名>/api/open/v1/orders/?updated_since=2026-10-09T10:00:00%2B08:00&page=1&page_size=100
Authorization: Bearer <令牌>
```

**入参（三个）**：

| 入参 | 口径 |
|---|---|
| `updated_since` | 这一档的**必给**参数：ISO 8601，且**必须带时区**（`+08:00` 或 `Z`）。⚠️ 不带时区（`2026-10-09T10:00:00`）/ 格式非法（`abc`）/ **空串** ⇒ `code=1000` + `msg` **逐字** `时间参数 updated_since 必须带时区`。⛔ 我们**不会**替你按某个时区猜 —— 静默按我们的本地时区解释会让你的游标窗口整体偏移（漏单或多单），而症状只是"你那边少了几张单" |
| `source_order_no` | ⛔ **不能与 `updated_since` 同时给**（同时给 ⇒ `code=1000` + 二选一那句，见 §4.2） |
| `page` / `page_size` | 可选，**只在这一档生效**：默认 `1` / `20`；`page_size` 上限 **100**（超过就**夹到 100**）；非法（`abc` / `0` / 负数）⇒ `code=1000` |

**答复**：`code=0`，`data` **恰好四个键**：

```json
{"count": 12, "results": [ 订单对象, ... ], "page": 1, "page_size": 20}
```

- `results` 的每一行 = **与 §4.1 / §3 逐字相同的订单载荷**（顶层 17 键）——⛔ 不是"为轮询优化的
  精简版"（代价：响应体更大，含 `costs` 成本与提成）；
- `count` 是**命中总数**、⛔ 不是本页条数；分页口径与 §4.3 那三个列表端点**同一套**；
- 页号超出范围 ⇒ `code=0` + 空 `results` + **真实的** `count`（⛔ 不是 `1002`）；
- ⭐ **不给 `updated_since` 时，返回形状与旧版逐字相同**（`{"items", "total"}`，§4.2）⇒ 旧客户端
  **零感知**。

**取哪些单（逐条都是契约）**：

| 项 | 口径 |
|---|---|
| 时间边界 | `updated_at >= updated_since`（**含端点**）：恰好等于那一刻的单**会**给你 |
| 排序 | `updated_at` **升序** → 同一时刻再按 `id` 升序。⭐ 升序是**有意**的（你要拿"上一批最后一个 `updated_at`"当游标往下走）；⚠️ 同刻并列时**必须靠 `id`** 才有确定次序，请按**这两个键一起**的顺序处理 |
| 范围 | 只有**本租户**、**未软删**的单（与 §3.8 同一条边界） |

**⚠️ 两条如实登记的边界**（照它设计你的对账逻辑，⛔ 别把它当成"任何变化都能拉到的通道"）：

1. **它不是"任何变化都能拉到"的通道**：这一档靠的是订单的**更新时间戳**，而本平台存在**绕过它的
   写链路**（直接改库的那些动作，例如某些对账 / 退款 / 上游同步）⇒ 经那些链路发生的改动
   **不会**出现在增量结果里。
   - ⭐ **对"发现新单"这个用途不构成缺口**：新建的单一定会带上时间戳；
   - ⛔ **别拿增量结果当"这一张单现在的样子"**：要确认某张单的最新状态，请**按单号查详情**（§4.1）；
   - ⚠️ **删除也看不到**：软删**不**更新那个时间戳 ⇒ 增量里**不会**出现"某张单没了"这件事。
     要感知删除只能靠 §5.1 的 `order.deleted` 回调。
2. **游标请回退一个"重叠窗口"**：我们按"写库那一刻的时间戳"取值，而**取值序 ≠ 提交序**
   （极端并发下时间戳更早的那一笔可能**后**提交）⇒ 如果你严格拿"上一批最大的 `updated_at`"当游标，
   **可能漏掉**那一张单（⚠️ 不是只会重复）。
   ⇒ 正确用法是拿 **`max(updated_at) - 重叠窗口`**（例如往前退 **2 分钟**）当下一轮的 `updated_since`，
   重复取到的行请按**你自己那边的业务键**去重。⛔ 本版**没有**"时间戳 + 主键"的复合游标参数。

### 4.4 写端点：录单 `POST /api/open/v1/orders/`

- 请求头：`Authorization: Bearer <令牌>` + `Idempotency-Key`（**必带**，8–128）。
- **必填**：`game`（**本租户**的游戏 id）、`project_text`（代练/陪玩项目，自由文本）、
  `total_price`（客户支付价，**金额字符串两位小数**）、`source_order_no`（**你自己的单号**，
  非空、≤ 128 字符）。
- **可选**：`server`（区服 id）、`game_account`、`game_role_name`、`content`（客户原文）、
  `remark`（备注 —— ⚠️ **写得到、查单读不回**：它是我方员工写的东西，不在 §3 的白名单里）、
  `hall_price`（发单价，**金额字符串两位小数**）、`assignee`（建单后指派给这个内部用户 id）、
  `throw_to_hall`（`true` = 建单后抛进内部抢单大厅；与 `assignee` **互斥**，同时给 ⇒ `1000`；
  为真时 `hall_price` 必须 `> 0`，否则也是 `1000`）。
- ⛔⭐ **表外的键一律被拒**（`code=1000` + **一行都不落库**，`msg` 点名，见 §2.5）。
- 成功响应：`code=0`，`data` = **这张单的查单载荷**（键集与 §3 逐字相同）。

**这一条端点的作答码（逐档）：**

| `code` | 什么情况 |
|---|---|
| `0` | 建单成功（`data` 见上） |
| `1000` | 缺 `Idempotency-Key` / 键长不合规 / **表外字段** / 缺必填（含 `source_order_no` 为空）/ 参数非法（金额、`game`、超长单号）/ `game` 不是本租户的 |
| `1001` | 同一个 `Idempotency-Key` 的上一笔**还在处理中**（稍后用**同一个键**重试即可） |
| `1022` | 单**已建好**、但**指派没成**：`data = {"order_no", "reason", "assign_code"}` |
| `1023` | 单**已建好**、但**抛入内部抢单大厅没成**：`data = {"order_no", "reason"}` |
| `401` / `403` / `429` | 凭据 / 权限 / 限流（见 §6.2） |

⚠️⭐ `1022` / `1023` 出现时**订单是存在的**（单号就在 `data` 里）⇒ ⛔ **不要再录一次**：
用同一个 `Idempotency-Key`（或同一个 `source_order_no`）重发会**回放同一份响应**（§2.3 / §2.4）。

#### ⛔ 对标差异表（如实写：对标有的、我们没有；形态不同的）

我们的接口**形态**对标鸡蛋铺的开放平台，但**字段名与字段集用我们自己的**（形态对齐、
⛔ 不照抄对标的拼写），而且有几处**行为**也不同。照对标文档写的调用方会在**第一次调用**
就看到下面这些答复：

| 对标那边的名字 / 行为 | 我们这边的情况 | 你该怎么做 |
|---|---|---|
| `hours`（"时间要求（小时）"） | 在我们的数据模型里它是**绩效行**的列（**每人一份**，不是订单级的），录单端点**不收**它 | ⛔ 别传（传了 ⇒ `1000`）；要表达时间要求就用 `project_text` / `content` / `time_requirement`（改单那张表里有） |
| `customerId`（客户标识 / 会员号） | 我们**没有**"客户/会员"主键这一列（只有 `customer_phone` / `customer_qq` / `customer_ww` 三个联系方式列，它们**也不在**录单字段表里） | ⛔ 别传（传了 ⇒ `1000`）；客户联系方式本批**只能**在租户自己的后台补 |
| `game_password`（客户游戏密码） | 订单表上**没有**密码列 ⇒ "记录客户游戏凭据"这件事本系统今天不做 | ⛔ 别传（传了 ⇒ `1000`） |
| `gaemTf`（对标那个拼写） | 语义对应我们的"区服"，我们的字段名是 `server`（**本租户**的区服 id） | 传 `server` |
| `souresOrderID`（对标那个拼写） | 语义对应"你自己的单号"，我们的字段名是 `source_order_no`（**必填**） | 传 `source_order_no` |
| `ignoreRepeatOrderNo`（对标那个"忽略重复单号"开关） | ⛔ **不照抄**：幂等与来源单号去重是**我们**的契约，**不接受调用方关掉** | ⛔ 别传；重复提交（同键或同 `source_order_no`）一律回放原来那一单（§2.3 / §2.4） |
| `ImgType=1`（进群二维码） | ⛔ **本批不收**：那是我们**内部**的业务动作（每个租户自己的群邀请），第三方没有它的语义 | ⛔ 别传 `img_type=1`（传了 ⇒ `1000`，§4.7） |
| **上传截图**是一个接口传一个 `imgUrl` | 我们是**两步**：**取票**（拿一次性上传地址）+ **认领**（告诉我们传完了）—— 我们的服务器**不会**去抓你给的 URL（§4.7） | 照 §4.7 的三步做（取票 → 直传 → 认领） |
| **排行榜**（`GetRecOrderRankList`） | ⛔ **本批不实现**：本平台没有对应物 ⇒ 路径保留，恒回 `code=1024` + `接单排行榜尚未开放` | ⛔ 别拿 `1002` / `1000` 去猜它的意思（那两档说的是别的事） |
| **交单时间**（对标会有一个真实时刻） | 我们**没有**这一列 ⇒ `submitted_at` **恒为 `null`**（§4.3） | 判空用 `is null`；⛔ 别等它"过一阵会有值" |
| **响应码方向** | 我们：**`code == 0` 是成功**，非 0 是失败；对标：读接口 `code == 0` 成功、**写接口 `code > 0` 才是成功**（两个方向相反） | ⛔ 别把对标的判据抄过来：在**我们**这里 `code > 0` 一律是失败 |

⚠️ 上表**只点名**了几个最常见的、最容易照抄错的；完整的"我们能收什么"以本节上面那张
**必填 / 可选**清单为准 —— 那张清单**就是契约的全部**，清单外的键一律 `1000`（§2.5）。

### 4.5 改状态 / 改发单价

- `POST /api/open/v1/orders/<order_no>/status/`：入参 `{"status": "<枚举值>", "remark": ""}`
  ⇒ 成功 `data = {"order_no", "status", "status_text"}`。
  ⚠️ **只收枚举值**（例如 `IN_PROGRESS`），⛔ 中文标签会被拒（`1000`）。
  `remark` 可选（≤ 255）—— 它落我们内部的留痕行（"问题单 / 已暂停"这两个目标态最常需要它）。
- `PUT /api/open/v1/orders/<order_no>/assign-price/`：入参
  `{"price": "<金额字符串两位小数>", "reason": ""}` ⇒ 成功 `data = {"order_no", "hall_price"}`。
  ⚠️ **只收金额**：⛔ 内网那种 `"50%"`（按接单价比例）形态**对外没有** ⇒ 传了回 `1000`。
  ⚠️ 金额 `0` 与**负数**都合法（负值表示冲抵 / 退款口径），⛔ 别自己加"必须大于 0"的校验。

**状态枚举值（发这些；中文只是给你看的对照）：**

| 值（**发这个**） | 中文标签（⛔ 发中文会被拒：`1000`） |
|---|---|
| `UNASSIGNED` | 未分配 |
| `WAITING_GRAB` | 待抢单 |
| `IN_PROGRESS` | 代练中 |
| `PENDING_REVIEW` | 待验收 |
| `COMPLETED` | 已完成 |
| `ISSUE` | 问题单 |
| `PAUSED` | 已暂停 |
| `REFUNDED` | 已退单 |

⚠️ 这张表是平台状态枚举的**抄件**（方便读文档的人），⚠️ 也⛔ 不写"共 N 个状态"这类会过期的
绝对句：**校验只认平台那一个出处**，平台加状态时这张表**不自动跟上** ——
权威条数以你实际拿到的 `1000` 答复为准（`msg` 里会列出合法取值）。

**这两条与录单共用同一套幂等口径**（§2.3 那四档**逐字相同**：同键同体 ⇒ 回放、
同键异体 ⇒ `1000`、缺键 ⇒ `1000`）；业务失败则回**领域规则给的那个码**：

| `code` | 什么情况 |
|---|---|
| `1002` | 那张单查不到（不存在 / 已软删 / 不是本租户），**或**这条状态流转不允许（状态机判非法边） |
| `1014` | 该单的打手工资**已结账** ⇒ 一律拒绝改发单价（`msg`：`该单的接单人绩效已结账，不能改发单价；请先撤销结账再改`） |
| `1000` | 入参非法（非枚举的状态值 / 金额形状不对 / 超长 `remark`） |

### 4.6 改单 `PATCH /api/open/v1/orders/<order_no>/`

改一张已有订单的**普通字段**（客户信息、项目文本、备注…）。⛔ **改不了**状态、金额、
订单号与归属人 —— 那几样各有自己的专用端点（状态走 §4.5 的 `status/`、发单价走
`assign-price/`），**在这里传它们会回 `1000`**。

- 请求头：`Authorization: Bearer <令牌>` + `Idempotency-Key`（**必带**，8–128）。
- 请求体：**只放你要改的字段**（`PATCH` 语义：没提到的字段保持原值）。
- 成功响应：`code=0`，`data` = **改完之后**那张单的查单载荷（键集与 §3 逐字相同）。
- ⚠️ **与 `GET /api/open/v1/orders/<order_no>/` 是同一条路径的两条方法**
  （查一张 / 改一张），两条**用同一套** Bearer 令牌。

**可以改的字段（恰好这 25 个）：**

| 你要改的 | 说明 |
|---|---|
| `game` | **本租户**的游戏 id（换游戏会连带校验区服 / 分类 / 项目是否对得上） |
| `server` / `category` / `project` | 区服 / 项目分类 / 项目 id（三者必须与 `game` 同一条链，否则 `1000`） |
| `project_text` | 代练 / 陪玩项目（自由文本，**必填** ⇒ 传空串回 `1000`） |
| `order_type` / `source` / `source_order_no` / `tag` / `is_urgent` | 订单类型 / 来源 / 你的单号 / 自定义标记 / 是否加急 |
| `content` / `demand` / `time_requirement` | 客户原文 / 需求描述 / 时间要求 |
| `game_account` / `game_sub_account` / `game_role_name` | 游戏账号 / 子账号 / 角色名 |
| `current_info_1` / `current_info_2` | 当前信息（两列，语义由你们自己定） |
| `customer_phone` / `customer_qq` / `customer_ww` | 联系电话 / QQ 或微信 / 旺旺或 YY |
| `payment_method` | 支付方式（**收款状态不行**，见下） |
| `sales_agent` | 接单销售客服（自由文本那一列） |
| `remark` | 备注（⚠️ **写得到、查单读不回**：它是我方员工写的东西，不在 §3 的白名单里） |
| `order_source` | 来源字典项 id |

**⛔ 不可以改的字段（传了 ⇒ `1000` + 一行都不落库）：**

| 字段 | 为什么 |
|---|---|
| `status` | 状态**只能**走 §4.5 的 `status/` 端点（状态机要判合法边） |
| `total_price` / `received_price` / `platform_price` / `hall_price` / `refund_fee` / `fee` | 金额只能走各自的专用动作（改价要单独留痕） |
| `sales_user` | 归属人决定客服提成的归属，⛔ 不接受通用改单 |
| `payment_status` | 收款状态只能走专用端点 |
| `order_no` / `id` | 单号与主键是身份，⛔ 不给改 |
| `created_at` / `updated_at` / `created_by` / `updated_by` | 时间与"谁改的"由**我们**写（对外记成「开放平台应用 <应用名>」） |
| `completed_at` / `hall_publisher` / `deleted_at` / `deleted_by` | 由服务端动作（完单 / 抛单 / 软删）写 |
| **任何我们不认识的键** | 例如对标文档里的 `hours` / `gamePassword`（我们没有这几样，见 §4.4 的对标差异表） |

⚠️ **"传了 ⇒ `1000`"与录单（§4.4）是同一条纪律**：我们**不会**收下一个字段然后悄悄丢掉
（那样你会以为写进去了、其实没有，**而且没有任何信号**）。`msg` 会**点名**是哪些键。

⚠️ **`PATCH {}`（一个字段都不改）是合法的**（`code=0`，什么都不改、也不写留痕）。

**这一条端点的作答码（逐档）：**

| `code` | 什么情况 |
|---|---|
| `0` | 改成功（`data` 见上）；`{}` 空改也是 `0` |
| `1000` | 缺 `Idempotency-Key` / 键长不合规 / **表外字段**（含只读字段与未知字段）/ 参数非法（`game` 不是本租户的、`project_text` 为空、超长文本、非法枚举值）/ 请求体不是 JSON 对象 |
| `1001` | 同一个 `Idempotency-Key` 的上一笔**还在处理中** |
| `1002` | 这张单**查不到**（不存在 / 已软删 / 不是本租户——三者**同形**） |
| `401` / `403` / `429` | 凭据 / 权限 / 限流（见 §6.2） |

⚠️ **改单不留"改了 A→A"的噪音**：某个字段你传的值与库里**一模一样**时，那一列**不写留痕**
（业务结果仍然是 `code=0`）。
⚠️ **幂等回放的是"上一次那次的响应快照"**（⛔ 不是"拿库里现在的值重新渲染"，§2.3）。

### 4.7 进度图：**取票 + 认领**两步

⚠️⭐ **本节与对标的形态有意不同**（对标是**一个接口**传一个图片 URL；我们是**两步**）：
本系统所有图片都走**浏览器/客户端直传对象存储**（我们只发一张一次性上传凭据），
⛔ **我们的服务器不会去抓你给的 URL**（那会引入 SSRF 面）。⇒ 你的接法是三步：

| 步骤 | 干什么 | 端点 |
|---|---|---|
| ① **取票** | 告诉我们"要传一张进度图"，拿回一个对象名与一个一次性上传地址 | `POST /api/open/v1/orders/<order_no>/images/ticket/` |
| ② **直传** | 把图片字节 **PUT** 到 `upload_url`（地址自带授权，⛔ 不用带令牌） | （对象存储，不经我们的 API） |
| ③ **认领** | 告诉我们"传完了" ⇒ 我们校验 + 把这张图挂到订单上 | `POST /api/open/v1/orders/<order_no>/images/` |

**① 取票**：入参 `{"ext": "jpg", "img_type": 0}` ——
`ext` **必填**，只收 `jpg` / `jpeg` / `png`（表外 ⇒ `code=1000`）；
`img_type` 可选、**只允许 `0`**（订单进度图）。
⛔ **对标有 `ImgType=1`（进群二维码）、我们对本 API 不做**：传 `1` ⇒ `code=1000`
（那是我们内部的业务动作，第三方没有它的语义）。
成功回 `data` **恰好三个键**：`key`（对象名）/ `upload_url`（一次性直传地址）/
`expires_in`（**秒**；到期前必须传完，否则那个地址失效，要重新取票）。

> ⛔⭐ **改准（2026-10-09，企微群码线；上面那三行原文保留）**：`img_type` 今天**按应用类别
> 分叉** —— 上面那句「只允许 `0`」与「第三方没有它的语义」是**通用应用**的情形；
> **锁定应用**（§1.4）**恰好相反**。逐格如下：

| 应用类别 | 你传的 `img_type` | 结果 |
|---|---|---|
| **通用应用**（§1.2；缺省就当 `0`） | 缺省 / `0` | ✅ 成功：订单进度图（**今天的行为一字不变**） |
| **通用应用** | `1` | `code=1000` + `本接口只支持订单进度图（img_type=0）`（**今天的行为一字不变**） |
| **通用应用** | **其它任何整数**（`2` / `-1` …） | `code=1000` + **同一句** `本接口只支持订单进度图（img_type=0）` |
| **锁定应用**（§1.4） | `1` | ✅ 成功：**群聊二维码**（本版新增的用法） |
| **锁定应用** | 缺省 / `0` | `code=1000` + `本应用只能上传群聊二维码（img_type=1）`（⛔ **不按 `1` 兜底**：漏填参数就是漏填） |
| **锁定应用** | **其它任何整数**（`2` / `-1` …） | `code=1000` + **同一句** `本应用只能上传群聊二维码（img_type=1）` —— ⚠️ 逐字写清：锁定应用这一支的判据只有"**是不是 `1`**"，⛔ **没有**"其它取值 ⇒ 另一句非法取值文案"这回事（对不上文案时请照这一行核） |
| **两类都一样** | **不是整数**（`"abc"` / `true` …） | `code=1000` + `请填写合法的整数值。` —— ⚠️ 这一句**不是本平台写的**（框架语言包的文案），而且它发生在"按应用类别分叉"**之前** ⇒ **两类拿到的是同一句**，与上面那些业务文案**都不是同一句** |

**群聊二维码（`img_type=1`）这一行的语义（逐条如实登记）**：

- 它**只对锁定应用开放**（每租户一把，§1.4）；通用应用**仍然收不到**它（上表第二行）；
- 对象名走**共享段** `shared-orders/<链上最初单号>/qr.<随机>.<ext>`（⭐ 改准：`D-0316`，
  2026-10-27——群码随订单同步，⛔ 不再是本租户前缀）；
- **不占"每单最多 20 张"那个名额**（20 只数订单进度图）——⚠️ 但它有自己的约束：
  **每单最多 1 张**，且**认领新图时自动淘汰**本单上一张**已认领**的群码（覆盖语义）。
  ⚠️ 取票之后**还没认领**的那些 `pending` 行**不**淘汰，它们由 **24 小时**的清理任务收掉
  ⇒ 程序化客户端可以反复取票、攒下多条 `pending` 群码行（⛔ 本版不加新闸，如实登记）；
- ⛔ **只进「租户 ↔ 租户」的同步通道、且只做 peer 广播**（⭐ 改准：`D-0316`，2026-10-27）：
  群码的 `order.screenshot.add` 会随订单同步到上下一级（接收侧**后到覆盖**、同单只留最新一张），
  但**删除不广播**、共享字节删行时**不删**；开放平台 `order.image_added` 回调仍**不推**群码；
- ⛔ **也不会推 `order.image_added` 回调**（§5.6 里 `img_type` 恒为 `0`）；
- ⚠️⭐ **但它会跟人工上传的群码一样，出现在我们另一条既有的出站链路上** —— 本平台会把该单的群码
  按图种转给**对标平台**那套会员图推送。⚠️ 那条链路**不是**本 API、本版也⛔ **没有**新开任何
  通道，但「群码不会外流」这句话**不成立**：请按"这张群码会被转发出去"来理解；
- ⚠️ **认领端点（③）没有 `img_type` 入参**：图种来自**取票那一跳**（你取票时传的值）。
  认领成功回的"该图片项"里那个 `img_type` 会**照给**（`1`，它本就是列表项的七个键之一）。

> ⛔⭐ **改准（2026-10-09，企微群码线；上面那几条原文保留）**：把上面「**群聊二维码这一行的
> 语义**」与「**认领端点（③）没有 `img_type` 入参**」两条合起来才是**完整**的口径 ——
> **"锁定应用只能传群聊二维码"是取票那一跳的限制**（那个端点只接受 `img_type=1`），
> ⛔ 它不是"这张票一定是群码"那种**凭证级 / 行级不变量**：**票的图种由取票那一跳决定，
> 认领端点不重判图种**（它只认「本单 + 还没认领 + 同一个上传人」）。
> ⇒ 由此有一条**存在但本版未修**的边界（前提三条 + 代价），逐条写在 **§1.4** 那张表下面。

**③ 认领**：入参 `{"key": "<取票时回的对象名>", "original_name": "", "remark": ""}` ——
`key` **必填**；`original_name` ≤ 255、`remark` ≤ 50（超长 ⇒ `code=1000`）。
成功回 `data` = **该图片项**，键集与 §4.3 的 `images/` 列表项**逐字相同**（七个键）。
⭐ 认领成功还会**推一条 `order.image_added` 回调**（§5.1）。

| `code` | 什么情况 |
|---|---|
| `0` | 成功（③ 成功时这张图**已在订单上**） |
| `1000` | 缺键 / 键长不合规 / `ext` 不在白名单 / **`img_type=1`** / `key` 找不到待认领的记录 / 对象还没传上来 / 空文件 / 超过 **18 MiB** / 不是 jpg 或 png / 端点路径过长（订单号那一段长得超出可存范围时回这一档，⛔ 不是 500） |
| `1002` | 取票时**这张单查不到**（不存在 / 已软删，两者**同形**） |
| `403` | 对象名**不属于当前租户**（`msg` 说明原因） |
| `401` / `429` | 凭据 / 限流（见 §6.2） |

⚠️ **如实登记的边界**：① 每张单**最多 20 张**订单进度图（含已取票但还没认领的），
第 21 张起回 `1000`；② 认领失败时**那一行会被清掉**，你可以重新取票；
③ 取票之后一直不认领的行会被**定期清理**（**24 小时**的清理任务收掉它，那个 `key` 也就作废了）
——⛔ 别把"取了票"当成"传好了"：拿到票要在 `expires_in` 之内 PUT，再调认领。
⚠️ `expires_in` 由**对象存储那一层**给出（⛔ 不是我们编的固定值）：它在不同环境可能不同，
请**读响应里的那个数**，别在代码里写死。

## 5. 回调推送契约（我们推给你）

⭐ **这是第三方唯一需要自己实现签名的地方**（§0.1）。这一节是**完整**契约：
报文字段、签名算法、请求头、期望回执、重试节奏、以及"至少一次"该怎么处理。

### 5.1 什么时候推、推哪三种事件

推送的**前提**（三个条件同时成立）：应用 `state=enabled`、`callback_state=enabled`、
`callback_url` 非空（§1.2）。三个条件任一不成立 ⇒ **根本不会产生推送**（⛔ 不会给你报错，
也不会排队等你）。

| `event` | 什么时候推 | 多带的字段 |
|---|---|---|
| `order.status_changed` | 订单状态发生变化（含通过本 API 改的、以及租户在页面上改的） | `status`、`note` |
| `order.deleted` | 订单被删除（软删） | 无（报文里就是 §5.2 那 8 个通用键 + `timestamp` + `sign`） |
| `order.image_added` | 订单新增一张进度图（**认领成功后**，含通过 §4.7 认领的） | `images`（一张列表，见 §5.6） |

⚠️ **⛔ 建单本身不推**：第三方感知"新建了一张单"靠的是**你自己那次录单的应答**（§4.4）。
⚠️ **同一件事不会重复入队**：我方在入队前已按（应用 + 事件 + 订单号）去重
（同一状态、同一张图不会被推两次）。⚠️ 但**重投**与"至少一次"仍在 ⇒ 仍请按 §5.5 去重。
⚠️ **顺序**：同一订单**按产生顺序**推送（前一单还没投出去时，后一条会等）；
**不同订单之间不保证顺序**。

### 5.2 报文字段（逐字段）

`POST` 到你的 `callback_url`，`Content-Type: application/json; charset=utf-8`。
以 `order.status_changed` 为例（**这个例子里的值都是合成值**）：

```json
{
  "event": "order.status_changed",
  "delivery_id": "6f1c0f7c9a2e4f0b8a3d5c7e9f1a2b3c",
  "order_no": "20261008120000000042",
  "source_order_no": "AB-2026-0007",
  "status": "IN_PROGRESS",
  "note": "",
  "occurred_at": "2026-10-08T12:00:00+08:00",
  "timestamp": 1760000000,
  "sign": "b44b31b4a46978079edf28e78ba06f2e30fa7fad6d02d560c059befdf910286f"
}
```

| 键 | 类型 | 说明 |
|---|---|---|
| `event` | string | 事件名，三种之一（§5.1）。⚠️ 请按它分派，⛔ 别按"哪个键在不在"猜 |
| `delivery_id` | string | ⭐ **这一条推送的去重身份**（32 位十六进制）。**同一条推送的每一次重投都沿用同一颗**（§5.5） |
| `order_no` | string | 团团通订单号 |
| `source_order_no` | string | 来源单号（**你自己**的单号）。⚠️ 没有时是**空串**（⛔ 不是 `null`） |
| `status` | string | 目标状态码（**只有** `order.status_changed` 带；取值同 §4.5 那张枚举表） |
| `note` | string | 备注（`order.status_changed` 带；本批恒为**空串**，⛔ 但**键一定在**） |
| `images` | array | 进度图列表（**只有** `order.image_added` 带，见 §5.6）。每项是 `{"url", "img_type", "remark"}` |
| `occurred_at` | string | 业务事件**发生的时刻**（ISO 8601，带时区偏移）⚠️ 与 `timestamp` 不是同一个时刻（见下） |
| `timestamp` | integer | ⭐ **这一条推送发出的时刻**（UTC Unix 秒）。它参与签名（§5.3） |
| `sign` | string | ⭐ 签名（小写 hex，64 位）。**它盖住的是"去掉 `sign` 之后的整个报文"**（含 `timestamp`） |

⚠️ **`occurred_at` 与 `timestamp` 是两件事**：前者是"这张单什么时候变的"，
后者是"我们什么时候发的"（签名覆盖它，也是你判新鲜度的依据）。
⚠️ **`timestamp` 与 `sign` 都是投递那一刻现算的**：同一条推送重投时**两个都会变**
（`delivery_id` ⛔ **不变**）⇒ 请用 `timestamp` 判新鲜、用 `delivery_id` 判重复。

### 5.3 签名算法与三个请求头（**逐字冻结**）

```
body_without_sign = 收到的报文 JSON 里**去掉 "sign" 键**之后的那份对象（timestamp **在**里面）
canonical         = json.dumps(body_without_sign, ensure_ascii=False, sort_keys=True,
                               separators=(",", ":")) 的 UTF-8 字节
sign              = HMAC-SHA256(key = app_secret, msg = f"{timestamp}\n{delivery_id}\n"
                                                     f"{sha256(canonical).hexdigest()}") 的 hex（小写）
```

请求头（三个，**逐字**）：

```
X-TT-Timestamp: <Unix 秒，十进制整数，与报文里的 timestamp 同一个值>
X-TT-Delivery:  <delivery_id，与报文里的同一个值>
X-TT-Signature: <sign，与报文里的同一个值>
```

**逐条钉死（⚠️ 这几条每一条都会让"双方各自写对了却验不通"）：**

1. ⭐ **`sha256` 盖的是"规范化之后的字节"**，而规范化的口径就是上面那三条
   （`ensure_ascii=False` + `sort_keys=True` + `separators=(",", ":")`）——**缺一不可**。
   ⇒ 你**复算**的正确姿势是：**解析收到的 JSON → 去掉 `sign` → 用同一套规范化重新序列化
   → `sha256(...).hexdigest()`**。⛔ **不要**直接对"收到的原始字节里截掉 sign 那段"算摘要
   （你截不准，而且键序 / 空白 / 转义都会影响字节）。
2. ⭐ **待签串是三步、用 `\n` 连接**（`timestamp` → `delivery_id` → `sha256` 的小写 hex），
   ⛔ **顺序不能换**、⛔ **末尾不额外加 `\n`**。`timestamp` 用**十进制整数的规范写法**
   （`1760000000`，⛔ 无前导零、⛔ 不带小数、⛔ 不是毫秒）。
3. ⭐ **HMAC 的密钥是 `app_secret` 的 UTF-8 字节**（⛔ 不是 `app_key`），
   签名 hex **小写**。
4. ⭐ **`sign` 自己不在被签的内容里**：算的时候把它去掉，比的时候用 `hmac.compare_digest`
   这类**常量时间**比较（⛔ 别用 `==` 拼字符串比较）。
5. ⚠️ **`sha256` 只是把变长报文折成定长**，⛔ 它**不是**"防篡改"（防篡改由外层 HMAC 负责）。
6. ⚠️ 请按**收到的原始 `body` 字节**解析 JSON 后再复算，⛔ 不要"先改成自己的结构体再
   序列化回去"（多一个键、少一个键、换个键序都验不过）。

**验证一条回调的标准步骤**（Python 的可跑实现在 §9.2 的 `verify_callback()`）：

1. 逐个校验三个头都在（缺任何一个 ⇒ 记一条日志并回 4xx，见 §5.4）；
2. 解析报文，取 `delivery_id` / `timestamp` / `sign`；
3. 按上面那三条规范化 + 算待签串 + HMAC，与报文里的 `sign` 做**常量时间比较**；
4. ⭐ **按 `delivery_id` 去重**（§5.5）——**这一步在验签之后、处理业务之前**；
5. 处理业务（幂等！你的处理也要能被重放），然后回 **2xx**。

⚠️ **时间窗（可选）**：本契约**不强制**你校验 `timestamp` 的新鲜度
（我们不承诺一个固定的窗口，重投可能发生在 `occurred_at` 之后很久）。
如果你要防重放，可以用"收到的 `timestamp` 与你的本地时钟差超过某个阈值就拒"，
但请把阈值放宽到**至少几小时**（重投最多跨约 7.5 小时，见 §5.4），
并且**在那之前先按 `delivery_id` 去重** —— 否则你会把一次正常的重投判成攻击。

### 5.4 期望回执与重试退避

- ⭐ **只有 HTTP 2xx 算成功**（3xx / 4xx / 5xx / 超时 / 连不上**全部算失败**）。
  ⚠️ 我方**不跟随重定向**（3xx 一律当失败，⛔ 不会跟着跳到别处）。
- ⚠️ 一次投递的**超时是 10 秒**；我方**只读少量响应体**（最多 2048 字节，读完即弃）。
  ⇒ 请在 10 秒内**尽快**回 2xx（正确的做法是：验签 + 落一条待处理记录 + 立刻回 2xx，
  真正的业务处理放到你自己的队列里）。
- ⭐ **重试退避 10s / 60s / 5m / 15m / 1h / 6h，共 6 次机会**：

| 第几次投递 | 什么时候 |
|---|---|
| 第 1 次（首发） | 事件入队后**立即** |
| 第 2 次 | 第 1 次失败后 **10 秒** |
| 第 3 次 | **60 秒** |
| 第 4 次 | **5 分钟** |
| 第 5 次 | **15 分钟** |
| 第 6 次 | **1 小时** |
| 第 7 次 | **6 小时** |

⇒ **首发 + 6 次重投 = 一次事件最多 7 次 HTTP 尝试**（跨度约 7.5 小时）。
⭐ **六档全部可达**：第 1–6 次失败各取一档（含最后那档 `6h`），**第 7 次仍然失败**才落终态
`failed`（⚠️ 台账里那行会**保留**，租户可以在页面上看到原因并**手工重投**，§1.2）。
- ⚠️ **回执码会被记下来**（`response_status`）：请回一个**有意义的** 2xx（200 / 204 都行），
  ⛔ 不要回 200 之后再在响应体里写错误（我方**不看响应体**判成败，只看状态码）。
- ⚠️ **回调地址不合法（非 https / 解析到内网）时也走退避重试**（不是立刻放弃）：
  地址是**你自己**的域名，DNS 是可变的，"这次解析到内网"不等于"永远是内网"。
  ⇒ 一个**永久**不合法的地址会试满 7 次（约 7.5 小时）才落终态 `failed`。
- ⚠️ **中途关掉推送**：应用被停用 / `callback_state` 关掉 / 地址被清空 ⇒ 之后**不再产生**
  新推送；**已经在队列里**的那些行会落终态 `failed` + 一句人话（⛔ 不是静默丢弃，也⛔ 不是
  一直重试到把别的应用饿死）。

### 5.5 ⭐「至少一次」⇒ 请按 `delivery_id` 去重

⭐ **我们的投递语义是"至少一次"（at-least-once）**，⛔ 不是"恰好一次"。具体地说：

- 你**超时没在 10 秒内回**、但**实际上已经收到了**并处理了 ⇒ 我方按失败重投
  ⇒ **你会收到第二次**；
- 我方在落终态那一刻崩了、或你回了 5xx 但其实处理成功了 ⇒ 同样会重投；
- ⇒ ⭐ **请按 `delivery_id` 去重**：同一颗 `delivery_id` 处理**恰好一次**
  （落一张"已处理的 `delivery_id`"表，或在你自己的业务键上加唯一约束）。
  ⚠️ `delivery_id` 在**同一条推送的每一次重投里都不变**（§5.2）—— 那正是给你去重用的；
  ⛔ 别按 `timestamp` 去重（重投会变）、⛔ 也别按 `order_no` + `status` 去重
  （"状态回到同一个值"是合法业务事件，那样会把真事件吃掉）。
- ⚠️ **两个方向都要防**：① 同一条重投 ⇒ 按 `delivery_id` 去重（上面那条）；
  ② 不同的 `delivery_id` 带**相同的业务内容** ⇒ 那是**两次真实事件**，⛔ 不要合并。
- ⚠️ 我方的**手工重投**（§1.2）**只对 `failed` 的行开放**：已成功的行不允许重投
  （那会让你收到两次）。但**退避重试**是自动的 ⇒ "至少一次"仍然成立。

### 5.6 `images` 里给的是预签名 URL（有效期 1–2 小时）

`order.image_added` 的报文里，`images` 是一个列表，每项**恰好三个键**：

```json
{"url": "https://<对象存储域名>/…?X-Amz-…", "img_type": 0, "remark": ""}
```

- ⭐ **`url` 是投递那一刻现场生成的预签名直链，有效期 1–2 小时**
  （生产对象存储按整点对齐；本机/测试环境 300 秒）。
  ⇒ 请在**拿到报文后尽快**把图**下载到你自己那边**再慢慢处理；
  ⛔ **不要**把它当永久链接存进数据库（过期就 403 失效），⛔ 也不要转发给终端用户长期使用。
- ⚠️ **重投会带着一张新的 `url`**（重新预签，所以每次都可能不同）——
  这也是"⛔ 别按 url 去重"的原因：去重请用 `delivery_id`（§5.5）。
- `img_type` 本批恒为 `0`（订单进度图；`1` = 进群二维码**不会**推给你，§4.7）。
- `remark` 是上传时填的备注（可能为空串）。

### 5.7 回调地址的要求（仅 https、必须公网）

- ⛔ **只允许 `https`**：`http://` / `ftp://` 等一律在保存时被拒；
- ⛔ **地址里不许带用户名 / 密码**（`https://user:pass@host/…`）；
- ⛔ **域名必须解析得出来**，且**解析到的每一个地址都必须是公网地址**
  （回环 `127.0.0.0/8`、私网 `10/172.16/192.168`、链路本地 `169.254.0.0/16`、
  CGNAT `100.64/10`、保留段 / 组播 / 未指定一律拒）。
  ⚠️ 这条判据**每次投递前都会重跑一遍**（DNS 是可变的）⇒ 域名被指向内网时推送会**失败并重试**，
  而不是"照发"。这也是"内网自建回调本批不支持"的落地方式。
- ⛔ **不跟随重定向**、**10 秒超时**：你的回调地址应当是**直连**的、**快速**回 2xx 的端点。
- ⚠️ 我方一次投递**只读最多 2048 字节**响应体（读完即弃）⇒ ⛔ 别指望把大量数据放在回执里
  传给我们（要传数据请用你自己的查询接口 / 我方 §2.1 的读端点）。

## 6. 响应格式与错误码

### 6.1 业务失败也是 HTTP 200 —— 判据是 `code`

**除取令牌端点（§1.1）之外**，所有响应都是同一个信封：

```json
{"code": 0, "msg": "", "data": {...}}
```

⭐ **`code` 才是判据，⛔ 不是 HTTP 状态码**：业务失败（参数缺失、资源不存在）也回 **HTTP 200**，
`code` 非 0。**传输 / 认证层失败**（401 / 403 / 429）才保留 HTTP 状态码，且 `code` 取同一数值。

⇒ 你的代码必须写成"**先看 `code`，再看 `data`**"，⛔ 不要写成"200 就是成功"。
⚠️ 只有**取令牌端点**是例外：它按 OAuth2 标准回**裸体**（成功是三键、失败是两键，
⛔ 没有 `code` / `msg` / `data`）—— 见 §1.1。

### 6.2 对外承诺的错误码

| `code` | HTTP | `msg`（逐字，除非注明） | 什么情况 |
|---|---|---|---|
| `0` | 200 | `""` | 成功。`data` 见 §3 |
| `1000` | 200 | （随情况，例如 `缺少参数：source_order_no` / `缺少幂等键` / `请求里有本 API 不接受的字段：…` / `缺少必填参数：total_price`） | **参数问题**：缺参数、值超长、缺 `Idempotency-Key` / 键长不合规、**表外字段**（§2.5）、入参非法（金额 / 枚举值 / `game_id` / `img_type=1` / `key` 找不到）、应用管理端点的入参非法 |
| `1001` | 200 | `同一个幂等键的请求正在处理中` | **幂等冲突**：同一个 `Idempotency-Key` 的上一笔还在处理中（§2.3）⇒ 用同一个键重试 |
| `1002` | 200 | `记录不存在或已被删除` | **查不到**（不存在 / 已软删 / 不是本租户，三者同形，§7.2）；写端点上也用它表示"这条状态流转不允许" |
| `1014` | 200 | `该单的接单人绩效已结账，不能改发单价；请先撤销结账再改` | 该单的打手工资**已结账** ⇒ 一律拒绝改发单价（§4.5） |
| `1022` | 200 | （带单号的那句：「单已建好（单号 …），指派没成功：…」） | **单已建好、指派没成**（录单，§4.4）：`data = {"order_no", "reason", "assign_code"}`，⚠️ **单是存在的** |
| `1023` | 200 | （带单号的那句：「单已建好（单号 …），抛入内部抢单大厅没成功：…」） | **单已建好、抛内部抢单没成**（录单，§4.4）：`data = {"order_no", "reason"}`，⚠️ **单是存在的** |
| `1024` | 200 | `接单排行榜尚未开放` | ⛔ **本批不实现**的端点（`GET /api/open/v1/ranks/`，§4.3）：路径保留、**说破**它还没开（⛔ 不是"查不到"，也不是"你参数写错了"） |
| `401` | **401** | `应用凭据无效` | **Bearer 令牌那一侧**：没带 `Authorization` / 拼法不对 / 令牌不对 / 应用不存在 / **应用已停用**（**有意同一句话**，不给你应用枚举面） |
| `401` | **401** | `令牌已过期` | 令牌的 `exp` 已到（有效期 7200 秒，过期就重新换，§1.1） |
| `401` | **401** | `来源 IP 不在白名单内` | 应用配了 IP 白名单且你的来源 IP 不在里面（§7.6） |
| `401` | **401** | `{"error": "invalid_client", "error_description": "应用凭据无效"}` | ⚠️ **取令牌端点**那一档（**裸两键、不是信封**）：凭据错 / 应用不存在 / 已停用（三档逐字同句，§1.1） |
| `401` | **401** | `{"error": "unsupported_grant_type", "error_description": "仅支持 client_credentials"}` | ⚠️ 取令牌端点：`grant_type` 不是 `client_credentials`（§1.1） |
| `403` | **403** | （两处）⭐ `该应用无权访问本端点`（**锁定应用**越权，§1.4 / §7.2）；或"对象名不属于当前租户"（§4.7） | **凭据对、但这次操作不归你**：① **锁定应用**（§1.4）打了它白名单外的对外端点 ⇒ `msg` **逐字** `该应用无权访问本端点`；② 进度图**认领**时对象名不属于当前租户（§4.7）。⚠️ 这是**拒绝**（业务上"这次不许"），⛔ 别跟 **401** 混（401 = 凭据本身有问题） |
| `429` | **429** | `请求已被限流。 预计 <N> 秒后可用。`（⛔ 不是本平台写的文案：它由框架出厂渲染，`<N>` 随剩余窗口变） | **业务端点**的兜底闸超限（默认 6000 次/分钟/应用，§7.5）；带 `Retry-After` 头 |
| `429` | **429** | `{"error": "temporarily_unavailable", "error_description": "请求过于频繁，请稍后再试"}` | ⚠️ **取令牌端点**的限流（裸两键）：兜底额度超限，或**按来源 IP 的失败闸**已超限（§1.1 / §7.5） |

⚠️ **401 的四句话就是上面那四句**（逐字，⛔ 不要按英文习惯去猜措辞）；
⚠️ **取令牌端点**那两档是**裸 OAuth2 体**（⛔ 不是信封，见 §1.1）。
⚠️ **"应用凭据无效"这一句覆盖五种原因**（没带 / 拼错 / 令牌假 / 应用没了 / 应用停用）是**有意的**：
否则就能用响应差异**枚举出哪些应用存在** —— 排障时请⛔ 不要指望从 `msg` 里分出来。
⚠️ `msg` 里**不会**出现框架原文、异常堆栈、密钥。

> ⚠️⭐ **改准（2026-10-09，企微群码线；上面那一句原文保留）**：那一句的**本意**是"我们不会把
> 异常堆栈 / 库错的英文原文 / 密钥漏出去"，**不是**"每一个字都由我们手写"。⚠️ **至少有两处**
> 是**框架**渲染、而且**照实**出现在 `msg` 里的（⛔ 这里不声称这是一个穷尽列表）：
> ① **限流那一句**（见本表 `429` 行）；② **类型 / 格式不合法**那一类字段校验文案
> （例如取票传 `img_type: "abc"` ⇒ `请填写合法的整数值。`，逐格见 §4.7 的分叉表）。
> ⇒ 判据请打在 **`code`** 与那几句**写进契约的业务文案**上，⛔ 别假设 `msg` 一定是人写的中文。

## 7. 必须知道的禁令与边界

### 7.1 ⛔ 浏览器端直连不支持

本 API **没有 CORS 响应头**（专门没做，因为要新增运行时依赖）⇒ **必须在服务端调**。
在浏览器里 `fetch` 会因为没有 `Access-Control-Allow-Origin` 而失败。
⚠️ 就算将来开了 CORS，把 `AppSecret` 放进浏览器也等于**公开密钥**（谁都能读 JS）⇒ 那条路不可行。

### 7.2 ⭐「查不到」与「不是你的单」回**同一句话**（有意）

不存在 / 已软删 / 不是本租户的单，三种情况都回 `code=1002` +
`msg="记录不存在或已被删除"`。**这是有意的**：否则就能用这个 API **枚举**出"哪些订单存在"
（存在与不存在的差别本身就是信息）。⇒ 你**分辨不出**这几种情况，排障时⛔ 不要往
"是不是权限问题"上死磕（今天**没有**权限范围这回事，§0.1）——先核对单号本身、
以及"是不是你这个应用所在的租户"。

> ⛔⭐ **改准（2026-10-09，企微群码线；上面那句「今天**没有**权限范围这回事」原文保留）**：
> 那句话**不再成立** —— 本版多了一类**锁定应用**（§1.4），它是**有**权限范围的：
>
> - **哪一类凭据**：`kind=wecom_group_qr` 的那一把（每租户唯一，§1.4）。⚠️ **通用应用不受
>   影响**：它们**仍然没有**任何权限范围（一个通用应用凭据 = 本租户全部业务数据）；
> - **它放行哪些端点**（**恰好六条**，判据是「**HTTP 方法 + 端点**」两个一起，
>   ⛔ 不是只看路径）：
>   ① `GET /api/open/v1/orders/`（含 §4.2.1 的按时间增量拉单）、
>   ② `GET /api/open/v1/orders/<order_no>/`、
>   ③ `GET /api/open/v1/orders/<order_no>/status/`、
>   ④ `GET /api/open/v1/orders/<order_no>/images/`、
>   ⑤ `POST /api/open/v1/orders/<order_no>/images/`（认领）、
>   ⑥ `POST /api/open/v1/orders/<order_no>/images/ticket/`（取票）。
>   ⚠️ **同一条路径上的第二个方法不等于放行**：`POST /api/open/v1/orders/`（录单）、
>   `PATCH /api/open/v1/orders/<order_no>/`（改单）、`POST /api/open/v1/orders/<order_no>/status/`
>   （改状态）**都在拒的那一侧**。⚠️ 一条**新加**的对外端点**默认也是拒的**（fail-closed）。
> - **形状（逐字）**：**HTTP 403** + `code=403` + `msg` = `该应用无权访问本端点`，
>   `data` 为 `null`。⛔ 拿它当 401 排查会走错方向：**401 = 你的密钥 / 令牌有问题**，
>   **403 = 凭据是对的、只是这次操作不归它**；
> - ⚠️ 这一档与上面那个 `1002` 是**两件事**，⛔ 别混：`1002` 说"这张单不在你这家租户"
>   （或"这条状态流转不允许"），`403` 说"**你这个应用没资格打这个端点**"。

### 7.3 ⛔ 轮换密钥 = 瞬间断电

租户调 `POST /api/open/apps/<pk>/rotate-secret/` 之后**旧密钥立即失效、没有宽限期、
也不会有通知**（平台没有主动外呼能力）⇒ 你正在跑的集成会**当场 401**（§1.1 第 2 条：
该应用**已经发出去的令牌也一起失效**）。
⚠️ 换密钥要靠**人工**协调：租户在页面上看到新密钥后手工告诉你。
⚠️ 密钥**永不过期**（平台不设 `expires_at`）⇒ 泄露不会自愈，只能靠人工轮换。

### 7.4 ⭐ **`app_secret` 是明文、随时可取**

- 应用管理页的列表里**每一行都显示明文密钥**，并带一个**复制**动作；
- 后端**所有**取应用的响应都带它（列表 / 创建 / `PATCH` / 轮换，§1.2）；
- ⭐ 业务方 2026-10-07 的原话是「**密钥改成明文展示 可以随时获取 不要加那个只能看一次
  的限制**」⇒ ⛔ **不存在"只显示这一次"这回事**：真丢了回后台再抄一次就行，
  ⛔ **不必**为了"没抄到"去轮换（轮换是"瞬间断电"，§7.3）。

⭐ **AppSecret 是明文、租户随时可以取到** —— 请把 `app_secret` 当**凭据**对待：
⛔ 不要贴进聊天群 / 工单 / 截图；发现外泄就**立刻轮换**。

⚠️ **代价（如实登记，⛔ 不只写好处）**：能打开这个页面的账号管理员**都能读到全部应用的密钥**，
而且密钥会进入**响应体** ⇒ 可能落到浏览器历史 / 截图 / 反代访问日志 / 前端调试面板里。

⛔ **平台侧没有放松的那一条**：密钥**不进**平台的日志 / 操作留痕 / 错误消息
（由 `src/tests/test_openapi_app_api.py::AppSecretNeverLoggedTests` 逐条钉住）。

### 7.5 ⚠️ 限流是"兜底"，⛔ 不是配额

平台**不设每应用配额**（业务方要测服务器上限）。只有两道**极宽的兜底闸**：

1. **业务端点**：默认 **6000 次 / 分钟 / 应用**——正常业务**永远碰不到**，它只挡失控
   （死循环、脚本跑飞）。超限 ⇒ **HTTP 429** + `code=429` + `Retry-After: <秒>`。
2. **取令牌端点**：**每来源 IP 每 60 秒 600 次，含成功与失败**；超限 ⇒ **HTTP 429** +
   裸 OAuth2 体（§1.1）。

⛔ 别把它们读成"有额度这回事"：没有套餐分级、没有提额流程。

⚠️ 另有一条**按来源 IP 的失败计数**（**60 秒窗口内失败 20 次**后，那 60 秒内**连正确的请求**
也会被拒）：它挡的是"穷举 `client_secret` / 猜 `AppKey`"。**Bearer 那条路与取令牌端点
共用同一行计数**。⇒ ⭐ **凭据写错别硬重试**：先按 §8 排查，否则你会把自己挡在门外最多一分钟
（第 21 次起回 **429**，⛔ 不是 401）。

⚠️ **所以真正的第一道防线是密钥管理 + 人工停用应用**（秒级生效、立刻 401，§7.6）。
请自己也做好用量监控。

### 7.6 ⚠️ 其它如实登记的边界

- **停用是唯一的关闭动作**：应用**只能停用不能删**（没有 `DELETE` 端点，已认证且有节点的
  调用方得到 **405**）。停用后**所有**调用立刻 `401` + `应用凭据无效`（秒级生效，不缓存）。
- **IP 白名单**：默认**不启用**（空 = 不限制）。租户可以配（每行 / 逗号一个 IP 或网段）；
  配了之后来源 IP 不在名单内 ⇒ `401` + `来源 IP 不在白名单内`。
  ⚠️ 平台侧的取值口径是"优先 `X-Real-IP`、其次 `X-Forwarded-For` 的**最右段**"，
  前提是**只有一台可信反代**；将来加 CDN 会重新评估。
- **重放**：⛔ 本版**没有** nonce / 请求级防重放 —— 令牌有效期内（最长 7200 秒）
  同一个请求可以被重放。只读接口无害；**写接口靠 `Idempotency-Key` 兜**
  （同一个键重发 ⇒ 回放，⛔ 不会执行两次业务）。
- **一个应用 = 一本密钥 + 一个租户域名**：对接 N 家工作室就是 N 套（§1.3）。
- ⚠️ **计费 / 流量**：本平台**不按调用量计费**，也⛔ 不承诺任何 SLA 数字（没有对外承诺过
  可用性指标）⇒ 请你自己的集成做好超时与重试（尤其是**写端点的幂等键**）。

## 8. 给 AI 的排查顺序

> 这份文档的读者首先是 AI ⇒ 下面是**按顺序**排查的清单。⚠️ 每一条都对应一个真实会踩的坑，
> 请**按顺序**走，⛔ 不要跳着猜。

**⛔ 先记住三条底层事实**（它们能解释你看到的大部分现象）：

- 判据是响应体里的 **`code`**（HTTP 200 也可能是失败）——**唯一例外**是取令牌端点（§1.1）；
- 业务端点**只认** `Authorization: Bearer <令牌>`：⛔ 签名头那一族**已经不存在**了（§0.1）；
- 入参是**白名单 fail-closed**：表外的键不会"被忽略"，而是 `1000` **并点名**（§2.5）。

**按这个顺序查：**

1. ⭐ **换不到令牌**（`POST /api/open/oauth/token`）：
   - 拿到 `401` + `invalid_client` ⇒ 三档（密钥错 / 应用不存在 / 应用停用）**故意同一句**，
     ⛔ 别想从文案分辨：核对 `client_id` 是不是**这一家租户的** `AppKey`、
     `client_secret` 有没有多余空白、应用是不是被停用了（§1.1）。
   - 拿到 `401` + `unsupported_grant_type` ⇒ `grant_type` 写错 / 没传 / **体不是
     form-urlencoded**（发了 JSON 也会落到这一档，§1.1）。
   - 拿到 `429` + `temporarily_unavailable` ⇒ 别硬重试（§7.5，等窗口过去）。
   - ⚠️ 确认你打的是**这一家的域名**（拿 A 家密钥打 B 家域名 = 401，§1.3）。
   - ⚠️ **`expires_in` 是 7200 秒**、⛔ 没有 refresh：到点直接**重新换**（§1.1）。
2. ⭐ **`401`（业务端点）**：四句话**逐字**对应四种情况（§6.2）——
   `应用凭据无效`（没带 `Authorization` / 拼法不是 `Bearer <令牌>` / 令牌假 / 应用停用）、
   `令牌已过期`（重新换）、`来源 IP 不在白名单内`（找租户加白名单）。
   ⛔ **不要**再去找"签名怎么算"——入站签名今天不存在（§0.1）。
3. ⭐ **`1000`（参数问题）**：读 `msg`，它会**点名**。
   - `请求里有本 API 不接受的字段：…` ⇒ 你传了**表外**的键（含照**对标文档**写的
     `hours` / `gamePassword` / `customerId` / `gaemTf` 等）：删掉它们，或换成我们名字
     （§4.4 的对标差异表）。
   - `缺少幂等键` / `幂等键长度必须是 8–128 个字符` ⇒ 写端点必带 `Idempotency-Key`（§2.2）。
   - `缺少必填参数：…` ⇒ 录单缺 `total_price` / `source_order_no`（§4.4）。
   - `缺少参数：source_order_no` / `缺少参数：game_id` ⇒ query 少了必填项（§4.2 / §4.3）。
   - 其它（金额形状、非法枚举值、`img_type=1`、`game` 不是本租户的）⇒ 见对应小节的表。
4. **`1001`**：同一个 `Idempotency-Key` 的**上一笔还在处理中**。
   ⇒ 用**同一个键**稍后重试（⛔ **不要换一个新键**：换键就等于再执行一次业务）。若你**每次都拿到
   `1001`**，检查是不是把同一个键并发打出去了（§2.3）。
5. **`1003`？—— 本对外面⛔ 不会出现这个码**：`1003` 是平台**账号线**的码
   （"最后一个管理员不能删"这类内部动作），⛔ 与开放平台任何端点无关。
   ⚠️ 你若在开放平台看到 `1003`，那说明你看的不是本契约的响应（例如打到了别的站 / 页面接口）。
6. **`1002`**：查不到，或状态流转不允许（§6.2）。
   - 查单 ⇒ 核对**单号是不是本租户的**（⛔ 不要拿**来源单号**当订单号用：那是两个键、
     两个端点，§4.1 / §4.2）。
   - 改状态 ⇒ 这条边**状态机不允许**（页面上不允许的边，这里也不允许）。
   - ⚠️ 软删的单也算"查不到"（与"不存在"同形，§7.2）。
7. **`1014`**：该单的打手工资**已结账** ⇒ 改发单价一律被拒。要改必须先**撤销结账**（§4.5）。
8. **`1022`**：录单时**单已建好、指派没成**。⭐ **订单是存在的**（`data.order_no` 就是它）
   ⇒ ⛔ **不要再录一次**（同键 / 同来源单号重发会回放这一份失败，§2.3）；
   用 `data.assign_code` / `data.reason` 去看"为什么没指派成"。
9. **`1023`**：同上，只是"抛进内部抢单大厅"这一步没成（`data = {"order_no", "reason"}`）。
10. **`1024`**：`GET /api/open/v1/ranks/` —— **接单排行榜本批不实现**（§4.3）。
    ⛔ 别拿 `1002` / `1000` 去理解它：这一档说的是"**有这个接口、只是还没开**"。
11. **`429`**：限流（§7.5）。读 `Retry-After` 等到点再试；⚠️ 别硬重试
    （尤其**凭据类的 429**：那是按来源 IP 的失败闸，硬重试只会把自己挡得更久）。
12. ⭐ **回调签名对不上**（我们在推给你，你验不过）：
    - 你算的待签串是不是**三步**：`timestamp` → `delivery_id` → `sha256(规范化报文)`
      （⛔ 顺序不能换、⛔ 末尾不加 `\n`，§5.3）？
    - 规范化是不是**三条全对**：`ensure_ascii=False` + `sort_keys=True` +
      `separators=(",", ":")`（少一条，摘要是另一个值，§5.3）？
    - 你是不是**先解析 JSON、去掉 `sign`、再重新规范化**（⛔ 不是对原始字节截字符串）？
    - 密钥是不是 `app_secret`（⛔ 不是 `app_key`）？hex 是不是**小写**？
    - **拿 §9.1 的合成夹具自检**：用你手上的代码（密钥换成示例里那把合成密钥）算一遍 ——
      必须得到 `b44b31b4a46978079edf28e78ba06f2e30fa7fad6d02d560c059befdf910286f`。
      算不出这个值 ⇒ **问题在你的验签代码里，与我们无关**，先修到能算出为止。
    - 还有问题 ⇒ 检查你是不是**拿旧密钥**在验（租户**轮换过密钥** ⇒ 用新密钥重算，
      §7.3；⚠️ 轮换之后**新推的报文才用新密钥签**，老报文仍是老密钥）。
13. ⚠️ 分辨"我这边的问题"与"对方的问题"：**拿 §9.2 的 `call_api()` 打一次 §2.1 的读端点**
    （最省事的一条是 `GET /api/open/v1/games/`）：它通了说明认证与网络都没问题，
    再把问题收敛到具体的写端点 / 参数上。

```python
⚠️ 三个联网函数都带一个 `opener` 形参（默认走真实网络）：
那是给**离线自检与测试**留的接缝 —— 注入一个桩就能在不联网的情况下驱动整条流程。
直接运行本文件时**不联网**，只打印 §9.1 那个期望签名。
"""
import hashlib
import hmac
import json
import urllib.error
import urllib.parse
import urllib.request


class OAuth2Error(RuntimeError):
    """换令牌失败：`error` / `error_description` 就是我们回给你的那两个键（§1.1）。"""

    def __init__(self, error, error_description):
        super().__init__(f"{error}: {error_description}")
        self.error = error
        self.error_description = error_description


def _open(request, *, opener=None):
    """发一个请求：默认走真实网络；`opener` 不为空时交给它（离线自检 / 测试注入的**桩**）。"""
    if opener is None:
        return urllib.request.urlopen(request)
    return opener(request)


def fetch_token(base_url, client_id, client_secret, *, opener=None):
    """① 换令牌：`POST /api/open/oauth/token`（form-urlencoded）。

    成功回**裸三键** `{"access_token", "token_type", "expires_in"}`；
    失败是**裸两键** `{"error", "error_description"}`（⛔ 不是本仓的 code/msg/data 信封）。
    ⚠️ 令牌有效期到点即失效、⛔ 没有 refresh ⇒ 到点就再调一次本函数。
    """
    form = urllib.parse.urlencode(
        {
            "grant_type": "client_credentials",
            "client_id": client_id,
            "client_secret": client_secret,
        }
    ).encode("utf-8")
    request = urllib.request.Request(
        base_url + "/api/open/oauth/token",          # ⚠️ 这条路径**没有**末尾斜杠
        data=form,
        method="POST",
        headers={"Content-Type": "application/x-www-form-urlencoded"},
    )
    try:
        with _open(request, opener=opener) as response:
            return json.loads(response.read().decode("utf-8"))
    except urllib.error.HTTPError as exc:
        # 401 / 429 都是裸 OAuth2 体；⛔ 不要在这里去看 code/msg（那两个键根本不存在）。
        payload = json.loads(exc.read().decode("utf-8"))
        raise OAuth2Error(payload["error"], payload["error_description"]) from exc


def call_api(base_url, access_token, path, *, method="GET", body=None,
             idempotency_key=None, opener=None):
    """② 调业务端点：带 `Authorization: Bearer <令牌>`；**写端点**还要带 `Idempotency-Key`。

    ⚠️ 判据是响应体里的 `code`（⛔ 不是 HTTP 状态码）：业务失败也是 HTTP 200。
    """
    data = None if body is None else json.dumps(body, ensure_ascii=False).encode("utf-8")
    headers = {"Authorization": "Bearer " + access_token}
    if data is not None:
        headers["Content-Type"] = "application/json"
    if idempotency_key is not None:
        headers["Idempotency-Key"] = idempotency_key
    request = urllib.request.Request(
        base_url + path, data=data, method=method, headers=headers
    )
    with _open(request, opener=opener) as response:
        envelope = json.loads(response.read().decode("utf-8"))
    if envelope["code"] != 0:
        raise RuntimeError(f'{envelope["code"]}: {envelope["msg"]}')
    return envelope["data"]


def canonical_json(value):
    """报文的**规范化** UTF-8 字节（唯一口径：三条缺一不可）。"""
    return json.dumps(
        value, ensure_ascii=False, sort_keys=True, separators=(",", ":")
    ).encode("utf-8")


def compute_signature(secret, timestamp, delivery_id, body_without_sign):
    """`sign = HMAC-SHA256(secret, f"{timestamp}\\n{delivery_id}\\n{sha256(报文)}")` 的 hex。"""
    digest = hashlib.sha256(canonical_json(body_without_sign)).hexdigest()
    message = f"{timestamp}\n{delivery_id}\n{digest}".encode("utf-8")
    return hmac.new(secret.encode("utf-8"), message, hashlib.sha256).hexdigest()


def verify_callback(secret, headers, raw_body):
    """③ 验证一条回调：`headers` 是收到的那三个头，`raw_body` 是请求体 bytes。

    ⚠️ 顺序：**先验签，再按 `delivery_id` 去重，最后处理业务**（§5.5）。
    """
    body = json.loads(raw_body.decode("utf-8"))
    received = body.pop("sign", "")          # ⛔ 签名不覆盖 sign 自己
    expected = compute_signature(
        secret,
        headers["X-TT-Timestamp"],
        headers["X-TT-Delivery"],
        body,
    )
    return hmac.compare_digest(expected, received)
```

```php
<?php
// 团团通开放平台：验证回调签名（PHP 8+）。⚠️ 本段未在本仓跑过（本机无 PHP 解释器）。
function canonical_json($value): string {
    // 与 Python 的 json.dumps(ensure_ascii=False, sort_keys=True, separators=(",", ":")) 对齐：
    // JSON_UNESCAPED_SLASHES|JSON_UNESCAPED_UNICODE 对应 ensure_ascii=False，
    // 而 PHP 的 json_encode 本来就不加空白；键序要自己递归排（见 tt_sort）。
    return json_encode(tt_sort($value), JSON_UNESCAPED_SLASHES | JSON_UNESCAPED_UNICODE);
}

function tt_sort($value) {
    if (is_array($value)) {
        $isList = array_keys($value) === range(0, count($value) - 1);
        $out = [];
        if ($isList) {
            foreach ($value as $item) { $out[] = tt_sort($item); }
            return $out;
        }
        $keys = array_keys($value);
        sort($keys, SORT_STRING);            // ⚠️ 契约是"按键升序"，与 Python 的 sort_keys 同义
        foreach ($keys as $key) { $out[$key] = tt_sort($value[$key]); }
        return $out;
    }
    return $value;
}

function compute_signature(string $secret, $timestamp, string $deliveryId, array $bodyWithoutSign): string {
    $digest  = hash('sha256', canonical_json($bodyWithoutSign));      // 小写 hex
    $message = $timestamp . "\n" . $deliveryId . "\n" . $digest;      // ⚠️ 顺序不能换
    return hash_hmac('sha256', $message, $secret);                    // 小写 hex
}

function verify_callback(string $secret, array $headers, string $rawBody): bool {
    $body    = json_decode($rawBody, true);
    $inBody  = $body['sign'] ?? '';
    $inHeader = $headers['X-TT-Signature'] ?? '';
    // ⚠️ 头里的 X-TT-Signature 与报文里的 sign 是**同一个值**（§5.3）：任一为空或两者
    // 不一致 ⇒ 直接拒（⛔ 别"取其中一个就行"：那样等于放过了被改过的那一半）。
    if ($inBody === '' || !hash_equals($inBody, $inHeader)) { return false; }
    unset($body['sign']);                       // ⛔ 签名不覆盖 sign 自己
    $expected = compute_signature($secret, $headers['X-TT-Timestamp'], $headers['X-TT-Delivery'], $body);
    return hash_equals($expected, $inBody);     // ⚠️ 常量时间比较，⛔ 不用 ==
}

$body = [
    'delivery_id' => '6f1c0f7c9a2e4f0b8a3d5c7e9f1a2b3c',
    'event' => 'order.status_changed',
    'note' => '',
    'occurred_at' => '2026-10-08T12:00:00+08:00',
    'order_no' => '20261008120000000042',
    'source_order_no' => 'AB-2026-0007',
    'status' => 'IN_PROGRESS',
    'timestamp' => 1760000000,
];
var_dump(compute_signature($secret, 1760000000, $body['delivery_id'], $body));
```

### 9.4 Node.js（`crypto`，可直接跑）

```javascript
// 团团通开放平台：验证回调签名（Node 18+，无第三方依赖）。
const crypto = require('crypto');

function sortValue(value) {
  if (Array.isArray(value)) return value.map(sortValue);
  if (value && typeof value === 'object') {
    const out = {};
    // ⚠️ 契约是"键升序"。JS 的 sort() 按 UTF-16 码元排、Python 的 sort_keys 按码点排
    // —— 报文里的键都是 ASCII（event/delivery_id/…），两者在这里等价；键名出现非 ASCII
    // 时请自己按码点排。⛔ 不要用 JSON.stringify 的默认键序（那是插入序）。
    for (const key of Object.keys(value).sort()) out[key] = sortValue(value[key]);
    return out;
  }
  return value;
}

function canonicalJson(value) {
  // 与 Python 的 json.dumps(ensure_ascii=False, sort_keys=True, separators=(",", ":")) 等价：
  // JSON.stringify 不加空白、也不转义非 ASCII（⛔ 别用带缩进的版本）。
  return JSON.stringify(sortValue(value));
}

function computeSignature(secret, timestamp, deliveryId, bodyWithoutSign) {
  const digest = crypto.createHash('sha256').update(canonicalJson(bodyWithoutSign), 'utf8').digest('hex');
  const message = `${timestamp}\n${deliveryId}\n${digest}`;   // ⚠️ 顺序不能换
  return crypto.createHmac('sha256', Buffer.from(secret, 'utf8'))
    .update(Buffer.from(message, 'utf8')).digest('hex');
}

function verifyCallback(secret, headers, rawBody) {
  const body = JSON.parse(rawBody.toString('utf8'));
  const received = body.sign || '';
  delete body.sign;                                   // ⛔ 签名不覆盖 sign 自己
  const expected = computeSignature(secret, headers['X-TT-Timestamp'], headers['X-TT-Delivery'], body);
  const a = Buffer.from(expected, 'utf8');
  const b = Buffer.from(received, 'utf8');
  return a.length === b.length && crypto.timingSafeEqual(a, b);   // ⚠️ 常量时间比较
}
```

### 9.5 三份代码的公共约定（照抄时别丢）

| 事项 | 正确写法 | 常见错法 |
|---|---|---|
| 换令牌的体 | `application/x-www-form-urlencoded` | 发 JSON（⇒ `unsupported_grant_type`） |
| 业务端点凭据 | `Authorization: Bearer <令牌>` | 想去找"签名怎么算"（入站签名已不存在，§0.1） |
| 写端点 | 必带 `Idempotency-Key`（8–128，随机串） | 不带（⇒ `1000`）/ 每次都换新键（⇒ 重复执行） |
| 成败判据 | 响应体里的 `code == 0` | "HTTP 200 就是成功" |
| 报文的规范化 | `ensure_ascii=False` + `sort_keys=True` + `separators=(",", ":")` | 用自己语言的默认序列化（键序 / 空白 / 转义任一不同就全验不过） |
| 待签串 | `timestamp` → `delivery_id` → `sha256` 的 hex，`\n` 连接 | 换顺序 / 末尾多一个 `\n` / 少一段 |
| HMAC 的密钥 | `app_secret` 的 UTF-8 字节 | 用 `app_key` |
| 签名 hex | 小写 | 大写（比不过，且我们**不做**宽容比较） |
| 比较 | `hmac.compare_digest` / `hash_equals` / `timingSafeEqual` | `==` / `===`（非常量时间） |
| 去重 | 按 `delivery_id`（同一条重投沿用同一颗） | 按 `timestamp` 或 `url` 去重（重投会变） |
