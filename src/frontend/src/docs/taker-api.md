## 0. 三十秒总览（先读这一段）

| 问题 | 答案 |
|---|---|
| 这是什么 | **抢单大厅**的对外接口：把厅里的单**镜像**到你自己的系统，并在你自己的系统里**抢单**、交单、传进度图 |
| 谁用 | **打手**（用别家系统的外部工作室）。在团团通里，这套凭据**绑定一个打手账号**（§1.2） |
| 认证方式 | ⭐ **`Authorization: Bearer <令牌>`**。令牌从取令牌端点换（§1.1）。⛔ 请求**不需要任何签名** |
| 换令牌 | `POST /api/taker/oauth/token`（form-urlencoded 的 `client_id` / `client_secret`）⇒ 裸三键 `access_token` / `token_type` / `expires_in`（§1.1） |

| 域名 | **每个租户（工作室）一个域名**，拿谁家的密钥就调谁家的域名（§1.3） |
| 失败长什么样 | ⚠️ **业务失败也是 HTTP 200**，判据是响应体里的 `code`（§8.1）。⚠️ **只有取令牌端点例外**：它回 OAuth2 标准体（§1.1） |
| 浏览器能直连吗 | ⛔ **不能**。没有 CORS，必须**服务端**调（§9） |
| 这把令牌能看多少 | ⭐ **只有它绑定的那个打手自己的东西**：他**游戏范围内**的厅单（§3）+ **他自己接手的单**（§5） |
| 判据在哪 | 本文档 + `src/tests/test_takerapi_doc_examples.py`（它跑本文档 §10 的示例代码并与期望值对拍，也会跑 §12.3 那段验签代码并与**实现**算出来的签名对拍） |

⛔⭐ **改准（2026-10-09，第二期）**：上表「我们推给你吗」那一行**原写**
「⛔ **不推**。**本侧没有任何主动回调推送**（第一版就没有）⇒ 你必须**轮询**（§0.1 第 1 条）」
（**原句在此保留**）—— **第二期加了回调推送**（§12）。⚠️ 两件事**没有放松**：
① **大厅里来了新单仍然不推**（「大厅必须轮询」这一半不变）；
② 推送是**至少一次**、延迟 ≈ 10 秒、**不在业务事务里**（§12.8）⇒ 轮询仍是有效的兜底。

**一句话**：拿 `AppKey` / `AppSecret` → 调 `POST /api/taker/oauth/token` 换 `access_token` →
带 `Authorization: Bearer <令牌>` 调 `{域名}/api/taker/v1/…` → 读响应体里的 `code`。

### 0.1 最容易踩的三件事（先看这三条）

1. ⛔⭐ **没有推送，必须轮询**。本侧**没有**任何"单被抢走了 / 你这张单状态变了"的主动通知
   —— 第一版**刻意不做**（理由与代价如实登记在 `docs/specs/2026-10-08-taker-open-api-design.md` §10-1）。
   ⇒ 大厅靠**你自己定时拉**（§3.5 的镜像对账法），「我的单」的状态变化靠定时调 `GET /api/taker/v1/my/orders/`（§5.3）。
   ⚠️ 你能拿到多新的数据 = **你自己的轮询间隔**，我们这边没有任何"延迟推送"这回事。
   ⛔⭐ **改准（2026-10-09，第二期）：上面这一条已经过期**（原句逐字保留）。第二期**加了回调推送**
   （§12）：**他当前接手的单**的状态变化 / 被删 / 新增进度图 / **不再是他的了**
   （`order.reassigned`）这四类会**主动推给你**（前提是那个应用配了回调地址且开关是开的）。
   ⚠️ 但**这不等于"可以不管轮询"**：⛔ **大厅里来了新单仍然不推**（大厅只能靠轮询，§3.5）；
   而且推送是**至少一次**、**延迟 ≈ 10 秒**、**不在业务事务里**（§12.8）
   ⇒ 想立刻看到、想兜底，都还得靠轮询（§12.5 那套去重也一样要做）。
2. ⛔⭐ **取令牌端点回的**不是**本仓信封**。其余每条端点都是 `{"code", "msg", "data"}`，
   而 `POST /api/taker/oauth/token` 按 OAuth2 标准回**裸三键 / 裸两键**（§1.1）。
   ⇒ 你的客户端必须**分两条解析路**，⛔ 别拿 `code` 去读它。
3. ⛔⭐ **抢单的应答只代表"那一刻"**。`POST …/claim/` 回的 `{order_no, status, status_text}` 不是
   一份"事实查询"：**同一个 `Idempotency-Key` 重发会回放上一次那一段响应**（§4.4）。
   ⇒ **事实以查单（§5.2）/ 我的单（§5.1）为准**，⛔ 不要拿抢单应答去做你的订单状态机。

## 1. 接入三步

### 1.1 第一步：换令牌（`POST /api/taker/oauth/token`）

| 项 | 值 |
|---|---|
| 方法 / 路径 | `POST /api/taker/oauth/token`（⚠️ 逐字，**⛔ 末尾没有斜杠**） |
| 请求头 | `Content-Type: application/x-www-form-urlencoded`（⛔ 不是 JSON） |
| 请求体（三个字段） | `grant_type=client_credentials`、`client_id=<AppKey>`、`client_secret=<AppSecret>` |
| 认证 | ⛔ **不需要**任何 `Authorization` 头（这个端点自己就是凭据入口） |

**成功（HTTP 200）**：响应体是**裸的三个键**（⛔ 不是本仓那个 `code` / `msg` / `data` 信封）：

```json
{"access_token": "<令牌>", "token_type": "Bearer", "expires_in": 7200}
```

| 键 | 说明 |
|---|---|
| `access_token` | 令牌本体。⚠️ 它是一个**不透明字符串**（形如 `base64url(payload).base64url(HMAC-SHA256(…))`）—— 按原样回传，⛔ 不要解析、不要改、不要拼格式 |
| `token_type` | 恒为 `Bearer`（放请求头时写 `Authorization: Bearer <令牌>`） |
| `expires_in` | 有效期**秒数**，恒为 **7200**（2 小时）。⚠️ 它是"从这一刻起还能用多久"，⛔ 不是绝对时刻 |

**失败（HTTP 401）**：响应体**恰好两个键**（⛔ 同样**没有** `code` / `msg` / `data`）：

```json
{"error": "invalid_client", "error_description": "应用凭据无效"}
```

| 情形 | HTTP | `error` | `error_description` |
|---|---|---|---|
| 密钥错 / 应用不存在 / 应用已停用 | **401** | `invalid_client` | `应用凭据无效`（⚠️ **三档逐字相同**，见下） |
| `grant_type` 不是 `client_credentials`（含没传、传空） | **401** | `unsupported_grant_type` | `仅支持 client_credentials` |
| 限流（见 §9.4） | **429** | `temporarily_unavailable` | `请求过于频繁，请稍后再试` |

- ⭐ **三档凭据失败共用同一句话是有意的**：否则就能用响应差异**枚举出哪些 `AppKey` 存在**
  （应用不存在与密钥错必须长得一样）。⇒ 排障时⛔ 不要指望从这句话里分出"是密钥错了"
  还是"这个应用没了"，请直接找租户核对 `AppKey` / `AppSecret`。
- ⭐ **校验顺序**：先判 `grant_type`，再判凭据。⇒ `grant_type` 写错时**不会**顺带告诉你
  凭据对不对（那一档不查库）。
- ⚠️ **体不是 form-urlencoded**（例如你发了 JSON 体）⇒ 字段被当成**缺失** ⇒ 你会拿到
  `401` + `unsupported_grant_type`。⛔ **不会**是 415 / 400，也⛔ **不是**本仓信封 ——
  这条端点的每一种答复都是 OAuth2 体。

**令牌的四条语义（逐条都是契约，⛔ 别照别的平台的习惯推断）：**

1. ⭐ **有效期到点即失效**：`expires_in` 一到，用它的请求一律 `401` + `令牌已过期`。
   ⇒ **没有"自动续期"**，到点就重新换一次（换令牌很便宜，成功了不写业务数据）。
2. ⭐ **轮换密钥 ⇒ 所有旧令牌立刻失效**：租户点一次「轮换密钥」（§1.2），
   该应用**已经发出去的每一颗令牌当场作废**（令牌的签名是用 `app_secret` 算的，
   换了密钥就验不过）⇒ 你正在跑的对接会**当场 401**。要靠**人工**协调换密钥的时机。
3. ⭐ **⛔ 没有 refresh token**：这个端点**只有** `client_credentials` 一种授权类型，
   ⛔ 没有 `refresh_token`、⛔ 没有 `grant_type=refresh_token`、⛔ 也没有续期接口。
   过期了就**重新换一颗**（拿同一对 `client_id` / `client_secret`）。
4. ⭐ **令牌不能单独吊销**：⛔ 没有一个"作废这一颗令牌"的端点。要立刻废掉一批令牌，
   只有两条路 —— 轮换密钥（废掉该应用**全部**令牌）或**停用应用**（§9.3）。
   ⚠️ 代价如实登记：**泄露一颗令牌 = 在它剩余有效期内拿着这个打手的全部能力**。

⚠️ **令牌里不带租户标识**：租户上下文只来自你请求的**域名**。⇒ 拿 A 家工作室的令牌
去打 B 家的域名，一律 `401` + `应用凭据无效`。要给 N 家工作室对接，就是 **N 套密钥 + N 个域名**。

⚠️ **令牌是凭据**：⛔ 别把它放进 URL / query（会进反代与浏览器历史）、⛔ 别写进前端代码、
⛔ 别贴进聊天群或工单；它应当只出现在**服务端发出**的 `Authorization` 头里。

**`client_id` / `client_secret` 从哪里来**：租户（工作室）在团团通后台的
「开放平台 → **打手对接**」页面上创建应用（§1.2）。**第三方开发者不调创建应用那一步**。

#### 换令牌的可跑示例

§10 的 Python 段里有一个 `fetch_token()`，可以直接复制使用（它把 401 / 429 的
`error` / `error_description` 翻成一个异常，⛔ 不会把裸体当成令牌）。

### 1.2 第二步：租户侧的准备（第三方⛔ 不调这些端点）

这一节的端点**调用方是租户自己**（工作室的人在网页上操作，或用**自己的登录会话**调这些
内部端点）：它们走**会话认证**（cookie + CSRF），⛔ **不认** Bearer 令牌，
而且要求操作人的账号有 `system.allow_taker_open_api`（打手本人）**或**
`system.pinduoduo_settings`（系统管理员）节点。

| 方法 | 路径 | 认证 | 说明 |
|---|---|---|---|
| `GET` | `/api/taker/apps/` | 会话 + 节点 | 列表（⭐ 每行含**明文 `app_secret`**，见 §9.5）。⚠️ 打手只看得到**自己的**那一行，管理员看全部 |
| `POST` | `/api/taker/apps/` | 会话 + 节点 | 创建：`{"name": "<应用名，≤50 字符，租户内唯一>"}`；⚠️ **打手建时不许带 `taker`**（锁死为他自己），**管理员建时必带** `{"taker": <账号 id>}` |
| `PATCH` | `/api/taker/apps/<pk>/` | 会话 + 节点 | 改单个字段：`{"state": "disabled"}` / `{"state": "enabled"}` / `{"name": "新名"}` / `{"ip_allowlist": "1.2.3.4\n10.0.0.0/8"}`；缺席 = 保持原值。⛔ **`taker` 不在这里**（改它 = 不换凭据就换掉整个权限面）⇒ 传了回 `1000` 并点名 |
| `POST` | `/api/taker/apps/<pk>/rotate-secret/` | 会话 + 节点 | 换密钥：响应含**新**密钥；**旧密钥当场失效、没有宽限期**（§9.3），该应用**全部已发出的令牌立刻失效**（§1.1） |
| ⛔ | **没有 `DELETE`** | —— | **只能停用不能删**（§9.3）：已认证且有节点的调用方对 `DELETE` 得到 **405** |

**应用行载荷的键（`GET` / `POST` / `PATCH` / 轮换四条共用一个装配出口）**：
`id` / `name` / `app_key` / ⭐ `app_secret`（明文）/ `taker` / `taker_name` / `state` /
`state_text` / `ip_allowlist` / `last_used_at` / `secret_rotated_at` / `created_at`。

- ⛔ **创建应用时**载荷里出现**表外**的键 ⇒ `1000` + **点名**那几个键 + 一行都不落库
  （与上家侧**不同**：上家侧那几个序列化器吃 DRF 的"忽略未知键"默认行为，本侧**不吃**）。
- ⛔ **不能把 `taker` 绑到租户管理员账号上**：管理员账号在权限体系里被短路成"全部游戏"，
  绑上它等于把整个大厅交出去 ⇒ 那种创建**被拒**（`1000` + 点名，一行不落库）。
- ⛔ **今天没有**任何"授权范围"要配：范围**从绑定的那个打手账号算**
  （他的游戏权限 + "他接手的单"），没有第二套授权存储、也⛔ 不存在"还要去勾权限 / 勾游戏范围"这一步。
  ⚠️ 代价：**那个账号的职位 / 权限节点一改，你这套凭据的能力就静默跟着变**（`docs/TAKER-API.md`
  是给第三方的，这条是给**租户自己**看的，页面上也写着）。

⚠️ **一个应用 = 一个打手账号**：一个工作室有 10 个打手，就是 10 套密钥（⛔ 一套密钥不能代表多个人）。

### 1.3 第三步：带令牌调业务端点

```
GET  https://<租户域名>/api/taker/v1/hall/                 （拉大厅；带筛选与分页）
GET  https://<租户域名>/api/taker/v1/my/orders/            （我的单；可带 updated_since）
POST https://<租户域名>/api/taker/v1/hall/<order_no>/claim/        （写：还要带 Idempotency-Key）
```

请求头（**读端点只要第一个**）：

```
Authorization: Bearer <令牌>
Idempotency-Key: <8–128 个字符的随机串>     ← ⚠️ 只有写端点需要，见 §2
```

- ⚠️ **路径末尾的斜杠不能少**（**除了** `/api/taker/oauth/token` 那一条**没有**斜杠）：
  漏了会先拿到 **301 重定向**；请按 §2 那张全表逐字照抄。
- ⚠️ **域名是"哪一个"**：本平台**一个租户一个域名**，密钥与域名是**绑定的一对**
  （拿 A 家的密钥打 B 家的域名 ⇒ **401**）。
- ⛔ **浏览器端直连不支持**（没有 CORS，§9.1）⇒ 必须服务端调。

## 2. 端点全表

对外前缀是 `/api/taker/v1/`（与平台自己的 `/api/business/`、上家侧的 `/api/open/v1/`
**并列**）。⚠️ 版本号写进路径：契约一旦发布**不能悄悄改**。
⚠️ 下面这张表就是**全部**对外端点（**恰好七条**）—— 一个不多一个不少。

| # | 方法 | 路径 | 作用 | `Idempotency-Key` |
|---|---|---|---|---|
| 1 | `GET` | `/api/taker/v1/hall/` | 拉可接单列表（§3） | —（读） |
| 2 | `POST` | `/api/taker/v1/hall/<order_no>/claim/` | **抢单**（§4） | **必带** |
| 3 | `GET` | `/api/taker/v1/my/orders/` | **我的单**列表（§5.1） | —（读） |
| 4 | `GET` | `/api/taker/v1/orders/<order_no>/` | 按单号**查一张单**（§5.2） | —（读） |
| 5 | `POST` | `/api/taker/v1/orders/<order_no>/status/` | **改状态**（交单 / 问题单 / 暂停，§6） | **必带** |
| 6 | `GET` | `/api/taker/v1/orders/<order_no>/images/` | 进度图**列表**（§7） | —（读） |
| 6 | `POST` | `/api/taker/v1/orders/<order_no>/images/ticket/` | 进度图**取票**（§7） | **必带** |
| 6 | `POST` | `/api/taker/v1/orders/<order_no>/images/` | 进度图**认领**（§7） | **必带** |
| 7 | `POST` | `/api/taker/v1/hall/upstream/<pk>/claim/` | **接镜像单**（§4.5） | **必带** |
| 8 | `POST` | `/api/taker/v1/hall/peer/<pk>/claim/` | **接团团通镜像单**（§4.6，2026-10-25 新增） | **必带** |

⚠️ 第 6 行是**三条**（同一族的三步）、第 7 行是**接镜像单**（2026-10-24 新增，D-0296）、
第 8 行是**接团团通镜像单**（2026-10-25 新增，D-0303），
所以"八条"说的是**八个编号行**；**路径**去重后是**九条**
（`images/` 那条路径上 `GET` 与 `POST` **同住一个视图类**，是两个方法、一条路径）。

**统一口径：**

- 认证一律 `Authorization: Bearer <令牌>`；⛔ 没有会话 cookie 这一路（浏览器直连也不行，§9.1）；
- ⚠️ **业务失败也是 HTTP 200**，判据是响应体里的 `code`（§8.1）；认证层的 401 / 429 保留 HTTP 状态码；
- 写端点**必带** `Idempotency-Key`：长度 **8–128 个字符**（含两端）；缺失 / 长度不合规 ⇒ `1000`
  （⛔ **不会**"默默放行"——放行就等于同一笔业务被执行两次）。
  ⚠️ 键值请用**随机串**（例如 UUID 去掉横线）；⛔ 别拿订单号 / 时间戳当键（那样重试时会变成新键）；
- 分页参数 `page` / `page_size`：默认 **1** / **20**，`page_size` **上限 100**（要 1000 就**夹到 100**，
  ⛔ 不是报错）；`?page=abc` / `?page=0` ⇒ `1000`（⛔ 不是 500）。
  `data` 里回的是**实际生效**的那两个值（超上限时 `page_size` 就是 `100`）；
- 列表载荷恒为 `{"count", "results", "page", "page_size"}`：`count` 是**命中总数**（⛔ 不是本页条数）；
  页号超出范围 ⇒ 空 `results` + 真实 `count`（⛔ 不是错误）；
- ⚠️ **读端点一个字节都不写业务数据**：唯一的一行写库发生在**认证层**（记下该应用
  `last_used_at` 这个时间戳）。

### 2.1 幂等四态（四个写方法共用同一份实现）

同一个 `Idempotency-Key` 在**同一个应用**下的四种状态：

| 状态 | 判据 | 答复 |
|---|---|---|
| **新键** | 这个键没见过 | 执行副作用 + 记下这一步的响应快照 |
| **同键同体** | 键见过、请求体**逐字节相同**、快照非空 | **回放上一次的响应**（HTTP 与信封逐字相同，⛔ 不会执行第二遍） |
| **同键异体** | 键见过、但请求体不同 | `code=1000` + `同一个幂等键配了不同的请求体` |
| **在飞** | 键见过、但上一笔**还在处理中**（快照为空） | `code=1001` + `同一个幂等键的请求正在处理中` |

- 缺失键 ⇒ `1000` + `缺少幂等键`；长度不在 8–128 ⇒ `1000` + `幂等键长度必须是 8–128 个字符`。
- ⭐ **业务失败（码非 0）⇒ 这个键下次可以重试**（我方会把那一笔的内部记录整笔回滚，
  ⛔ 不会让你永久卡在"正在处理中"）。⚠️ 唯一的例外见 §7.3（进度图认领的"拒收即清理"那几档）。
- ⚠️ **回放的是"上一次那次的响应快照"**，⛔ **不是**"拿库里现在的值重新渲染"：
  两次调用之间若那一单被别的路径改过，回放出来的仍是**上一次的载荷**。
- ⚠️ 幂等台账的保留期是 **30 天**：超过窗口后同一个键会被当成**新键**。

## 3. 拉大厅：`GET /api/taker/v1/hall/`

### 3.1 入参（六个筛选 + 分页）

| 参数 | 类型 | 说明 |
|---|---|---|
| `game` | 整数 | 游戏 id（≥1）。⚠️ 传 `abc` ⇒ `1000` |
| `server` | 整数 | 区服 id（≥1） |
| `project_text` | 字符串 | 项目文本，**包含匹配**（不区分大小写） |
| `keyword` | 字符串 | ⭐ **只能按订单号搜**（见 §3.3） |
| `source_order_no` | 字符串 | ⭐ **三方/来源单号精确筛选**（打手拿上家的号来大厅找单；空串 = 没传） |
| `price_min` / `price_max` | 金额（两位小数） | 按**生效接单价**筛选。⚠️ **可以传 `0` 与负数**（`0` 是合法值，⛔ 不是"没传"） |
| `page` / `page_size` | 整数 | 分页（§2 的统一口径） |

- ⚠️ **空串按"没传"处理**（`?game=` 不是非法值，是"没选"）。
- ⚠️ **筛选真的生效**：`game` / `project_text` / 价格区间三条各真的收窄结果。
  ⛔ 本端点**没有** `status` / `is_urgent` / `tag` / 日期 这些参数：它只筛"大厅真的会应用的字段"。
- ⚠️ 结果**只包含**：本租户、**你的游戏权限范围内**、状态是"待抢单"**且**还没有人接手的单
  （三者缺一不可）。⛔ 别人的单、进行中的单、已完成的单**都不会出现**。

### 3.2 一行**恰好 11 个键**（⛔ 多一个少一个都是契约变更）

| 键 | 类型 | 说明 |
|---|---|---|
| `order_no` | string | ⭐ **展示订单号**（2026-10-30 起，D-0338）：这张单**有来源单号就是来源单号**、没有（纯自录单）就是我方内置单号——**拼接单 URL 就用它（按原样拼）**。镜像两路的这一键也一直是各自的展示号（见下）⇒ 三路同口径："给你看的、拼 URL 用的，都是这一个" |
| `source_order_no` | string | **三方/来源单号**原值（没有就是空串）。有来源号时它与 `order_no` **同值**；§3.1 的 `source_order_no` 参数按它**精确筛选** |
| `game` | int | 游戏 id |
| `game_name` | string | 游戏名 |
| `server` | int 或 null | 区服 id（没区服就是 `null`） |
| `project_text` | string | 项目文本 |
| `content` | string | **客户写的**原始需求 |
| `time_requirement` | string | 时间要求 |
| `is_urgent` | bool | 是否急单 |
| `hall_price` | string 或 null | ⭐ **生效接单价**（**字符串两位小数**）。⚠️ `null` = **这一单没有接单价**，那种单**真的在厅**，但抢它会回 `1013`（§4.3） |
| `created_at` | string | ISO 8601（带时区偏移） |

⛔ **大厅行里不给**（**有意不给，不是遗漏**）：

- `customer_phone` / `customer_ww` —— ⭐ **P2：他不是这张单的当前接手人时不给客户联系方式**。
  当他是当前接手人时（**自己抢到的** 或 **我方指派给他的**）走 §5 才有（§5.3 那条口径）；
- `remark`（**我方员工写的**备注）、`sales_agent` / `created_by` / `hall_publisher_name`（员工身份）；
- `net_received` / `refund_fee` / `payment_*` / `total_price`（财务）；
- `source_system` / `remote_*`（上家镜像那一路的**内部**投影键）。

⭐⭐ **改准（2026-10-24，D-0296）：大厅里有了镜像单** —— 上面那张 11 键的表是**原生单**的行。
**上家镜像单**也在同一个列表里返回，行是**恰好 13 键** = 上面那 11 个**同键同名** ＋ 下面两个行身份键：

| 键 | 类型 | 说明 |
|---|---|---|
| `origin` | string | ⭐ **镜像行的身份键**：鸡蛋铺上家镜像行恒 `"upstream"`，团团通上家镜像行恒 `"peer"`（原生行**没有**这个键）—— 你据此分辨行身份、选对应的接单端点（§4.5 / §4.6） |
| `mirror_pk` | int | 镜像行 id —— 拼**接镜像单**的 URL 就用它（§4.5 / §4.6） |

⚠️ **鸡蛋铺上家镜像行**与原生行的取值差异（照实现如实登记）：`server` 恒 `null`（镜像是**文本**区服，
没有我方区服档案）、`time_requirement` 恒空串、`is_urgent` 恒 `false`、`content` 放的是区服**文案**、
`hall_price` 是**勾兑展示价**（恒有值，缺价按 `0.00`）、`order_no` / `source_order_no` 都是**上家展示号**
（⛔ 不是我方订单号——它还没被接走、还没转正）。§3.3 的 `keyword` 对镜像行匹配的就是这个展示号。

#### ⭐ 团团通上家（`peer`）镜像行的取值差异（2026-10-25，D-0303）

同样 13 键，但有几个键的语义与鸡蛋铺镜像行不同（最要紧的是 `origin` / `content` / `hall_price`），
照鸡蛋铺口径解析会读错：

- `origin` 恒 `"peer"`（⛔ 不是 `"upstream"`）⇒ 接单走 §4.6 的 `/hall/peer/<pk>/claim/`；
- `content` = **客户原始需求**（与原生行同义）—— ⛔ 不是区服文案（那是鸡蛋铺镜像行的口径）；
- `hall_price` **可以是 `null`** = 这一单没有展示价（未定价）；这种行**真的在厅**，
  但抢它会回 `1013`（**闸门拒 NULL 价**）⇒ ⛔ 不要把 `null` 当 `0.00` 去抢；
- `order_no` / `source_order_no` 都是**上家单号**（`peer_order_no`），不是我方订单号；
- `server` 恒 `null`、`time_requirement` 恒空串、`is_urgent` 恒 `false`（团团通载荷没有这些字段）。

### 3.3 ⭐⭐ `keyword` **只能按订单号搜**（其它字段一律搜不到）

**这条是承重的，不是"顺便说一下"：**

- `keyword` 的匹配值**恰好**是行上 `order_no` 那一个键**显示的值**（2026-10-30 起原生行
  = **来源号优先展示号** ⇒ 有来源号的单拿**来源号**搜得到、镜像行拿**展示号**搜得到；
  ⛔ 拿客户手机号、游戏角色名当关键词，一律搜不出来——哪怕它们在库里确实是这个值；
  ⛔ 有来源号的单拿我方**内置单号**也搜不出来——这个值已经不在这条载荷里了）；
  ⭐ `§3.1` 的 `source_order_no` 参数仍在（按来源单号**精确**匹配，语义不变）；
- ⛔ **不是"漏了做"**：这是一条**不变式**——**对外可搜的字段必须 ⊆ 响应载荷的键集**
  （§3.2 那 11 个）。否则"搜得到但看不见"就是一条**可探测的信道**：
  拿一个值当 `keyword`，"命中 / 不命中"就能反问出"这张单的某个**你看不到的**字段是不是这个值"；
- ⚠️ 排障提示：**"搜不到"不等于"这张单不在厅"**。核对一张单在不在，
  请用**订单号**搜，或者直接调 §5.2 的查单（那张单得是**你的**才查得到）。

```json
{

  "msg": "",
  "data": {
    "count": 137,
    "results": [
      {
        "order_no": "SYN-2026-0007",
        "source_order_no": "SYN-2026-0007",
        "game": 3,
        "game_name": "示例游戏",
        "server": 11,
        "project_text": "示例项目",
        "content": "客户写的需求原文",
        "time_requirement": "今晚",
        "is_urgent": false,
        "hall_price": "88.00",

```

**纯自录单**（没有来源号）的行则是 `"order_no": "20261008000000000001", "source_order_no": ""`。

### 3.5 ⭐⭐ 镜像同步怎么写（**必须每轮全量翻页 + 按 `order_no` 集合对比**）

⚠️ **大厅不是一张表、也没有"某一行被删了"的推送**（§0.1 第 1 条）。它每一刻都是从
"本租户 + 你的游戏范围 + 待抢单 + 没人接"这几条**现算出来**的一个集合。⇒ 你**不能**靠
"新增了什么"来做增量同步，必须这样做：

1. **每轮全量翻页**：`page=1` 起，`page_size=100`（上限），一直翻到 `len(results) == 0`
   或已取满 `count` 条为止。⚠️ 翻页期间**集合本身可能已经变了**（有人抢走了单）
   ⇒ 这是**最终一致**的对账，不是一刻的快照；
2. **按 `order_no` 集合对比**：把这一轮取到的**全部** `order_no` 收成一个集合，与你上一轮
   存下的集合比 —— 新增的入库、**消失的从你自己的"在厅"表里删掉**（或标记成"已不在厅"）；
3. ⚠️⭐ **发版 / 重启 / 网络中断期间也一样靠它兜**：你漏掉的任何一轮（哪怕漏了一小时），
   下一轮全量对账都会把差异补齐 —— 这正是不做推送时**唯一**能自愈的对账方式。
   ⛔ 别写"只取第 1 页"的增量逻辑：那样第 2 页之后的新单你**永远看不到**，而且**没有任何报错**；
4. ⚠️ **`count` 只用来算总页数 / 判进度**，⛔ 不要拿它当"变化的信号"（它每轮都在变）。

⚠️ **代价如实登记**：全量翻页在厅单很多时是**你自己的带宽与请求数**（每 100 条一次请求），
且受 §9.4 那道兜底闸约束。真要更省，只能等我们做增量 / 游标口径（那是**重新评估的触发条件**，
不在第一版里）。

## 4. 抢单：`POST /api/taker/v1/hall/<order_no>/claim/`

### 4.1 入参

| 项 | 值 |
|---|---|
| 路径段 | `<order_no>` = §3.2 那一行里的订单号（**按原样拼**）。⭐ **镜像单也一样**：`origin="upstream"` 或 `origin="peer"` 的这一键都是各自上家单号，原样拼进来即可——原生查不到时旧路径会依次按鸡蛋铺、团团通镜像解析（peer 单号有歧义时拒绝猜测）；两路各自的 `mirror_pk` 专用端点仍保留（§4.5 / §4.6）。⭐ **原生行同理**（2026-10-30 起）：这一键是**来源号优先展示号**，原样拼进来即可——有来源号的单按来源号接、纯自录单按内置单号接，两条都通 |
| 请求体 | ⛔ **不需要**（无 body）。⚠️ 多带一个 body 既不 500、也⛔ 不被判成 `1000` |
| 请求头 | `Authorization: Bearer <令牌>` + **必带** `Idempotency-Key`（§2.1） |

### 4.2 成功（HTTP 200）

```json
{"code": 0, "msg": "", "data": {"order_no": "20261008000000000001", "status": "IN_PROGRESS", "status_text": "进行中"}}
```

⚠️ `data` **恰好三个键**：`order_no` / `status` / `status_text`。

### 4.3 失败档（**逐条**）

| `code` | 什么情况 | 人话 |
|---|---|---|
| `1002` | ⛔ **不在大厅** / **不在你的游戏范围** / 单号不存在 / 已软删 / **孤儿订单** | `该订单不存在或不在抢单大厅`（⚠️ **五种成因共用这一句**，见下） |
| `1012` | **已被接走** | `该订单已被接走（包含你自己刚才已经接过）` |
| `1013` | **抢不了**：没有接单价 / 被设为禁止自助接单 / 接单价不在允许区间 / 你手上的未完成单已达上限 | ⚠️ **四支各自有一句**（见下面那四条），`msg` 会说明是哪一支 |
| `1000` | 缺 / 非法 `Idempotency-Key` | `缺少幂等键` / `幂等键长度必须是 8–128 个字符` |
| `1002` | 状态机不允许这条流转 | 状态机给的那句话 |
| `401` | 凭据问题（§8.2） | 见 §8.2 |
| `429` | 兜底闸超限（§9.4） | 框架渲染的那句 |

- ⭐⭐ **`1012` 的含义包含"你自己刚才已经接过"**：你**双击**抢单按钮、或者换了**新的**
  `Idempotency-Key` 再发一次同一张单 ⇒ 你会拿到 `1012`。**这不是故障**——
  那张单**已经是你的了**（去 §5 看它）。⚠️ 这一句就是我们为这件事准备的唯一解释。
- ⭐ **`1002` 那一句覆盖五种成因是有意的**：不存在 / 不在你的游戏范围 / 不在厅 / 已软删 /
  孤儿订单**共用同一句话**。否则拿一串单号打过去，就能按文案差别**枚举出本租户有哪些订单号**
  —— 那是一条可探测的信道。⇒ 排障时⛔ 不要往"是不是权限问题"上死磕：先核单号本身与大厅。
- ⚠️ **"没人在厅"与"被别人抢走"长得一样**（都回 `1002` / `1012` 这一族）：
  抢单**只保证"此刻这个人拿到了"**，它不承诺"这张单曾经在厅里"。

**`1013` 那四支各自的 `msg`**（⚠️ 逐字，便于你在日志里认出是哪一支）：

| 哪一支 | `msg` |
|---|---|
| 没有接单价 | `该单没有接单价，请联系客服` |
| 被设为禁止自助接单 | `你已被设置为禁止自助接单` |
| 接单价不在允许区间 | `接单价必须在 <下限>~<上限> 之间`（上下限是**租户给我们配的**） |
| 手上未完成单已达上限 | `你手上未完成的订单已达 <上限> 单` |

⚠️ 后两支里的上限是**配置值**（每个租户不同、随时可改）⇒ 文档这里只给形状，⛔ 不写死数字。

### 4.4 ⭐⭐ 抢单应答**只代表那一刻**（同键重发是**回放录像**，不是事实查询）

- 同一个 `Idempotency-Key` 重发 ⇒ 回放**上一次那一段响应**（逐字相同），⛔ 不会执行第二遍；
  两次调用之间这张单被改过，回放出来的仍是**上一次**的载荷（§2.1）；
- ⭐ **事实以查单（§5.2）/ 我的单（§5.1）为准**：⛔ 不要拿抢单应答里的 `status` 去驱动你自己的
  订单状态机 —— 那一份是"抢到的那一刻"的快照，而这张单**后**可能被我方或客户改过；
- ⛔ **不要用抢单当"探活 / 探测"**：它会**真的把单接走**（接单直接进绩效与结算 ⇒ **动钱**）。
  要探活请用 §3 的读端点。

### 4.5 接镜像单：`POST /api/taker/v1/hall/upstream/<pk>/claim/`（2026-10-24 新增）

大厅（§3）里 `origin == "upstream"` 的那一路**镜像单**也归你接 —— 路径参数用那一行里的 `mirror_pk`。
⚠️ 2026-10-24 追改：**也可以不走本端点**——把镜像行的展示号原样拼进 §4 那个老端点即可（同一套接单逻辑、同一套错误码）；两条任选其一，第三方按自己顺手的来。

| 项 | 值 |
|---|---|
| 路径段 | `<pk>` = §3.2 大厅**镜像行**里的 `mirror_pk`（int，照原样拼） |
| 请求体 | ⛔ **不需要**（无 body） |
| 请求头 | `Authorization: Bearer <令牌>` + **必带** `Idempotency-Key`（§2.1） |

**成功**（HTTP 200）：`data` 与 §4.2 **同形的恰好三键** `{"order_no", "status", "status_text"}`。
⚠️ 这里的 `order_no` 是**转正后我方订单**的订单号：接成功的那一刻，这张镜像单在我们这边
**转正成一张真订单**（并写操作留痕），此后它在 §5「我的单 / 查单」里与原生单**毫无区别**
—— 交单 / 传进度图 / 改状态都走 §5–§7 那几条。

**失败档**（判据是 `code`；码表与 §8.2 同一张，⛔ 不新开码）：

| `code` | 什么情况 | 人话 |
|---|---|---|
| `1012` | **已被别的打手接走** / **租约输家**（别的打手正在接这单——对方秒级收口，刷新即见终局）/ 不在你的游戏范围 / `mirror_pk` 不存在 | `该笔订单已被其他打手接取`（⚠️ **几种成因共用这一句**，不泄露是哪一种——与 §4.3 的 `1002` 同一条防探测思路） |
| `1013` | **抢不了**：§4.3 抢单限制的各支（价按**勾兑展示价**判）⭐ **＋ 优选闸**（见下） | `msg` 会说明是哪一支 |
| `1002` | 上游已收下这张单、我方落库失败（提成 / 押金校验的罕见竞态；⭐ 2026-10-30 起「有人正在接」已并入 `1012`，本码只剩这一个成因） | `正在抢单，请稍后刷新查看` |
| `1000` | 缺 / 非法 `Idempotency-Key` | 同 §2.1 |
| `401` / `429` | 凭据问题 / 兜底闸超限 | 同 §8.2 / §9.4 |

⭐ **优选闸（2026-10-24 起）**：镜像行按**勾兑展示价**判「优选」；个人打手**一次都没完成过订单**
⇒ 拒：`优选订单需要先完成过订单才能接：你还没有已完成的订单`；完成数异常多
⇒ 按「可能已被接手」拒：`此订单可能已被接手，请刷新重试`（同码 `1013`，文案可区分）。
工作室账号与管理员不受这道闸限制。幂等语义与 §4.4 **同一份**（同键重发是回放、事实以查单为准）。

### 4.6 接团团通镜像单：`POST /api/taker/v1/hall/peer/<pk>/claim/`（2026-10-25 新增，D-0303；⭐ D-0347 起同步直连）

与 §4.5 **同族但不同源**：§4.5 接的是鸡蛋铺（上家）镜像行，这一条接的是**团团通之间的**
大厅镜像行（`origin="peer"`）。`mirror_pk` 同样来自 §3 大厅行的 `mirror_pk` /
`origin` 键；路径段用共享的 `int` 转换器。

⚠️ **同步直连（⭐ D-0347，2026-10-31 业务方拍板「能抢就是抢到 抢不到就是抢不到」；
原「确认制 / 接单中」口径已废）**：本端点在**请求内**把抢单请求直转给上家（最多等
**3 秒**，可按机调），当场给结论，三档：

- **上家受理** ⇒ **当场成交**：本方订单已建、挂在接单人名下（§5「我的单」立即可见），
  响应 `code=0`、`data.status="promoted"`（状态文案「已转正」）；
- **上家回绝**（单已被别人接走 / 已撤下 / 没共享给这一家）⇒ `1012`
  「该笔订单已被其他打手接取」；那张卡按拒绝原因下架或放回大厅；
- **3 秒内没拿到上家结论**（超时 / 上家版本旧 / 多跳转发）⇒ `1017`
  「对端未响应，请稍后重试」：卡**当场放回大厅**，可立即重试。若上家其实已经受理，
  订单随后会落进本方**未分配池**（客服可指派，单不会丢）——以「我方已放回」为准。

⚠️ **超时兜底（P3，2026-10-25；⭐ D-0335 起 60 秒，原 300 秒）**：极端情况（请求进程中断
等）残留的 `claiming` 行由常驻 `peer_sync` 每轮调 `peer_hall.reclaim_stuck_claims` 退回
`listed`。判据是 `claiming_at` **严格早于**「此刻 − 60 秒」（恰好 60 秒不回收）；已转正
（`promoted`）的行不碰。正常请求内要么成交、要么当场放回，走不到这一兜底。
前置闸（行可接 / 绑定启用 / 抢单限制各支 / 实名闸 / 优选闸 / 押金）与幂等语义
（`Idempotency-Key` 必带、同键重发是回放）照 §4.1–§4.4 同一份。
团团通镜像单**不分区代练 / 陪玩**（对端载荷无订单类型），抢单上限按代练档（`BOOST`）。

## 5. 我的单 / 查单

### 5.1 我的单：`GET /api/taker/v1/my/orders/`

| 参数 | 类型 | 说明 |
|---|---|---|
| `page` / `page_size` | 整数 | 分页（§2 的统一口径，上限 100） |
| `updated_since` | ISO8601 **时刻**（可选） | 只要**这个时刻之后被改过**的单。⚠️ **必须带时间与时区**，见下 |
| `source_order_no` | 字符串 | ⭐ **三方/来源单号精确筛选**（可选；只在你自己的单里筛） |

- ⚠️⭐ **`updated_since` 必须带"时间那一半"与"时区"**：
  `2026-10-08T00:00:00+08:00` ✅ / `2026-10-08 00:00:00+08:00` ✅ / `2026-10-08T00:00:00Z` ✅；
  ⛔ `2026-10-08`（裸日期）⇒ `1000`、⛔ `2026-10-08T00:00:00`（没时区）⇒ `1000`、⛔ `abc` ⇒ `1000`。
  **为什么**：裸日期是"哪一天"、不是"哪一刻"，收下来我们只能**猜**一个时分秒；
  而没时区的值会在不同机器上被解析成**两个时刻**。⇒ 两种都不收，⛔ **也不"静默不过滤"**
  （静默不过滤会让你以为拿到了增量、实际是全量，而你可能据此**删掉**自己那边的单）。
- ⚠️ 过滤的是订单的**最后修改时刻**：**同一张单被改两次，第二次也会再出现一次**
  ⇒ 你的合并逻辑要按 `order_no` **覆盖**，⛔ 不要假设"一个单只会出现一次"。
- ⭐ **这里只会有"你当前接手的、还没被软删的"单**（判据 = 那条「打单工资」绩效行的接手人
  就是你这把凭据绑定的账号）。⛔ 别人接的单、你只是"参与过"的单**都不在这里**。
- ⚠️ **`order_no` 在这里是内置单号**（⛔ 与 §3.2 大厅行的"来源号优先展示号"**不同**）：
  它是 §5.2 查单 / §6 改状态 / §7 进度图三条端点的**路径参数**，按它拼 URL；
  有来源号的单，来源号照旧在 `source_order_no` 键上。

### 5.2 查单：`GET /api/taker/v1/orders/<order_no>/`

- 成功：`code=0` + `data` = **一张单**，键集与 §5.3 那一行**逐键同形**（单数版，⛔ 不是包在数组里）；
- 不存在 / **不是你的单** / 已软删 ⇒ `1002` + `该订单不存在或不是你的单`
  （⚠️ 三者**同形**，见 §3 的同一条理由）；
- ⭐ 排障：**"抢到了但查不到"几乎一定是拿错了单号**（或者拼错了一个字符）。
  ⛔ 别拿**来源单号**当订单号用：它在行里叫 `source_order_no`（2026-10-23 起给），
  但路径与 `keyword` 只认 `order_no`。

### 5.3 ⭐ 行 = **恰好 18 个键**（§3.2 那 11 个 **＋** 这 7 个）

| 加的键 | 类型 | 说明 |
|---|---|---|
| `status` | string | 订单状态**机器值** |
| `status_text` | string | 状态**中文名**（与本平台页面**同一份**枚举，⛔ 不是另造的一份） |
| `claimed_at` | string 或 null | **接单时刻**（ISO 8601）。⚠️ 它是**绩效行上**那一列，`null` = 那一行没有这个值 |
| `updated_at` | string | 最后修改时刻（`updated_since` 过滤读的就是它） |
| `customer_phone` | string | ⭐ **客户手机号**（**当他是这张单的当前接手人时**才给，见下） |
| `customer_ww` | string | ⭐ **客户旺旺**（同上） |
| `total_price` | string 或 null | 订单总价（字符串两位小数） |

⭐ **P2：客户联系方式**（`customer_phone` / `customer_ww`）**当他是这张单的当前接手人时才给**：
§3.2 的大厅行里**没有**这两个键，只有「我的单 / 查单」才有。
⚠️ 判据是「**他是这张单的当前接手人**」（那条「打单工资」绩效行的接手人 = 这把凭据绑定的账号），
它**包含**两种情况：**他自己抢到的** 与 **我方把单指派给他的**
（以及换人之后的新接手人）⇒ ⛔ **不要**把它读成"抢到之后才有"。
⚠️ 这条**不是**"我们忘了加"，而是**有意的**：厅里的单谁都能看见，联系方式只给接手人。
⇒ 反过来说：**单被转给别人之后，你这边就看不到它的联系方式了**（它会从你的「我的单」里消失）。

⭐ **2026-10-23 变更**：`source_order_no`（三方单号）已加入大厅行与「我的单 / 查单」；
它只用于**对单**，⛔ 仍**不能**当 `order_no` 拼路径、也**不在** `keyword` 的匹配面里。

⛔ **仍然不给**（`docs/specs/2026-10-08-taker-open-api-design.md` §5.2 逐条）：
`remark`（我方员工写的）· 员工身份（`sales_agent` / `created_by` / `updated_by` / `hall_publisher*`）·
`net_received` / `refund_fee` / `payment_*` / 成本 / 提成 / `fee` ·
镜像那一路的 `origin` / `source_system` / `remote_*` / `mirror_pk`。

## 6. 改状态：`POST /api/taker/v1/orders/<order_no>/status/`

### 6.1 入参

| 字段 | 必填 | 说明 |
|---|---|---|
| `status` | ✅ | ⭐ **只允许三档机器值**（见 §6.2）。⛔ 传**中文标签**（例如 `已完成`）⇒ `1000` |
| `remark` | `ISSUE` 必填，其他状态可空 | 去掉首尾空白后最多 **255** 字符，会记入操作日志。提交问题单时填写问题原因。 |

```json
{"status": "PENDING_REVIEW", "remark": "已按要求做完"}
```

- ⛔ **只收枚举机器值**：`IN_PROGRESS` / `COMPLETED` / `WAITING_GRAB` / `UNASSIGNED` /
  `REFUNDED` 这些都是**合法的枚举值**，但**不在允许写的那三档里** ⇒ `1000`
  （`msg` 会**点名**允许哪三个）。
- ⚠️ **`remark` 里 ⛔ 不要写客户隐私**：它会进我方的操作日志（那是给我们自己排障看的）。
- 提交问题单时，缺少 `remark` 或仅输入空白会返回 `1000` 和「请输入问题原因」，订单状态不变。
- ⚠️ 判据顺序是**先授权、后参数**：对**别人的单**打一个非法目标态，回的是 `1002`（不是 `1000`）
  —— 否则那句 `1000` 就等于告诉你"这张单存在"。

### 6.2 ⭐⭐ **只允许** `PENDING_REVIEW` / `ISSUE` / `PAUSED`

| 机器值 | 中文 | 含义 |
|---|---|---|
| `PENDING_REVIEW` | 待验收 | ⭐ **交单**（干完了，等我们验收） |
| `ISSUE` | 问题单 | 有问题（客户那边 / 游戏那边出状况） |
| `PAUSED` | 已暂停 | 先停下 |

⭐ **P3：`COMPLETED`（已完成）只能由团团通这边验收，对端永远不要传。**
⛔ 传了 ⇒ `1000` + 一句点名白名单的话。**这不是"权限不够"，是契约就没有这条路**：
「完成」是**我们**验收后的结论，⛔ 不是你那边宣布的。

⛔ 别的状态（`IN_PROGRESS` / `WAITING_GRAB` / `UNASSIGNED` / `REFUNDED` …）同样**不许**传：
它们即使在我方状态机上有边，也不在这份**对外白名单**里。

### 6.3 成功与失败

- 成功：`code=0` + `data = {order_no, status, status_text}`（**恰好三键**，与抢单同形）；
- `1002`：不存在 / 不是你的单 / 已软删 / 状态机不允许这条流转（⚠️ 同形）；
- `1000`：`status` 不是枚举值 / 不在白名单 / 问题单缺少 `remark` / `remark` 超 255 / 缺 `Idempotency-Key`；
- ⚠️ **改状态要带 `Idempotency-Key`**（§2.1）：它是**写端点**。

## 7. 进度图：列表 / 取票 / 认领（三步）

### 7.1 三步

| 步 | 方法 / 路径 | 做什么 |
|---|---|---|
| ① 列表 | `GET /api/taker/v1/orders/<order_no>/images/` | 看这单**已经认领完成**的图（分页） |
| ② 取票 | `POST /api/taker/v1/orders/<order_no>/images/ticket/` | 拿一张**上传票** + 一个**上传地址** |
| ③ 认领 | `POST /api/taker/v1/orders/<order_no>/images/` | 告诉系统"我刚把文件传上去了"，落成可读的一行 |

**完整流程**：② 取票 → **你自己**拿 `upload_url` 把图片 `PUT` 上去 → ③ 认领 → ① 列表里能看到它。
⚠️ **中间那一步的上传不经过我们**（直传对象存储），我们只在 ② ③ 两步记账。

### 7.2 入参与应答

② **取票**的入参：`{"ext": "jpg"}`（**必填**，≤8 字符；最终只放行 `jpg` / `jpeg` / `png`，
别的 ⇒ `1000`），可选 `img_type`（⚠️ **只收 `0`** = 订单进度图，传 `1` ⇒ `1000`）。
成功 ⇒ `data` **恰好三键**：

| 键 | 说明 |
|---|---|
| `key` | 对象名。**认领时必须原样回传它**（第三方手里只有这个 key） |
| `upload_url` | ⭐ **短时效预签名直链**，把文件 `PUT` 到这里 |
| `expires_in` | `upload_url` 的有效**秒数**（⚠️ 过期就要重新取票） |

③ **认领**的入参：`key`（**必填**，≤255）、`original_name`（可选，≤255）、`remark`（可选，≤50）。
成功 ⇒ `data` = **该图片项**，键**恰好七个**：
`img_type` / `url` / `original_name` / `size_bytes` / `remark` / `uploaded_by_name` / `created_at`。

① **列表**每一行就是上面那**七个键**（与 ③ 的应答**逐键同形**）。
⛔ 列表**只给已经认领完成的图**（`status=ready`），⛔ **不给内部主键、不给账号主键**
（上传人给的是**显示名** `uploaded_by_name`）。
⚠️ 一行都还没有时 `results` 是**空数组**（`code=0`）；⚠️ 而"这单根本不是你的" ⇒ `1002`
（两者**不同**：前者是"这单没有图"，后者是"这单不在你这里"）。

### 7.3 ⚠️ 三条如实登记的边界（⛔ 别照别的平台的习惯推断）

- ⭐ **我们⛔ 不抓取你给的网址**：`upload_url` 是**预签名直链**，你把字节 `PUT` 上去即可。
  本侧**没有**"给我一个 URL、我去下载"这回事（第一版不做，也不在计划里）；
- ⚠️ **`url` 是预签名直链**：列表与认领回的 `url` 都是**当时现签**的（生产有效期 **1–2 小时**；本机/测试 300 秒）
  ⇒ ⛔ 别把它长期存起来当永久地址、⛔ 也别拿 `url` 当图片的**去重键**（同一张图每次签出来的
  URL 都不一样）。要长期保存请**自己下载下来**；
- ⚠️ **拒收即清理那一档会"保留副作用"**：图片超过每单上限（20 张）/ 0 字节 / 超过 18 MiB /
  魔数认不出 ⇒ 我们会**删掉那一行与那个对象**并回 `1000`；这一档里**同一个 `Idempotency-Key`
  重发会回放那一次失败**（因为删除已经真的发生、不能回滚）⇒ 要重试请**换一个新键**
  （§2.1 的"业务失败可重试"那一条在这里**不适用**）。

## 8. 响应格式与错误码

### 8.1 业务失败也是 HTTP 200 —— 判据是 `code`

**除取令牌端点（§1.1）之外**，所有响应都是同一个信封：

```json
{"code": 0, "msg": "", "data": {...}}
```

⭐ **`code` 才是判据，⛔ 不是 HTTP 状态码**：业务失败（参数缺失、资源不存在）也回 **HTTP 200**，
`code` 非 0。**传输 / 认证层失败**（401 / 429）才保留 HTTP 状态码，且 `code` 取同一数值。

⇒ 你的代码必须写成"**先看 `code`，再看 `data`**"，⛔ 不要写成"200 就是成功"。
⚠️ 只有**取令牌端点**是例外：它按 OAuth2 标准回**裸体**（成功是三键、失败是两键，
⛔ 没有 `code` / `msg` / `data`）—— 见 §1.1。

### 8.2 对外承诺的错误码（**逐条**）

**信封那一侧**（除取令牌端点外的每一条端点）：

| `code` | HTTP | 什么情况 | 一句人话 |
|---|---|---|---|
| `0` | 200 | 成功 | `data` 见各端点 |
| `1000` | 200 | **参数问题**：缺 / 非法 `Idempotency-Key`、键长不在 8–128、分页参数非法、筛选参数非法（`?game=abc`）、目标状态不在白名单 / 不是枚举值、`remark` 超长、`ext` / `img_type` / `key` 非法、内部应用管理端点的入参非法（含**表外字段**） | `msg` 会**点名**是哪一处（例如 `缺少幂等键`） |
| `1001` | 200 | **幂等冲突**：同一个 `Idempotency-Key` 的上一笔**还在处理中**（§2.1） | `同一个幂等键的请求正在处理中` ⇒ 用**同一个键**稍后重试 |
| `1002` | 200 | **查不到 / 不是你的单 / 不在厅**（三者**同形**）· 状态流转不被状态机允许 | `该订单不存在或不在抢单大厅` / `该订单不存在或不是你的单` / 状态机那句 |
| `1012` | 200 | **已被接走**（⭐ **包含你自己刚才已经接过**，§4.3） | `该订单已被接走（包含你自己刚才已经接过）` |
| `1013` | 200 | **你现在抢不了这张单**：没有接单价 / 被设为禁止自助接单 / 接单价不在允许区间 / 手上未完成单已达上限 | 领域层给的**那一支**的那句话（四支各不相同） |
| `401` | **401** | **凭据问题**（§8.3） | `应用凭据无效` / `令牌已过期` / `来源 IP 不在白名单内` |
| `429` | **429** | **兜底闸超限**（§9.4） | 框架渲染的那句（带 `Retry-After`） |

⚠️ **本侧对外端点不返回 `403`**：对外面**不装权限类**（范围由"绑定的那个打手账号"算，
不满足一律回 `1002`）。`403` 只会出现在**内部**应用管理端点那一组（会话 + 节点门）上。

**取令牌端点那一侧**（**裸 OAuth2 体**，⛔ 不是信封 —— 见 §1.1）：

| `error` | HTTP | 什么情况 |
|---|---|---|
| `invalid_client` | **401** | 密钥错 / 应用不存在 / 应用已停用（**三档逐字同句**，`应用凭据无效`） |
| `unsupported_grant_type` | **401** | `grant_type` 不是 `client_credentials`（含没传、体不是 form-urlencoded） |
| `temporarily_unavailable` | **429** | 兜底额度超限，或**按来源 IP 的失败闸**已超限（§9.4） |

### 8.3 `401` 的语义：**四档同形，⛔ 分不出来**

业务端点上的 `401` 一共覆盖**四种**原因，`msg` **逐字不同**、但**都不告诉你更多**：

| `msg`（逐字） | 什么时候 |
|---|---|
| `应用凭据无效` | 没带 `Authorization` / 拼法不是 `Bearer <令牌>` / 令牌是假的 / **应用已被停用**（**这四种共用这一句**） |
| `令牌已过期` | 令牌的 `exp` 到了（有效期 7200 秒）⇒ **重新换一颗**（§1.1） |
| `来源 IP 不在白名单内` | 租户给这个应用配了 IP 白名单，而你的来源 IP 不在里面 |
| —— | ⚠️ 还有一类：**应用配了白名单 / 应用停用 / 令牌过期同时发生**时，你只会看到**其中一句**（先命中的那一档） |

- ⭐ **"应用凭据无效"覆盖四种原因是有意的**：否则就能用响应差异**枚举出哪些应用存在**。
  ⇒ 排障时⛔ 不要指望从 `msg` 里分出"是停用了还是密钥错了"，直接找租户核对。
- ⚠️ **本侧的令牌与上家侧的令牌互相不认**（结构上如此，不是"配置问题"）：
  拿**打手侧**的令牌打 `/api/open/v1/…` ⇒ `401`；拿**上家侧**的令牌打 `/api/taker/v1/…` ⇒ `401`。
  ⛔ 别试图"复用一把令牌打两个前缀"。
- ⚠️ **凭据写错别硬重试**：同来源 IP **60 秒内失败 20 次**之后，那 60 秒内**连正确的请求**
  也会被拒（回 **429**，§9.4）。第 21 次起看到 **429** 而不是 401 时，就是这个闸。

## 9. 必须知道的禁令与边界

### 9.1 ⛔ 浏览器端直连不支持

本 API **没有 CORS 响应头**（专门没做，因为要新增运行时依赖）⇒ **必须在服务端调**。
在浏览器里 `fetch` 会因为没有 `Access-Control-Allow-Origin` 而失败。
⚠️ 就算将来开了 CORS，把 `AppSecret` 放进浏览器也等于**公开密钥**（谁都能读 JS）⇒ 那条路不可行。

### 9.2 ⛔⭐ 没有推送 —— 必须轮询（⭐ 第二期已改准：见本节末，回调推送在 §12）

本侧**第一版没有任何主动回调推送**：⛔ 没有回调地址可配、⛔ 没有事件订阅、⛔ 没有
`X-TT-*` 那一族签名头（那是**上家侧**那份文档里的东西，与你无关）。
⚠️ 「我的单」的状态变化**不会通知你** ⇒ 你必须按时调 `GET /api/taker/v1/my/orders/`
（§5.1，可带 `updated_since`）自己发现。你能拿到多新的数据 = **你自己的轮询间隔**。

⛔⭐ **改准（2026-10-09，第二期）：上面整段已过期**（原句逐字保留）。
第二期**加了回调推送**（§12）：⛔ 上面那句「没有 `X-TT-*` 那一族签名头」**反了** ——
现在**本侧也有**那一族头（`X-TT-Timestamp` / `X-TT-Delivery` / `X-TT-Signature`，
签名契约与上家侧**逐字同一份**，见 §12.3）。逐条：
- ⭐ **有回调地址可配了**：`PATCH /api/taker/apps/<pk>/` 的 `callback_url` / `callback_state`
  （建应用时也能填，§12.9）；
- ⭐ **推的是「他当前接手的单」的四类事件**（§12.1）：状态变化 / 被删 / 新增进度图 /
  **不再是他的了**（`order.reassigned`）；
- ⛔ **大厅里来了新单仍然不推**（上面那段"大厅必须轮询"这一半**不变**，§12.1）；
- ⚠️ 而上面"你必须按时调「我的单」"这句话**仍然建议照做**：推送是**至少一次**、
  延迟 ≈ 10 秒、**不在业务事务里**（§12.8）⇒ 轮询是兜底，不是白做。

### 9.3 ⛔ 轮换密钥 = **瞬间断电**（无宽限期）

租户调 `POST /api/taker/apps/<pk>/rotate-secret/` 之后**旧密钥立即失效、没有宽限期、
也不会有通知**（平台没有主动外呼能力）⇒ 你正在跑的集成会**当场 401**（§1.1 第 2 条：
该应用**已经发出去的令牌也一起失效**）。
⚠️ 换密钥要靠**人工**协调：租户在页面上看到新密钥后手工告诉你。
⚠️ 密钥**永不过期**（平台不设 `expires_at`）⇒ 泄露不会自愈，只能靠人工轮换或停用应用。

### 9.4 ⚠️ 限流是"兜底"，⛔ 不是配额

平台**不设每应用配额**（业务方要测服务器上限）。只有两道**极宽的兜底闸**：

1. **业务端点**：**3000 次 / 分钟 / 应用**——正常业务**永远碰不到**，它只挡失控
   （死循环、脚本跑飞）。超限 ⇒ **HTTP 429** + `code=429` + `Retry-After: <秒>`；
2. **取令牌端点**：**每来源 IP 每 60 秒 300 次，含成功与失败**；超限 ⇒ **HTTP 429** +
   裸 OAuth2 体（§1.1）。

⛔ 别把它们读成"有额度这回事"：没有套餐分级、没有提额流程。

⚠️ 另有一条**按来源 IP 的失败计数**（**60 秒窗口内失败 20 次**后，那 60 秒内**连正确的请求**
也会被拒）：它挡的是"穷举 `client_secret` / 猜 `AppKey`"。**Bearer 那条路与取令牌端点
共用同一行计数**。⇒ ⭐ **凭据写错别硬重试**：先按 §11 排查，否则你会把自己挡在门外最多一分钟
（第 21 次起回 **429**，⛔ 不是 401）。

⚠️ **所以真正的第一道防线是密钥管理 + 人工停用应用**（秒级生效、立刻 401，§9.3）。
请自己也做好用量监控。

### 9.5 ⭐ **`app_secret` 是明文、随时可取**

- 应用管理页的列表里**每一行都显示明文密钥**，并带一个**复制**动作；
- 后端**所有**取应用的响应都带它（列表 / 创建 / `PATCH` / 轮换，§1.2）；
- ⭐ 业务方 2026-10-07 的口径是「**密钥改成明文展示 可以随时获取 不要加那个只能看一次
  的限制**」⇒ ⛔ **不存在"只显示这一次"这回事**：真丢了回后台再抄一次就行，
  ⛔ **不必**为了"没抄到"去轮换（轮换是"瞬间断电"，§9.3）。

⛔ **平台侧没有放松的那一条**：密钥**不进**平台的日志 / 操作留痕 / 错误消息
（由 `src/tests/test_takerapi_app_api.py::TakerAppSecretNeverLoggedTests` 逐条钉住）。

### 9.6 ⚠️ 其它如实登记的边界

- **停用是唯一的关闭动作**：应用**只能停用不能删**（没有 `DELETE` 端点，已认证且有节点的
  调用方得到 **405**）。停用后**所有**调用立刻 `401` + `应用凭据无效`（秒级生效，不缓存）。
- **IP 白名单**：默认**不启用**（空 = 不限制）。租户可以配（每行 / 逗号一个 IP 或网段）；
  配了之后来源 IP 不在名单内 ⇒ `401` + `来源 IP 不在白名单内`。
- **重放**：⛔ 本版**没有** nonce / 请求级防重放 —— 令牌有效期内（最长 7200 秒）
  同一个请求可以被重放。只读接口无害；**写接口靠 `Idempotency-Key` 兜**
  （同一个键重发 ⇒ 回放，⛔ 不会执行两次业务）。
- ⛔⭐ **回放不等于事实（这条覆盖所有写端点，不只是抢单）**：同一个 `Idempotency-Key`
  配同一个 body 重发时，我们回的是**那一刻那一次的响应快照**（§2.1 的四态语义），
  **不会重新查一次你的授权面**。⇒ 单在两次调用之间**被转给了别人 / 被软删 / 状态被改过**时，
  你重发仍会拿到**那一份旧的成功信封**（它说的是"当时成了"，不是"现在还能"）。
  ⇒ **事实一律以查单（§5.2）/ 我的单（§5.1）为准**，⛔ 不要拿任何写端点的**回放**当状态查询。
- ⚠️ **进度图的上传不因"单已完成 / 已结账"而关闭**：取票与认领**没有**额外那一道闸
  （它们与内网调的是**同一份**实现）⇒ 单完成了、甚至工资结账了，只要你是它的当前接手人，
  上传仍然会成功。⛔ 我们**不承诺**"完成后不能传图"——要拦这件事目前只能靠**人工停用应用**（§9.3）。
- **一个应用 = 一个打手账号 + 一个租户域名**：一个工作室有 N 个打手就是 N 套（§1.2）。
- ⚠️ **抢单直接进绩效与结算**（**动钱**）⇒ 拿它当探活 / 压测会真的把单接走（§4.4）。
- ⚠️ **计费 / 流量**：本平台**不按调用量计费**，也⛔ 不承诺任何 SLA 数字（没有对外承诺过
  可用性指标）⇒ 请你自己的集成做好超时与重试（尤其是**写端点的幂等键**）。

### 9.7 ⛔ 传了我们没收录的字段 ⇒ **fail-closed**：`1000` + 点名

⭐ **写端点（以及内部应用管理端点）的**请求体**是**白名单 fail-closed**：

- 体里出现**表外**的键 ⇒ `code=1000` + **点名**是哪些键 + **一行都不落库**；
- ⛔ **不是"忽略"**：我们不会收下一个字段然后悄悄丢掉它 —— 那样你会以为写进去了、其实没有，
  **而且没有任何信号**（"静默丢字段"比报错更贵）；
- ⚠️ 值是不是空的**不影响**这条判据：`""` / `null` 的未知键**照拒**；
- ⚠️ 表内的**可选**字段缺失**仍然照旧**（可选就是可选，⛔ 别读成"都要必填"）；
- ⚠️ **它管的是"请求体里的字段"，⛔ 不管 query 参数**：§3.1 那六个筛选之外的 query 参数会被
  **忽略**（`?status=IN_PROGRESS` 既不筛、也不报错）⇒ ⛔ 别把"没报错"读成"筛了"。

```python

四步：① 换令牌 ② 拉抢单大厅 ③ 抢单 ④ 查我的单。

⚠️ 每个联网函数都带一个 `opener` 形参（默认走真实网络）：
那是给**离线自检与测试**留的接缝 —— 注入一个桩就能在不联网的情况下驱动整条流程。
直接运行本文件时它是**离线**的（只用合成桩跑一遍形状），⛔ 不联网。
⚠️ **改准（2026-10-09，第二期）**：本行**原写**「⚠️ 本侧**没有推送**（§9.2）：真实对接里你要自己**定时**重复 ② 与 ④。」
（**原句在此保留**）—— 第二期**加了回调推送**（§12）⇒ ④（我的单）那一跳可以改成
「**等推送** ＋ 定时兜底」；⚠️ 而 **②（拉大厅）仍然必须定时重复**（大厅新单不推，§12.1）。
"""
import json
import urllib.error
import urllib.parse
import urllib.request


class OAuth2Error(RuntimeError):
    """换令牌失败：`error` / `error_description` 就是我们回给你的那两个键（§1.1）。"""

    def __init__(self, error, error_description):
        super().__init__("%s: %s" % (error, error_description))
        self.error = error
        self.error_description = error_description


def _open(request, *, opener=None):
    """发一个请求：默认走真实网络；`opener` 不为空时交给它（离线自检 / 测试注入的**桩**）。"""
    if opener is None:
        return urllib.request.urlopen(request)
    return opener(request)


def _base(base_url):
    """去掉结尾的斜杠（`base_url + path` 拼出来才是那个契约里的路径）。"""
    return base_url.rstrip("/")


def fetch_token(base_url, client_id, client_secret, *, opener=None):
    """① 换令牌：`POST /api/taker/oauth/token`（form-urlencoded）。

    成功回**裸三键** `{"access_token", "token_type", "expires_in"}`；
    失败是**裸两键** `{"error", "error_description"}`（⛔ 不是本仓的 code/msg/data 信封）。
    ⚠️ 令牌有效期到点即失效、⛔ 没有 refresh ⇒ 到点就再调一次本函数。
    """
    form = urllib.parse.urlencode(
        {
            "grant_type": "client_credentials",
            "client_id": client_id,
            "client_secret": client_secret,
        }
    ).encode("utf-8")
    request = urllib.request.Request(
        _base(base_url) + "/api/taker/oauth/token",   # ⚠️ 这条路径**没有**末尾斜杠
        data=form,
        method="POST",
        headers={"Content-Type": "application/x-www-form-urlencoded"},
    )
    try:
        with _open(request, opener=opener) as response:
            payload = json.loads(response.read().decode("utf-8"))
    except urllib.error.HTTPError as exc:
        # 401 / 429 都是裸 OAuth2 体；⛔ 不要在这里去看 code/msg（那两个键根本不存在）。
        failure = json.loads(exc.read().decode("utf-8"))
        raise OAuth2Error(failure["error"], failure["error_description"]) from exc
    # ⭐ 令牌体**恰好**这三个键（⛔ 没有 refresh_token，§1.1 第 3 条）——拼错了当场就说出来。
    expected = {"access_token", "token_type", "expires_in"}
    if set(payload) != expected:
        raise OAuth2Error("unexpected_token_body", ",".join(sorted(payload)))
    return payload


def call_api(base_url, access_token, path, *, method="GET", body=None,
             idempotency_key=None, opener=None):
    """②③④ 调业务端点：带 `Authorization: Bearer <令牌>`；**写端点**还要带 `Idempotency-Key`。

    ⚠️ 判据是响应体里的 `code`（⛔ 不是 HTTP 状态码）：业务失败也是 HTTP 200。
    """
    data = None if body is None else json.dumps(body, ensure_ascii=False).encode("utf-8")
    headers = {"Authorization": "Bearer " + access_token}
    if data is not None:
        headers["Content-Type"] = "application/json"
    if idempotency_key is not None:
        headers["Idempotency-Key"] = idempotency_key
    request = urllib.request.Request(
        _base(base_url) + path, data=data, method=method, headers=headers
    )
    with _open(request, opener=opener) as response:
        envelope = json.loads(response.read().decode("utf-8"))
    if envelope["code"] != 0:
        raise RuntimeError("%s: %s" % (envelope["code"], envelope["msg"]))
    return envelope["data"]


def list_hall(base_url, access_token, *, page_size=100, opener=None):
    """② 拉大厅（§3）。⚠️ 真实对接要**每轮全量翻页 + 按 `order_no` 集合对比**（§3.5）。"""
    query = urllib.parse.urlencode({"page": 1, "page_size": page_size})
    return call_api(base_url, access_token, "/api/taker/v1/hall/?" + query, opener=opener)


def claim_order(base_url, access_token, order_no, *, idempotency_key, opener=None):
    """③ 抢单（§4）。⭐ 应答只代表**那一刻**；事实以查单 / 我的单为准（§4.4）。

    ⚠️ `idempotency_key` 是**必带**的（8–128 字符）⇒ 重试时请**沿用同一个键**。
    """
    return call_api(
        base_url,
        access_token,
        "/api/taker/v1/hall/%s/claim/" % order_no,
        method="POST",
        idempotency_key=idempotency_key,
        opener=opener,
    )


def my_orders(base_url, access_token, *, updated_since=None, page_size=100, opener=None):
    """④ 我的单（§5.1）。⚠️ `updated_since` 必须**带时间与时区**（裸日期 / 无时区 ⇒ `1000`）。"""
    params = {"page": 1, "page_size": page_size}
    if updated_since is not None:
        params["updated_since"] = updated_since
    return call_api(
        base_url, access_token, "/api/taker/v1/my/orders/?" + urllib.parse.urlencode(params),
        opener=opener,
    )

class _StubResponse:
    """离线自检用的桩响应（只实现本示例用到的 `read()` 与上下文管理器）。"""

    def __init__(self, payload):
        self._payload = json.dumps(payload).encode("utf-8")

    def read(self):
        return self._payload

    def __enter__(self):
        return self

    def __exit__(self, *exc_info):
        return False


def offline_opener(responses):
    """离线自检用的桩 `opener`：按顺序吐出预置的响应（⛔ 不联网）。"""
    queue = list(responses)

    def opener(request):
        if not queue:
            raise AssertionError("桩被调用的次数超出预期：%s" % request.full_url)
        return _StubResponse(queue.pop(0))
```

## 11. 给 AI 的排查顺序

> 这份文档的读者首先是 AI ⇒ 下面是**按顺序**排查的清单。⚠️ 每一条都对应一个真实会踩的坑，
> 请**按顺序**走，⛔ 不要跳着猜。

**⛔ 先记住三条底层事实**（它们能解释你看到的大部分现象）：

- 判据是响应体里的 **`code`**（HTTP 200 也可能是失败）——**唯一例外**是取令牌端点（§1.1）；
- 对外端点**只认** `Authorization: Bearer <令牌>`：⛔ 没有签名（那是上家侧那份文档的事）、
  ⛔ 也没有会话 cookie；⚠️ 别与**我们推给你**的那一侧搞混 —— 那一侧（§12）**是带签名的**
  （`X-TT-*` 三个头，§12.3），只不过签的是**我们的出站请求**，不是你的入站请求；
- 入参是**白名单 fail-closed**：体里表外的键不会"被忽略"，而是 `1000` **并点名**（§9.7）。

**按这个顺序查：**

1. ⭐ **换不到令牌**（`POST /api/taker/oauth/token`）：
   - 拿到 `401` + `invalid_client` ⇒ 三档（密钥错 / 应用不存在 / 应用停用）**故意同一句**，
     ⛔ 别想从文案分辨：核对 `client_id` 是不是**这一家租户的** `AppKey`、
     `client_secret` 有没有多余空白、应用是不是被停用了（§1.1）；
   - 拿到 `401` + `unsupported_grant_type` ⇒ `grant_type` 写错 / 没传 / **体不是
     form-urlencoded**（发了 JSON 也会落到这一档，§1.1）；
   - 拿到 `429` + `temporarily_unavailable` ⇒ 别硬重试（§9.4，等窗口过去）；
   - ⚠️ 确认你打的是**这一家的域名**（拿 A 家密钥打 B 家域名 = 401，§1.3）；
   - ⚠️ **`expires_in` 是 7200 秒**、⛔ 没有 refresh：到点直接**重新换**（§1.1）。
2. ⭐ **`401`（业务端点）**：三句话**逐字**对应三种情况（§8.3）——
   `应用凭据无效`（没带 `Authorization` / 拼法不是 `Bearer <令牌>` / 令牌假 / **应用停用**）、
   `令牌已过期`（重新换）、`来源 IP 不在白名单内`（找租户加白名单）。
   ⛔ **不要**去找"签名怎么算"——本侧入站没有任何签名。
3. ⭐ **`1000`（参数问题）**：读 `msg`，它会**点名**。
   - `缺少幂等键` / `幂等键长度必须是 8–128 个字符` ⇒ 写端点必带 `Idempotency-Key`（§2）；
   - `该单没有接单价…` 之外的白名单句 ⇒ 你传的目标状态不在那三档里（§6.2）；
   - `请求里有本 API 不接受的字段…` 这一族 ⇒ 你传了**表外**的键（§9.7）；
   - `?page=abc` / `?page=0` / `?game=abc` ⇒ query 参数非法（§2 / §3.1）；
   - `updated_since` 相关 ⇒ 少了时间那一半或时区（§5.1）。
4. **`1001`**：同一个 `Idempotency-Key` 的**上一笔还在处理中**（§2.1）。
   ⇒ 用**同一个键**稍后重试（⛔ **不要换一个新键**：换键就等于再执行一次业务）。
5. **`1002`**：大厅那一侧（`该订单不存在或不在抢单大厅`）或我的单那一侧
   （`该订单不存在或不是你的单`）。
   - 抢单 ⇒ 单号对不对？**这张单在你的游戏范围里吗**？它还在厅里吗（可能已被别人接走）？
   - 查单 / 改状态 / 进度图 ⇒ **这张单是你接的吗**？⚠️ 抢别的单、或者你的单被别人接手过，
     都会看不到它；
   - ⚠️ 「不在你的范围」与「不存在」**长得一样**（有意，§4.3）⇒ ⛔ 别指望从文案分出来。
6. **`1012`**：**已被接走**（⭐ **包含"你自己刚才已经接过"**，§4.3）。
   ⛔ 别把它当故障：去 §5.1 的「我的单」里看它**是不是已经在你这儿了**。
7. **`1013`**：你现在抢不了这张单。读 `msg` 分辨是哪一支：没有接单价 / 禁止自助接单 /
   接单价不在允许区间 / 手上未完成单已达上限（§4.3）。⚠️ 前两支要找租户改配置（我们改不了）。
8. **`429`**：限流（§9.4）。读 `Retry-After` 等到点再试；⚠️ 别硬重试
   （尤其**凭据类的 429**：那是按来源 IP 的失败闸，硬重试只会把自己挡得更久）。
9. ⚠️ **大厅取到了、但是空的**：按这个顺序核 —— ① 你的游戏权限里有没有那款游戏
   （范围是**绑定账号**的，不是"整套凭据"的）；② 那款游戏里**此刻真的有**待抢且没人接的单吗；
   ③ 你有没有加一个**搜不到任何东西**的 `keyword`（⭐ `keyword` **只能按订单号搜**，§3.3）；
   ④ 你是不是只看第 1 页（§3.5 要求**全量翻页**）。
10. ⚠️ **"改状态成功了，但状态没变"**：检查你是不是**同一个 `Idempotency-Key`**重发了
    （那会回放**上一次**的响应，§2.1）⇒ 每次写动作请用**新的随机键**，只有"重试同一笔"
    才沿用旧键。
11. ⚠️ **进度图认领总回 `1000`「没有待认领的上传记录」**：核 ① 你认领用的 `key` 是不是
    **同一张票**回给你的那个（⛔ 别自己拼）；② 票过期了没有（§7.2 的 `expires_in`）；
    ③ 两次调用（取票 / 认领）用的是**同一把凭据**（换凭据 = 换了人）。
12. ⚠️ 分辨"我这边的问题"与"对方的问题"：**拿 §10 的 `call_api()` 打一次 §3 的读端点**
    （最省事的一条是 `GET /api/taker/v1/hall/?page=1&page_size=1`）：它通了说明认证与网络
    都没问题，再把问题收敛到具体的写端点 / 参数上。
13. ⚠️ **"配了回调，但一条推送都没收到"**：按这个顺序核（§12）——
    ① 那次变化是**他当前接手的单**的吗？（⛔ 大厅来了新单**不推**、别人接的单**不推**，§12.1）；
    ② 应用是不是**被停用**了、回调开关是不是**关着**、地址是不是**空的**？（三条缺一不可，§12.1）；
    ③ 地址是不是 **https + 公网**、有没有带用户名密码、有没有超 **200 字符**？（§12.7）；
    ④ 是不是**刚发生**的？投递进程**每 10 秒**跑一轮（§12.8），别把"还没到"当"没推"；
    ⑤ 去**台账页**看那一行的状态与 `reason`（失败会退避重试，第 7 次才落终态 `failed`，§12.4）。
14. ⚠️ **"收到了推送，但验签失败"**：核 §12.3 那六条 ——
    ① 是不是拿"原始字节截掉 sign"去算的（⛔ 错法，必须解析后**重新规范化**）；
    ② 规范化的三条 flag 少没少（`ensure_ascii=False` / `sort_keys=True` / `separators=(",", ":")`）；
    ③ 待签串是不是 `timestamp` → `delivery_id` → `sha256` 小写 hex、用 `\n` 连接、末尾**没有**多一个 `\n`；
    ④ HMAC 的密钥是不是 `app_secret`（⛔ 不是 `app_key`）。

## 12. 回调推送（我们主动推给你）

⭐ **第二期（2026-10-09）新增**。第一版**没有**推送 —— §0.1 第 1 条与 §9.2 的原句都按
「只增不改」**逐字保留**，**改准块就写在那两处**。现在**有**了，但**范围很窄**：

> ⭐ **只推「他当前接手的单」的变化**；⛔ **大厅里来了新单不推**（那一条仍然只能靠**轮询**，§3.5）。

⭐ **本节是完整契约**：什么时候推 / 报文长什么样 / 签名怎么算 / 期望什么回执 / 失败怎么重试 /
「至少一次」怎么处理 / 地址有什么要求。**这是本侧唯一需要你自己实现签名的地方**。

⚠️⭐ **本章编号排在最后（§12）是有意的**：§1–§11 的编号**已经是对外契约的一部分**了
（第三方的对接代码、页内那份目录、以及本文档里那几百处 `§x.y` 交叉引用都按它指认）
⇒ 新增的一章一律**追加**，⛔ **不重排既有编号**（重排会把别人的引用**静默**指到别处）。

⚠️ 与**上家侧**那份文档（`docs/OPEN-API.md` §5）的关系：**签名算法、三个请求头、退避表、
「2xx 才算成功」、「至少一次」这五样是同一套契约**（两族共用同一份实现，⛔ 不是两份）；
**不一样的是收件人语义与事件集合** —— 那边**一个应用 = 整个租户**、**没有** `order.reassigned`；
这边**一个应用 = 一个打手账号**、**多一个** `order.reassigned`（§12.1）。⛔ 别把两份文档的事件表混着读。

### 12.1 什么时候推、推哪四类事件

推送的**前提**（三个条件同时成立）：那个应用 `state=enabled`（应用没被停用）、
`callback_state=enabled`（回调开关是开的）、`callback_url` 非空（§1.2 的应用行载荷里就是这三格）。
⇒ 三个条件任一不成立 ⇒ **根本不会产生推送**（⛔ 不会给你报错，也不会排队等你）。

⭐ **收件人 = 「绑定账号 == 这张单的当前接手人」的那个应用**（⚠️ 与上家侧**最大的差别**）：

- 这张单**不是他接的**（还在厅里 / 别人接了 / 已经换给别人）⇒ **不会推给他**；
- 这张单**没人接**（孤儿单 / 接手人是空）⇒ **一个收件人都没有**
  （⛔ **不会**退化成"推给这个租户的全部打手应用"）；
- 一个打手名下有**多个**应用 ⇒ **每一个都各收到一份**（各自的去重身份 `delivery_id` 不同）。

| `event` | 什么时候推 | 多带的字段 |
|---|---|---|
| `order.status_changed` | **他接的单**状态发生变化（含他自己通过 §6 改的、以及租户在页面上改的） | `status`、`note` |
| `order.deleted` | **他接的单**被删除（软删） | 无（报文里就是 §12.2 那 8 个业务键里的 4 个 + `timestamp` + `sign`） |
| `order.image_added` | **他接的单**新增一张进度图（**认领成功后**，含通过 §7 认领的） | `images`（一张列表，见 §12.6） |
| ⭐ `order.reassigned` | ⭐ **这张单不再是他的了**：换人 / 清接手人 / 撤单回池 / 退单 / 删单 | `reason`（机器可读，见 §12.2.3） |

⭐ **`order.reassigned` 是本侧独有的事件**（上家侧那份文档里没有），用途很直接：
**让你停止在这张单上继续干活**（§12.8）。它推给**前任**接手人名下的应用 —— 那一刻库里
"当前接手人"已经是别人、或者已经清空了。

⚠️⭐ **`order.reassigned` 与 `order.deleted` 可能同时到**（同一张单被删时）—— **这是有意的**，
⛔ **不是重复**：`order.deleted` 说的是"这张单不存在了"，`order.reassigned(reason=deleted)`
说的是"你不该再干它了"。两句对着**同一张单**都成立，请**各按各的语义**处理。

⛔⭐ **大厅里来了新单，我们不推**（业务方 2026-10-09 裁定）：想第一时间知道"有新单可抢"，
仍然只能**轮询** `GET /api/taker/v1/hall/`（§3.5 的镜像对账法）。**这一条没有放松**。

⚠️ **入队前的去重**：`order.status_changed` / `order.image_added` / `order.deleted` 三类，
我方在**入队前**按（应用 + 事件 + 订单号 + 身份值）与你**最近一条**比过去重
（同一状态连着两次、同一张图**不会**连着推两条）。
⚠️ 但 ⭐ **`order.reassigned` 不去重**：同一张单、同一个 `reason` 连着来两次**会各推一条**
—— 语义上「每一次『不再是你的了』都是一个新事件」（换人 → 又换回来 → 再换人，你该收到两次）。
⚠️ 而 **「至少一次」永远成立**（自动重投 ＋ 手工重投）⇒ 无论哪一类，**都请按 §12.5 去重**。

⚠️ **顺序**：**同一订单**按产生顺序推送（前一条还没投出去时，后一条会等）；
**不同订单之间不保证顺序**；同一张单在同一个应用上只有**一条队列**（多应用各一条）。

### 12.2 报文字段（逐字段）

`POST` 到你的 `callback_url`，`Content-Type: application/json; charset=utf-8`。
以 `order.status_changed` 为例（**这个例子里的值都是合成值**，也是 §12.3 的签名示例）：

```json
{
  "event": "order.status_changed",
  "delivery_id": "9a1b2c3d4e5f60718293a4b5c6d7e8f9",
  "order_no": "20261008000000000077",
  "source_order_no": "SYN-2026-0007",
  "status": "IN_PROGRESS",
  "note": "",
  "occurred_at": "2026-10-08T12:00:00+08:00",
  "timestamp": 1760000000,
  "sign": "2d3b602594aae9f2f5247d6812584d6818826224b240afc54cab41f56278869d"
}
```

⚠️ **报文里的键序不重要**：`sign` 盖的是**规范化之后**的字节（§12.3），⛔ 不是"你收到的原始字节"。

#### 12.2.1 业务字段（8 个键：**每一类事件带其中一部分**）

| 键 | 类型 | 说明 |
|---|---|---|
| `event` | string | 事件名，**四类之一**（§12.1）。⚠️ 请按它分派，⛔ 别按"哪个键在不在"猜 |
| `delivery_id` | string | ⭐ **这一条推送的去重身份**（32 位小写十六进制）。**同一条推送的每一次重投都沿用同一颗**（§12.5） |
| `order_no` | string | 团团通订单号 |
| `source_order_no` | string | 来源单号（**你自己的**单号）。⚠️ 没有时是**空串**（⛔ 不是 `null`） |
| `status` | string | 目标状态码（**只有** `order.status_changed` 带；取值同 §6.2 那张白名单 ＋ 团团通那边自己推的那几档） |
| `note` | string | 备注（**只有** `order.status_changed` 带；本批恒为**空串**，⛔ 但**键一定在**） |
| `images` | array | 进度图列表（**只有** `order.image_added` 带，见 §12.6）。每项恰好三键 `{"url", "img_type", "remark"}` |
| `occurred_at` | string | 业务事件**发生的时刻**（ISO 8601，带时区偏移）。⚠️ 与 `timestamp` **不是**同一个时刻（见 §12.2.4） |

#### 12.2.2 投递时现算的两键（**每一类**事件都有）

| 键 | 类型 | 说明 |
|---|---|---|
| `timestamp` | integer | ⭐ **这一条推送发出的时刻**（UTC Unix 秒）。它参与签名（§12.3） |
| `sign` | string | ⭐ 签名（小写 hex，64 位）。**它盖住的是"去掉 `sign` 之后的整个报文"**（含 `timestamp`） |

#### 12.2.3 `order.reassigned` 多的那一键：`reason`

| 键 | 类型 | 说明 |
|---|---|---|
| `reason` | string | ⭐ **机器可读**的原因，**恰好三个取值之一**：`taker_removed`（换人 / 清接手人 / 撤单回池）/ `refunded`（退单）/ `deleted`（删单）。⚠️ 请按它分派（要不要清掉自己那边的工单 / 要不要通知客服），⛔ **别按中文描述猜** |

#### 12.2.4 `occurred_at` 与 `timestamp` 是两件事

- `occurred_at` = "**这张单什么时候变的**"（我们业务写入那一刻）；
- `timestamp` = "**我们什么时候发的**"（签名覆盖它，也是你判新鲜度的依据）。

⚠️ **`timestamp` 与 `sign` 都是投递那一刻现算的**：同一条推送重投时**两个都会变**，
`delivery_id` ⛔ **不变** ⇒ 请用 `timestamp` 判新鲜、用 `delivery_id` 判重复（§12.5）。

### 12.3 签名算法与三个请求头（**逐字冻结**）

```
body_without_sign = 收到的报文 JSON 里**去掉 "sign" 键**之后的那份对象（timestamp **在**里面）
canonical         = json.dumps(body_without_sign, ensure_ascii=False, sort_keys=True,
                               separators=(",", ":")) 的 UTF-8 字节
sign              = HMAC-SHA256(key = app_secret, msg = f"{timestamp}\n{delivery_id}\n"
                                                     f"{sha256(canonical).hexdigest()}") 的 hex（小写）
```

请求头（三个，**逐字**）：

```
X-TT-Timestamp: <Unix 秒，十进制整数，与报文里的 timestamp 同一个值>
X-TT-Delivery:  <delivery_id，与报文里的同一个值>
X-TT-Signature: <sign，与报文里的同一个值>
```

**逐条钉死（⚠️ 这几条每一条都会让"双方各自写对了却验不通"）：**

1. ⭐ **`sha256` 盖的是"规范化之后的字节"**，而规范化的口径就是上面那三条
   （`ensure_ascii=False` + `sort_keys=True` + `separators=(",", ":")`）—— **缺一不可**。
   ⇒ 你**复算**的正确姿势是：**解析收到的 JSON → 去掉 `sign` → 用同一套规范化重新序列化
   → `sha256(...).hexdigest()`**。⛔ **不要**直接对"收到的原始字节里截掉 sign 那段"算摘要
   （你截不准，而且键序 / 空白 / 转义都会影响字节）。
2. ⭐ **待签串是三步、用 `\n` 连接**（`timestamp` → `delivery_id` → `sha256` 的小写 hex），
   ⛔ **顺序不能换**、⛔ **末尾不额外加 `\n`**。`timestamp` 用**十进制整数的规范写法**
   （`1760000000`，⛔ 无前导零、⛔ 不带小数、⛔ 不是毫秒）。
3. ⭐ **HMAC 的密钥是 `app_secret` 的 UTF-8 字节**（⛔ 不是 `app_key`），签名 hex **小写**。
4. ⭐ **`sign` 自己不在被签的内容里**：算的时候把它去掉，比的时候用 `hmac.compare_digest`
   这类**常量时间**比较（⛔ 别用 `==` 拼字符串比较）。
5. ⚠️ **`sha256` 只是把变长报文折成定长**，⛔ 它**不是**"防篡改"（防篡改由外层 HMAC 负责）。
6. ⚠️ 请按**收到的原始 `body` 字节**解析 JSON 后再复算，⛔ 不要"先改成自己的结构体再
   序列化回去"（多一个键、少一个键、换个键序都验不过）。

**验证一条回调的标准步骤：**

1. 逐个校验三个头都在（缺任何一个 ⇒ 记一条日志并回 4xx，见 §12.4）；
2. 解析报文，取 `delivery_id` / `timestamp` / `sign`；
3. 按上面那三条规范化 + 算待签串 + HMAC，与报文里的 `sign` 做**常量时间比较**；
4. ⭐ **按 `delivery_id` 去重**（§12.5）—— **这一步在验签之后、处理业务之前**；
5. 处理业务（幂等！你的处理也要能被重放），然后回 **2xx**。

⚠️ **时间窗（可选）**：本契约**不强制**你校验 `timestamp` 的新鲜度
（我们不承诺一个固定的窗口，重投可能发生在 `occurred_at` 之后很久）。
如果你要防重放，可以用"收到的 `timestamp` 与你的本地时钟差超过某个阈值就拒"，
但请把阈值放宽到**至少几小时**（重投最多跨约 7.5 小时，见 §12.4），
并且**在那之前先按 `delivery_id` 去重** —— 否则你会把一次正常的重投判成攻击。

```
import hashlib
import hmac
import json

# ── §12.3.1 的合成夹具（⛔ 不是任何真实应用的密钥 / 订单）────────────────────
FIXTURE_APP_SECRET = "taker-doc-synthetic-secret-0001"
FIXTURE_TIMESTAMP = 1760000000
FIXTURE_DELIVERY_ID = "9a1b2c3d4e5f60718293a4b5c6d7e8f9"

#: 收到的那一条报文（§12.2 的例子，逐字）。
EXAMPLE_PAYLOAD = {
    "event": "order.status_changed",
    "delivery_id": "9a1b2c3d4e5f60718293a4b5c6d7e8f9",
    "order_no": "20261008000000000077",
    "source_order_no": "SYN-2026-0007",
    "status": "IN_PROGRESS",
    "note": "",
    "occurred_at": "2026-10-08T12:00:00+08:00",
    "timestamp": 1760000000,
    "sign": "2d3b602594aae9f2f5247d6812584d6818826224b240afc54cab41f56278869d",
}

#: 同一次投递的三个请求头（§12.3）。
EXAMPLE_HEADERS = {
    "X-TT-Timestamp": str(FIXTURE_TIMESTAMP),
    "X-TT-Delivery": FIXTURE_DELIVERY_ID,
    "X-TT-Signature": EXAMPLE_PAYLOAD["sign"],
}


def canonical_json(body):
    """规范化：三条 flag 缺一不可（§12.3 逐字）。回**字节**，不是字符串。"""
    return json.dumps(
        body, ensure_ascii=False, sort_keys=True, separators=(",", ":")
    ).encode("utf-8")


def sign_for(body_without_sign, *, secret, timestamp, delivery_id):
    """算签名（§12.3 那三行的逐字实现）。"""
    digest = hashlib.sha256(canonical_json(body_without_sign)).hexdigest()
    message = f"{timestamp}\n{delivery_id}\n{digest}".encode("utf-8")
    return hmac.new(secret.encode("utf-8"), message, hashlib.sha256).hexdigest()


def verify_callback(raw_body, headers, app_secret):
    """验一条回调：通过 ⇒ 回解析出来的报文（已去掉 `sign`）；⛔ 不通过 ⇒ 抛 `ValueError`。"""
    body = json.loads(raw_body.decode("utf-8"))
    given = str(body.pop("sign", ""))
    computed = sign_for(
        body,
        secret=app_secret,
        timestamp=headers["X-TT-Timestamp"],
        delivery_id=headers["X-TT-Delivery"],
    )
    if not hmac.compare_digest(computed, given):
        raise ValueError("签名不通过")
    return body


if __name__ == "__main__":
    body_without_sign = {k: v for k, v in EXAMPLE_PAYLOAD.items() if k != "sign"}
    print("sign=" + sign_for(
        body_without_sign, secret=FIXTURE_APP_SECRET,
        timestamp=FIXTURE_TIMESTAMP, delivery_id=FIXTURE_DELIVERY_ID,
    ))
    parsed = verify_callback(
        json.dumps(EXAMPLE_PAYLOAD, ensure_ascii=False).encode("utf-8"),
        EXAMPLE_HEADERS, FIXTURE_APP_SECRET,
    )
    print("event=%s order_no=%s dedup_key=%s" % (
        parsed["event"], parsed["order_no"], EXAMPLE_HEADERS["X-TT-Delivery"],
    ))
```

### 12.4 期望回执与重试退避

- ⭐ **只有 HTTP 2xx 算成功**（3xx / 4xx / 5xx / 超时 / 连不上**全部算失败**）。
  ⚠️ 我方**不跟随重定向**（3xx 一律当失败，⛔ 不会跟着跳到别处）。
- ⚠️ 一次投递的**超时是 10 秒**；我方**只读少量响应体**（最多 2048 字节，读完即弃）。
  ⇒ 请在 10 秒内**尽快**回 2xx（正确的做法是：验签 + 落一条待处理记录 + 立刻回 2xx，
  真正的业务处理放到你自己的队列里）。
- ⭐ **重试退避 10s / 60s / 5m / 15m / 1h / 6h，共 6 次机会**：

| 第几次投递 | 什么时候 |
|---|---|
| 第 1 次（首发） | 事件入队后**立即**（受 §12.8 那条轮询间隔约束） |
| 第 2 次 | 第 1 次失败后 **10 秒** |
| 第 3 次 | **60 秒** |
| 第 4 次 | **5 分钟** |
| 第 5 次 | **15 分钟** |
| 第 6 次 | **1 小时** |
| 第 7 次 | **6 小时** |

⇒ **首发 + 6 次重投 = 一次事件最多 7 次 HTTP 尝试**（跨度约 7.5 小时）。
⭐ **六档全部可达**：第 1–6 次失败各取一档（含最后那档 `6h`），**第 7 次仍然失败**才落终态
`failed`（⚠️ 台账里那行会**保留**，租户可以在页面上看到原因并**手工重投**，§12.9）。
- ⚠️ **回执码会被记下来**：请回一个**有意义的** 2xx（200 / 204 都行），
  ⛔ 不要回 200 之后再在响应体里写错误（我方**不看响应体**判成败，只看状态码）。
- ⚠️ **回调地址不合法（非 https / 解析到内网）时也走退避重试**（不是立刻放弃，也⛔ 不是"跳过不记"）：
  地址是**你自己**的域名，DNS 是可变的，"这次解析到内网"不等于"永远是内网"
  ⇒ 一个**永久**不合法的地址会试满 7 次（约 7.5 小时）才落终态 `failed`，页面上看得见原因。
- ⚠️⭐ **中途关掉推送**：应用被停用 / 回调开关关掉 / 地址被清空 ⇒ 之后**不再产生**新推送
  （入队那一刻就按三条判据挡掉，**没有延迟**）；**已经在队列里**的那些行会在
  **下一轮投递**（≈ 10 秒内，§12.8）落终态 `failed` + 一句人话（⛔ 不是静默丢弃，
  也⛔ 不是一直重试到把别的应用饿死）。⇒ 停用之后**最多一轮**就不再往你那边发东西了。

### 12.5 ⭐「至少一次」⇒ 请按 `X-TT-Delivery` 去重

⭐ **我们的投递语义是"至少一次"（at-least-once）**，⛔ 不是"恰好一次"。具体地说：

- 你**超时没在 10 秒内回**、但**实际上已经收到了**并处理了 ⇒ 我方按失败重投
  ⇒ **你会收到第二次**；
- 我方在落终态那一刻崩了、或你回了 5xx 但其实处理成功了 ⇒ 同样会重投；
- ⭐ **第二条来源 = 租户的「手工重投」**（§12.9）：台账里失败的行可以被手工再投一次
  （⚠️ 重投会让**对方再收到一次**，页面上也写着这句）。
- ⇒ ⭐ **请按 `delivery_id` 去重**：同一颗 `delivery_id` 处理**恰好一次**
  （落一张"已处理的 `delivery_id`"表，或在你自己的业务键上加唯一约束）。
  ⚠️ `delivery_id` 在**同一条推送的每一次重投里都不变**（§12.2.2）—— 那正是给你去重用的；
  ⛔ 别按 `timestamp` 去重（重投会变）、⛔ 也别按 `order_no` + `status` 去重
  （"状态回到同一个值"是合法业务事件，那样会把真事件吃掉）。
- ⚠️ **两个方向都要防**：① 同一条重投 ⇒ 按 `delivery_id` 去重（上面那条）；
  ② 不同的 `delivery_id` 带**相同的业务内容** ⇒ 那是**两次真实事件**，⛔ 不要合并
  （`order.reassigned` 尤其如此，§12.1）。
- ⚠️ 我方的**手工重投只对 `failed` 的行开放**：已成功的行不允许重投
  （那会让你收到两次）。但**退避重试**是自动的 ⇒ "至少一次"仍然成立。

### 12.6 `images` 里给的是预签名 URL（有效期 1–2 小时）

`order.image_added` 的报文里，`images` 是一个列表，每项**恰好三个键**：

```json
{"url": "https://<对象存储域名>/…?X-Amz-…", "img_type": 0, "remark": ""}
```

- ⭐ **`url` 是投递那一刻现场生成的预签名直链，有效期 1–2 小时**（生产对象存储按整点对齐；本机/测试 300 秒）。
  ⇒ 请在**拿到报文后的几秒内**把图**下载到你自己那边**再慢慢处理；
  ⛔ **不要**把它当永久链接存进数据库（过期就失效），⛔ 也不要转发给终端用户长期使用。
- ⚠️ **重投会带着一张新的 `url`**（重新预签，所以每次都可能不同）——
  这也是"⛔ 别按 url 去重"的原因：去重请用 `delivery_id`（§12.5）。
- `img_type` 本批恒为 `0`（订单进度图；`1` = 进群二维码**不会**推给你）。
- `remark` 是上传时填的备注（可能为空串）。

### 12.7 回调地址的要求（仅 https、必须公网）

- ⛔ **只允许 `https`**：`http://` / `ftp://` 等在**保存时**就被拒；
- ⛔ **地址里不许带用户名 / 密码**（`https://user:pass@host/…`）；
- ⛔ **域名必须解析得出来**，且**解析到的每一个地址都必须是公网地址**
  （回环 `127.0.0.0/8`、私网 `10/172.16/192.168`、链路本地 `169.254.0.0/16`、
  CGNAT `100.64/10`、保留段 / 组播 / 未指定一律拒）。
  ⚠️ 这条判据**保存时**与**每次投递前**各跑一次（DNS 是可变的）⇒ 域名被指向内网时推送会
  **失败并重试**（§12.4），而不是"照发"。这也是"内网自建回调本批不支持"的落地方式。
- ⛔ **不跟随重定向**、**10 秒超时**：你的回调地址应当是**直连**的、**快速**回 2xx 的端点。
- ⚠️ **地址长度上限 200 个字符**（与库里那一列同宽）：超了在**保存时**被拒（`1000` 并点名），
  ⛔ 不会静默截断。
- ⚠️ 我方一次投递**只读最多 2048 字节**响应体（读完即弃）⇒ ⛔ 别指望把大量数据放在回执里
  传给我们（要传数据请用你自己的查询接口 / 我方 §2 那些读端点）。
- ⚠️ **回调地址是"每个应用"的**：一个打手名下有多个应用就配多个地址，事件**各发一份**。

### 12.8 ⚠️ 如实说明：推送**不在**你的写事务里（延迟 ≈ 10 秒）

这几条都不是"注意事项"，而是**事实**，请按它们设计你的系统：

1. ⛔⭐ **投递不是事务的一部分**：团团通那边的业务**写库成功 ≠ 已经推给你**
   （入队发生在业务事务里，**HTTP 在事务之后**、由另一个常驻进程发出去）。
   ⇒ ⛔ 别把"对方该收到推送了"当成你自己那边某一步的回执。
2. ⚠️ **推送延迟 ≈ 10 秒**：投递进程**每 10 秒**轮询一次待发行（不是实时推送）。
   ⭐ 也就是说：**你改了状态，对方最多约 10 秒后才看到**；再加上你这边的处理时间。
   ⇒ **轮询仍然是有效的兜底**（尤其是"刚写完就想立刻看到"的场景）。
3. ⚠️ **被换人 / 退单 / 删单时，你应当停止在该单上继续干活** —— 这正是 `order.reassigned`
   的用途（§12.1）。⚠️ 但注意它**也是推送**（同样有约 10 秒延迟、同样可能重试）：
   ⇒ 判"这张单现在还是不是我的"**最终仍以查单（§5.2）为准**，⛔ 别拿"我还没收到
   `order.reassigned`"当"这单还是我的"。
4. ⛔ **大厅里来了新单不推**（§12.1）：要第一时间知道有新单可抢，**只能轮询**（§3.5）。
5. ⚠️ **推送失败不影响你的业务**：对方长时间不可达时，事件最多延后约 7.5 小时才落终态
   `failed`（§12.4），而那期间**你的 API 调用一切照旧**（两条通道互不影响）。

### 12.9 怎么配置、怎么看台账、怎么手工重投

⭐ **配置**（调用方是**租户自己**，用的是网页 / 会话，⛔ 不是你这把 Bearer 令牌）：

- 在【开放平台】→「**打手对接**」页面上：建应用时就能填**回调地址**（还可以顺手打开
  **回调开关**），建好之后在那张表的行内动作里随时改；

- ⚠️ 地址合不合法**由后端判**（§12.7），页面上**没有**前端校验门 ⇒ 填错了会拿到 `1000` 并点名。

⭐ **看台账 / 手工重投**（同上，租户自己用页面）：

- 台账页可以看到**最近推送**（每行含事件名 / 订单号 / 状态 / 尝试次数 / 对方回执码 / 失败原因）；
- **失败（`failed`）的行可以手工重投** —— ⚠️ 重投会让**对方再收到一次**
  （`delivery_id` **不变** ⇒ 请按 §12.5 去重）；**已成功**的行**不允许**重投。
