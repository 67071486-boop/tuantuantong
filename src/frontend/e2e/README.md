# 端到端测试（E2E）——真浏览器 + 真后端 + 真库

## 一句话

这是本仓的**回归网**：用真的 Chromium 打开真的前端、连真的后端和真的数据库，跑一条完整的订单业务链（登录 → 录单 → 抛单 → 抢单 → 改价 → 指派 → 完成 → 结账 → 退款），再验三条越权红线，最后把全站每个能打开的页面逐个打开一遍看它崩没崩。

一条命令：

```bash
cd src/frontend && pnpm e2e
```

这条命令按固定顺序做三件事，任何一步失败都会**响亮停住**、不会带着半套数据往下跑：

1. **确保租户在**（`node e2e/lib/tenant.mjs` 的 `ensureTenant()`，幂等：已在且能连上就跳过，不会重建）；
2. **灌业务夹具**（`manage.py seed_e2e`，幂等）；
3. **跑 Playwright**（`e2e/playwright.config.ts`）。

> 顺序为什么要写在一个 Node 脚本里、而不放进 Playwright 的 `globalSetup`：Playwright 会**先起 `webServer`、再跑 `globalSetup`**（本线读过 1.63.0 的源码，见设计文档 §1.1-1）⇒ 若把「灌数据」放进 `globalSetup`，后端起来时连的还是**还没灌数据的库**。所以排序由 `e2e/run.mjs` 控制，不交给框架。

跑单个用例（例如只跑主干）：

```bash
cd src/frontend && pnpm e2e --grep "订单主干"
```

⛔ **不要写 `pnpm e2e -- --grep …`**。那个裸 `--` 会被 Playwright 当成「选项到此为止」的终止符，后面的 `--grep` 变成没人看的位置参数 ⇒ **整套照跑**（实测，见 `docs/ERRORS.md` 的 **E-0083**）。调单个用例时看着像「grep 没生效」，其实是你多打了一个 `--`。

只想看界面、**不想每次重灌数据**时用：

```bash
cd src/frontend && pnpm e2e:headed --grep "连通性"
```

`e2e:headed` 是**直连** Playwright 的（不经过 `run.mjs`），所以它**不**保证租户与数据是最新的——调试用，别拿它当回归。

## 在隔离工作区（worktree）里跑

**一句话**：worktree 的「仓库根」是**它自己**，而 `.tools/` 不进 git ⇒ 它里面**一样都没有**。E2E 要用的 `uv`、缓存目录、Chromium、租户凭据全在主检出那边，**不借过来就会「一条命令跑不起来，还看不到任何错误」**。

### 症状：报「未就绪（）」，而且没有任何错误输出

```text
ℹ️  E2E 租户未就绪（）⇒ 开始供给
⛔ 供给失败。若提示角色已存在，说明库里已有一份凭据而我们不知道它的密码：
   …（后面是那条让人去加 --rotate-password 的建议）
```

⚠️ **最后那句是误导**：这个库里根本没有 E2E 租户的角色，`--rotate-password` 治不了这个病（它印出的命令用的还是同一个起不来的 `uv`，照着抄也跑不起来）。

⭐ **真正的信号是括号里空着**——真「没租户 / 凭据坏」时括号里一定有字（`凭据文件不存在或缺少 DB/USER`，或 `库连上了，但目录行（Tenant/Domain）缺失`）。**空的括号 = 探针进程根本没起来。**

### 真因（四条，逐条实测）

1. **`uv` 是「仓库里有就用、没有就回落成裸命令」**：`e2e/config.mjs` 的 `UV_BIN`（第 34–36 行）先看 `<仓库根>/.tools/bin/uv` 在不在，不在就回落成裸命令 `uv`；而**本机 `uv` 不在 `PATH`**（`which uv` 什么都不输出）。
2. **worktree 里没有 `.tools/`**（它不进 git）⇒ 上面那个判断落空 ⇒ 回落到裸 `uv` ⇒ 子进程**起不来**（`ENOENT`）。
3. **`ensureTenant()` 没检查 `spawnSync` 的 `r.error`**（`e2e/lib/tenant.mjs` 第 37–44 行）：进程起不来时 `status === null`、`stdout` / `stderr` 都是空的 ⇒ 拼出来的原因串是**空串** ⇒ 打出「未就绪（）」，然后走进「去供给」的分支；那一步同样是 `spawnSync`、同样起不来，于是**还是没有任何输出地失败**，只在最后留下那句「角色已存在」的误导建议。
4. **同一个原因还殃及另外两条路径**：`UV_CACHE_DIR`（`config.mjs` 第 39 行 → `<仓库根>/.tools/cache`）与 `BROWSERS_PATH`（第 43 行 → `<仓库根>/.tools/ms-playwright`）也指向**不存在**的目录。

### 补法：从主检出借四样东西

```bash
cd "$(git rev-parse --show-toplevel)"                            # 站在 worktree 根
MAIN=$(git worktree list --porcelain | awk 'NR==1{print $2}')   # 输出第一行就是主检出

mkdir -p .tools/e2e                                              # .tools 本身也不进 git，先建出来

ln -s "$MAIN/.tools/bin"           .tools/bin                    # ① uv 可执行文件
ln -s "$MAIN/.tools/cache"         .tools/cache                  # ② uv 缓存目录
ln -s "$MAIN/.tools/ms-playwright" .tools/ms-playwright          # ③ Chromium（Playwright 浏览器）
cp "$MAIN/.tools/e2e/tenant.env"   .tools/e2e/tenant.env         # ④ E2E 专用租户凭据（0600，不进 git）
```

- ①–③ 建好后，`config.mjs` 那三处「仓库内有就用」的默认值就都命中真目录了 ⇒ 真因里的第 2–4 条一起消失。
- ④ **不能省**：worktree 之间**不共享**凭据文件。若主检出那边也还没有（从没跑过 E2E），先在主检出跑一次、或在主检出按供给失败提示重跑一次供给，再回来复制。
- 不想软链也行：给 `UV_BIN` / `UV_CACHE_DIR` / `PLAYWRIGHT_BROWSERS_PATH` 三个环境变量指主检出的路径即可；但那要每次打一长串，软链是一次性的。

### 30 秒判据：分清「真没租户」和「进程没起来」

```bash
which uv                           # 本机什么都不输出 ⇒ 裸命令必然起不来
ls -l .tools/bin/uv                # 看不到 = 没补；看到指向主检出的软链 = 已补
.tools/bin/uv --version            # 打印版本号 = 软链是好的；报 No such file or directory = 软链缺了
lsof -nP -iTCP:8010 -sTCP:LISTEN   # 跑的过程中看后端有没有真的起来过；没有监听 = 编排器早死了
```

把两条摆一起看：**括号是空的** ⇒ 进程没起来（先查 `.tools/`）；**括号里有字** ⇒ 真的是租户 / 凭据问题（按下面「常见失败怎么查」处理）。

## 它连的是哪个库

**默认（读模式）连 `tt_e2e`**——专为本套 E2E 建的只读租户库；**只有**显式开写模式（`TT_E2E_WRITE=1`）
才改连**`tt_e2e_write`**（一次性写租户，**每次跑前推倒重建**，见下节「写模式」）：

| 模式 | 租户 schema | 域名 | 数据库 | 凭据文件 |
|---|---|---|---|---|
| 默认（读模式） | `e2e` | `e2e.test.local` | `tt_e2e` | `<仓库根>/.tools/e2e/tenant.env`（0600，不进 git） |
| 写模式（`TT_E2E_WRITE=1`） | `e2e_write` | `e2e-write.test.local` | `tt_e2e_write` | `<仓库根>/.tools/e2e/tenant-write.env`（0600，不进 git） |

⛔ **绝不碰 `tt_dev`**（日常开发库）。这条不是靠自觉：`e2e/playwright.config.ts` 在**把凭据灌进后端进程的那一处**按**本轮模式**判「库名必须**逐字**等于该模式的库（读 = `tt_e2e`、写 = `tt_e2e_write`）」，不相等就抛。

⛔ 破坏性用例（退款 / 删单）**只在这个专用库里做**。这个租户里的数据会随跑的次数累积（订单越来越多），那是有意的：主干用例按**订单号**定位自己那一行，不依赖「新单在列表第一页」。

## 它用哪些端口

| 服务 | 端口 | 为什么不能用别的 |
|---|---|---|
| 后端（Django `runserver --noreload`） | **8010** | `8000` 是开发服务，可能正被别的会话用着 |
| 前端（Vite，`e2e/server/vite.e2e.config.ts`） | **5273** | `5173` 同理 |

两个服务都只监听 `127.0.0.1`。配置里 `reuseExistingServer: false` 是**故意的**：8010/5273 上如果已经有别人（或上一次的残留）在跑，宁可**响亮失败**，也不要用错的那个服务去跑测试。

⛔ **不 kill、不占用** `8000` / `5173`。

## 判据口径：什么算红、什么只记录

| 类别 | 处置 |
|---|---|
| `pageerror`（页面里未捕获的 JS 异常） | **红** |
| HTTP ≥ 500 | **红** |
| 主干 / 越权的断言不符 | **红** |
| HTTP 4xx（含未登录的 401） | **只记录，不红** |
| 浏览器控制台里的 error 日志 | **只记录，不红** |
| island iframe **没挂载**，或 iframe 内 `#app` **一个元素子节点都没有** | **红** |

- 最后那条刻意只有两个**机械**条件，不设「内容够不够多」这类人为阈值——否则第一天就要为阈值吵架。
- 「只记录、不红」的那两类会进**冒烟体检表**（`smoke-report.json`），用来回答「哪一页在打自己没权限的接口」，但**不**用来判失败。
- 豁免 / 白名单必须**显式枚举**（写死哪一条），⛔ **禁止**用「理由文本里含某个词」当后门——那等于永久豁免。

### 写这条线上的用例时的两条硬要求

这两条是**本线实测踩出来的**（详见 `docs/ERRORS.md` 的 **E-0083**），新增 / 修改用例时必须遵守：

1. **比对文本时，两侧的归一化必须一致。** 要么都去掉空白、要么都用原文；⛔ 不能**一边删、一边不删**。
   反例（本线真实踩过）：哨兵 `'未登记的 island 页面'` **含空格**，而比对前把页面文本 `replace(/\s+/g,'')`
   删了空白 ⇒ 这条判据**永远不命中、不可能红**，但它看起来和一条有效判据**一模一样地绿**。
2. **做「弄红」对照（变异）时，只能改行为，⛔ 不能连期望一起改。** 行为与期望一起改的变异**自己跟自己自洽**，
   原则上**检不出**——它会给你一个假的安全感（本线实测：第一次变异写成 `= ACCOUNTS.admin`，用例仍然绿）。

### ⚠️ 这套网**做不到**什么（大白话，别误解）

**冒烟那部分只负责「把页面打开、看它崩不崩」，它不会去点页面里的按钮。** 所以——

> **一个页面「看起来渲染得好好的、但按钮点了没反应」，这套网是抓不到的。**

那不是漏做，是有意的边界：本线只做「打开不崩」这一层。要抓「点了没反应」，得另外写**驱动真交互**的用例（本仓已有先例：`.agents/notes/implemented/bug-fix/2026-09-24-island-layer-reentrancy-flag-sticky.md` 记的那条「新增游戏成功后再点确定没反应」，就是一条**页内驱动真交互**的用例抓到的，不是靠这套冒烟）。

另外两条已知边界：

- **壳页（1:1 复刻页）与真功能页用的是同一套判据**（都只断言「不崩」）。所以一页写着「尚未开放」**不算红**——「这页到底能不能用」需要另一张对照表，不在本套范围内。
- 登录态下仍然出现大量 **401**，本套只**记录**、不当成 bug 结论：要下结论得先跑一个「这个请求该不该由这个角色发出」的对照。

## 职位对拍（这张网怎么跑、要跑多久、边界在哪）

**一句话**：它按**职位**（系统管理员 + 客服 / 客服主管 / 代练员 / 系统开发员 + **最小权限** + **客服（单游戏）**）把菜单里**看得见**的页都走一遍，
再把页内的按钮**真的点一遍**，只记「点击触发的 `/api/**` **GET 403**」；已知的几条冻在基线里——
**新 403 红、基线里不再复现的（陈旧）也红**。⚠️ **基线今天为空**（`D-0146` 修好 `D-0145` 的名单端点后，
那两条按「陈旧必须红」的纪律删掉了，见 spec §12.6）。判据本体与设计取舍见
`docs/specs/2026-09-24-role-promise-audit-design.md`（下称 spec），本节只讲**怎么跑 + 边界**。

> **第 6 个职位「最小权限」（`minrole`，2026-09-25/26 最小权限角色线新增）**：一条**自定义 RBAC 角色**
> （⛔ 不是内置组预设），节点集**显式枚举、只给 `order.list`** ⇒ 它只看得见 `/` 与 `/orders`。
> 它补的正是本网此前缺的维度：内置预设按**栏目批发**节点，而「看得见但用不了」这类缺陷恰好集中在
> **某些节点没有**的角色上（本线一跑就点出 5 条，全在 `/orders`，已按 `D-0154` 同一原则修完）。
> 判据本体与实测见 `docs/specs/2026-09-25-minimal-role-audit-design.md`。
> **⭐ 评审修复波（2026-09-26）**：把 `/orders` 剩下的三处入口也按节点收口
> （「编辑订单」的门改取弹层第一发 `GET /orders/<no>/`；`.throwEdit` / `.cancelThrowHome`
> 两颗写入口各按后端那组 any 渲染；工具栏 `setRecMan` 与行内 `.jsr` 同门）
> ⇒ `minrole` 读模式整轮候选 **156 → 115**、写模式 **60 → 51**，`findings` 仍 **0**。
> ⚠️ 后两颗是**写路径**，而写模式探针**不填表单**（`submitThrow` 在校验处提前 return）⇒ 网**抓不到**
> 它们，只能靠页测试守（残差登记在 spec §8.7）。

> **第 7 个职位「客服（单游戏）」（`gamescope`，2026-09-26 游戏范围维度线新增）**：节点集与内置「客服」
> **同源**（`seed_e2e._seed_gamescope` 调 `apps/rbac/seed.py::builtin_role_nodes("客服")`），
> 但 `StaffProfile.games` **只挂第 1 款**游戏（`E2E 测试游戏`）⇒ 它补的是本网此前**完全没测过**的一条
> 权限轴：`apps/business/game_scope.py::games_of` 按账号的游戏集收窄。根因是**立线前 E2E 租户只有
> 1 款游戏**，「只给一款」与「给全部」在库里是同一种状态 ⇒ 本线先幂等建出**第 2 款**
> （`E2E 测试游戏乙`），这两种范围才**可分辨**。
> **实测（整轮）**：`reachable` / `menuVisible` **13 = 13**、`onlyVisible` / `onlyReachable` 全空、
> `findings` **0**、候选 **317**、层内 **6**、实例化页 **4** —— 与 `cs` **逐项一致**。
> ⛔ **别把"它看到的行数更少"当成这条轴被验证过的证据**：`cs001` 本身也只挂第 1 款、且租户里的订单
> **全在第 1 款上**（第 2 款一笔订单都没有）⇒ 今天`gamescope` / `cs` / `supervisor` 三者的行数必然相同。

### 怎么跑

| 想干什么 | 命令（在 `src/frontend` 下） | 实测耗时 |
|---|---|---|
| 只跑这条线（**7** 个职位 + 11 条收集期结构钉子） | `node e2e/run.mjs --grep "职位"`（等价 `pnpm e2e --grep "职位"`） | **18 分 00 秒（1080s）**，`18 passed`（含起后端 / 前端 / 灌夹具；**游戏范围维度线**实测，7 个职位 + 11 条结构钉子）。⚠️ 扩张到 6 个职位时是 **15 分 36 秒**（任务书里的对照是 **15 分 39 秒**）、5 个职位时 **11 分 02 秒**、层内扩张后 **14 分 49 秒**；多出的约 2.4 分钟 = 新角色那一行自己的 **2.3 分** |
| 只跑**一个**职位 | `node e2e/run.mjs --grep "职位对拍 cs"`（把 `cs` 换成 `admin` / `supervisor` / `taker` / `dev` / `minrole` / `gamescope`） | 客服 **1 分 35 秒**；`minrole` **约 1 分 0 秒**；`gamescope` **2.3 分**；`admin` 最慢——整轮里它这一条用例就 **7.8 分钟**（单独跑还要加约 40 秒起服务 / 灌夹具） |
| 只想跑**快**的那部分（跳过职位对拍） | `pnpm e2e --grep-invert "职位"` | 实测收集到 **74 条**：只跑 `00`–`04`（冒烟最慢）；`05` 里 **0 条**——收口轮把最后 4 条收集期钉子也改名成含「职位」，它们已跟着 `--grep "职位"` 跑 |
| 只跑这条线（**写模式**，一次性写租户） | `TT_E2E_WRITE=1 node e2e/run.mjs --grep "职位"` | 整轮 **15 分 12 秒**（T2b 实测，`15 passed`；同一轮**读模式**是 **14 分 54 秒**，见 spec §8.2）。⚠️ 写模式每跑一个职位前**重置一次**写租户，所以比读模式多花重置的时间 |

- ⛔ **不要写 `pnpm e2e -- --grep …`**：裸 `--` 是 Playwright 的选项终止符，后面的 `--grep` 会被当成位置参数
  **忽略**、整套照跑（实测，见 `docs/ERRORS.md` 的 **E-0083**）。
- `--grep-invert` 是**命令行开关**（显式写在你敲的那条命令里）；⛔ 不许把它做成

### 它判什么

- **看得见 ⇒ 必须用得了**：对每个职位各算两列——`reachable(R)`（逐条导航候选路由、**没被弹回 `/`** 的）
  与 `menuVisible(R)`（在 `/` 上读**渲染出来的**菜单）。判据两条：`onlyVisible` 必须**空**；
  `onlyReachable` **只允许**是 `menu.ts` 里**有意隐藏**的那些（隐藏集合从 `menu.ts` 推导，
  ⛔ 不是把某次跑出来的路径写死成白名单）。
- **控件层**：`reachable` 里每一页的页内控件逐个**真实点击**，把这次点击触发的 `/api/** GET 403` 记进
  `findings`（判据本体 = **职位 R + 页面 P + 控件 C ⇒ 一个 403**）。⛔ 「有 403 就报红」不成立——
  已知缺陷摆在那里，那样这条线从第一天就是红的。
- **基线**：`e2e/fixtures/role-audit-baseline.ts` 冻结**已知且已登记**的 403（每条**必须**带 `D-01xx` 编号）。
  跑出来 == 基线 ⇒ 绿；出现**基线之外**的 403 ⇒ 红；**基线里不再复现** ⇒ 也红（文案「基线陈旧，若缺陷已修，
  请删掉这一条」）⇒ **修好缺陷的人会被这张网逼着把基线删掉**，基线因此只会缩。
  ⚠️ **今天为空**（`D-0146` 修好 `D-0145` 的名单端点后，两条基线按上面这条纪律删掉了，见 spec §12.6）。
  ⚠️ 覆盖判据是**URL 级**的：同一个控件上的**每一条** 403 URL 都必须被某条基线条目覆盖，多出一条没被覆盖的
  （例如控件没变、端点换了）⇒ 判 `extra` 并**点名是哪条 URL**（⛔ 不会被"另一条 URL 命中了"静默吸收）。
- **覆盖率网自己的钉子**（每条都有一次「弄红」证明，原始输出见 spec §12）：N1 正对照（403 观测器接没接上）、
  N3（有候选的页至少点过一次）、N3′（每个职位枚举到的候选总数 ≥ 一个有余量的**外部常量**）、
  「每条可驱动候选都要有归属」（点过 / 去重记账，⛔ 不许静默少点）。
- **参数化详情页：`instancePageUnreachable`（记录、不判红；2026-09-26 控制方裁定 a 新增）**——
  实例**解析到了**、但导航该页被路由守卫**弹回 `/`**（该职位不持这条详情页要求的前置节点，
  例如只给 `order.list` 的「最小权限」角色）。它是**合法的最小权限行为**，⛔ 不是缺陷、也不算覆盖缺失。
  - 入账判据取**导航终态**（`settledPathAtEntry` 逐字等于 `/`），⛔ 不取 `visited`；
    终态去了别处 ⇒ **当场红**（⛔ 不是「万能跳过」后门）。
  - **D2 的「自证不是空转」与 `INSTANTIATED_CANDIDATE_FLOOR` 的 `-1` 哨兵都按「`visited` 的实例化页」取**
    （不再是 `parameterized` 条数）⇒ 本档不会把那两枚钉子误红；两枚钉子的「能红」证明见
    `docs/specs/2026-09-25-minimal-role-audit-design.md` §8.5。

### 写模式（`TT_E2E_WRITE=1`）——唯一允许改数据的一轮

**一句话**：默认那一轮把写请求全**拦断**（审计不是写测试、绝不改数据）；写模式是**唯一的例外**——
它在**一次性写租户** `tt_e2e_write` 上**放行**写，好让「**保存成功之后才出现**」的界面 / 请求进网。
⛔ **只在专用库上开**：写模式会真的建 / 改 / 删数据，⛔ **绝不要**把它指到 `tt_dev` 或任何真实租户上。

- **怎么开**：`TT_E2E_WRITE=1 node e2e/run.mjs --grep "职位"`（或任何 grep）。**不要**手搓
  `TT_E2E_TARGET`——`e2e/playwright.config.ts` 会拒绝「开关与目标不一致」的运行（那是一条会把写请求
  引到只读租户的灾难路径）。`run.mjs` 会先 `reset_e2e_write` **推倒重建**写租户（DROP 库与角色 →
  供给 → 灌夹具），再跑 Playwright。
- **怎么重置**：跑前由 `run.mjs` 重置一次；**每跑一个职位前**再由 spec 调 `resetWriteTenant()` 重置一次
  （写模式会真的删数据，不重置会让后一个职位面对被前一个改烂的租户）。命令本体是
  `manage.py reset_e2e_write`，它**只认库名 `tt_e2e_write`**（⛔ 不接受任何"选目标"的参数），
  且 `DEBUG=false` 时拒跑。
- **三道 fail-closed 闸门**：① 运行器断言凭据里的库名 == `tt_e2e_write`；② spec 在装写策略前断言
  `TT_E2E_TARGET === 'write'`（其余一切取值一律保持拦断）；③ 重置命令只认 `tt_e2e_write`。
- **报告多四个键**：`mode`（`'read'` / `'write'`）、`writesPerformed`（**探针决定放行**的写请求数，
  ⛔ 不等于服务端成功）、`nonGetApiResponses`（**真的收到响应**的非 GET `/api/**` 请求数，排除登录）、
  `resets`；另加**只记录、不判红**的 `writeIssues`（写模式下新出现的非 GET 403 / ≥500）。
- **两条钉子**（都能红）：**W2** = 写模式下 `nonGetApiResponses` 必须 `> 0`（开关真的切到了放行）；
  **W3** = 读模式下 `nonGetApiResponses` 必须 `== 0`（拦断没泄漏进默认模式）。
  ⚠️ W3 的判据是这条**与模式分支无关**的响应观测，⛔ 不是 `writesPerformed`——后者只在写模式分支里
  记账，读模式下恒 0，拿它判 W3 会是一条**永远绿**的钉子。
- **耗时**：整轮实测 **15 分 12 秒**（`15 passed`，比同轮读模式的 **14 分 54 秒**多出「逐职位重置」的钱）。
  ⚠️ **6 个职位后**的实测（最小权限角色线，2026-09-26）：测量轮 **15 分 29 秒（929s）/ `16 passed`**、
  回填后复跑轮 **15 分 57 秒（957s）/ `16 passed`**（见下一条）。
  ⚠️ **7 个职位后本线只做了"单角色写模式测量轮"**（`TT_E2E_WRITE=1 node e2e/run.mjs --grep "职位对拍 gamescope"`，
  **1 passed / 2.3 分**）——⛔ **没有**重跑写模式整轮，所以本行**不给**新的整轮耗时；
  写模式整轮的新数字要等下一个动租户数据形状的线去实测。
- **`gamescope`（客服（单游戏））在写模式下的实测**（2026-09-26，单角色测量轮）：整轮候选 **149**（可驱动 137）/
  层内可驱动 **6** / 实例化页候选 **4**（`/orders/77770000000000000004` 可达）/
  `writesPerformed` **1**、`nonGetApiResponses` **1** / `findings` **0**、**403 / 5xx 0 条**。

### 参数化详情页（`/orders/<20 位单号>` 与 `/system-users/<id>/edit`）

**一句话**：这两类页面**不占菜单位**（从列表点一行进去），而候选路由清单过去把所有含 `:` 的路径整个滤掉
⇒ 它们**从没进过网**。本线用**该职位自己的会话**取一个它看得见的实例、拼成具体路径，**再照旧驱动**
（页内控件 + 一层弹层）。设计与判据见 `docs/specs/2026-09-25-detail-pages-audit-design.md`。

- **登记表是唯一出处**：`e2e/fixtures/routes.ts` 的 `PARAMETERIZED_ROUTES` **显式枚举两条**
  （`pattern` / `routeName` / `detailOf` / `resolve` / `shape`）。⛔ **没有**"任何参数化路由都自动收"
  的通用规则——那会让一条没配父页的新路由静默混进来。模块加载期有一条自检：登记表必须与
  `src/router/index.ts` 里的参数化 path 对得上（每条 declared **恰好**匹配一条 actual；漏登记 /
  多登记 / 名字写错都当场抛）。⚠️ 这里**订正**一个曾经过度的说法（评审修复波第 10② 条）：
  它本来是**覆盖**语义（"至少匹配一条"），现在补成了"恰好一条"才是相等；而 catch-all
  `/:pathMatch(.*)*` 有意在"现实"侧排除 ⇒ 是"排除 catch-all 之后的集合相等"。
- **取实例必须用该职位自己的会话**（`page.request.get`，带 cookie 罐）：⛔ **不许**拿管理员的实例
  硬塞给别的职位——"谁看得见哪一笔"是**数据权限**维度，塞进去会把假象当结论。
- **取不到实例按两类分开**（评审修复波第 3 条；报告里是 `noInstance` 与 `contractBroken` 两栏）：
  - **"没数据"**（HTTP 200 / 业务码 0 / `data.items` 是**空数组** **且** `data.total === 0`）
    ⇒ 记 `noInstance`、**不判红**（数据短缺不是权限缺陷）⇒ **覆盖率与数据相关**，
    ⛔ 别把"某职位没扫到这一页"读成"这一页没问题"。
  - **"解析契约坏"**（网络层失败 / HTTP 非 2xx / 业务码非 0 / 响应缺字段（`data.items` 不是数组）/
    实例不过形状判据 / **翻页元数据 `total > 0` 但列表为空**）⇒ **当场红**，文案点名**哪条路由、
    坏在哪一步、拿到的原值**。
    ⛔ 分这两类的理由：混成一种时，"`resolve` 读错字段名 ⇒ 只剩另一条路由被实例化"会**整轮绿**、
    只留一行 `noInstance`（评审读码推演出的掩盖窗口）。
    ⚠️ **加固（spec §8.9）**：最后那条堵的是**另一个**静默窗口——**取数条件写错**（页码写成
    `page=999`、或多带一个后端会照办的过滤条件）时，端点会**老老实实回一个空列表** ⇒ 原来落进
    `noData`、**永远不红**，而网在这一页的覆盖率**静默归零**。`paginated()`
    （`apps/core/envelope.py`）**恒填** `total` ⇒ "`total > 0` 且列表为空"只可能是取数条件坏。
- **判据②（`onlyReachable ⊆ 有意隐藏的菜单路径`）⛔ 不覆盖参数化详情页**——评审修复波第 2 条：
  本线第一版把它写成 `HIDDEN_MENU_PATHS ∪ 实例化详情页路径`，但 `onlyReachable` 只从 `CANDIDATES`
  派生（61 条、**一条都不含 `:`**）⇒ 与具体详情路径**永不相交**，那个并集**改不了任何一位**（死代码）。
  详情页由 **D1 / D2** 守。⚠️ 这也订正了原文"谁接了参数化路由却忘配 `detailOf`、或父页对该职位
  不可达，判据当场红"——评审推演过：那种情况下**最终仍会红**，但红的是 **D1 的 per-role 那条**，
  **不是判据②**。
- **两枚新钉子（都能红，证明见 spec §8）**：
  - **D1**：① **per-role**：父页可达 ⇒ "取实例"这一步**不许契约坏**（坏 ⇒ 红，文案点名路由 / 步骤 / 原值）；
    若父页可达却零实例、且**每一条都是"没数据"** ⇒ **不判红**（覆盖率与数据相关，spec §2/§6）。
    ② **整轮（`afterAll`）**：只有**本次真的跑了整轮矩阵**（每个职位都写出了行）、且本轮**存在父页可达的
    职位**、而一条实例化页都没解析出来时，才在"本轮出现过契约坏"时分叉为红；全是"没数据"则不判红。
    ⚠️ 整轮那一半的载体是**文件**而不是内存标志（用例失败后 worker 会重启、模块级变量清零）。
    ⚠️ 单跑 `--grep "职位对拍 taker"`（父页都不可达）**不会**假红——这正是修复波第 1 条。
  - **D2**：实例化页面也要**计入候选下界**——`CANDIDATE_FLOOR` 的分子含它们，另有一条
    `INSTANTIATED_CANDIDATE_FLOOR` **单独**钉住实例化页那一份（⛔ 只靠总数的话，"加进清单但不驱动"
    会被 50% 的余量吃掉、静默通过）。`-1` 空位哨兵是**两半**：`parameterized` 为空 **且** 候选数为 0。
- **形状判据用仓里既有的那一份**：`src/api/orders.ts` 的 `isOrderNoShape`（`^\d{20}$`）。
  ⛔ **它 import 不进来**：那个模块拉进 `api/http.ts`，而 `http.ts` 用了 `import.meta.env`，
  在 Playwright 的 Node ESM 下是 `undefined` ⇒ 整套 E2E 一条用例都收集不到（实测报错
  `TypeError: Cannot read properties of undefined (reading 'VITE_API_BASE')`）。
  ⇒ 退用同一个正则 + **模块加载期自检**：从 `orders.ts` 原文里抽出 `ORDER_NO_RE` 的字面量与它**逐字比对**，
  对不上就响亮失败（⛔ 不是第二份会各自漂移的判据）。

## 常见失败怎么查

⛔ **先按「是不是工具的错」查一遍，再下「这是产品缺陷」的结论**（选择器写错、iframe 时机、cookie 没灌上、端口没起，都是本类测试最贵的误判来源）。

0. ⭐ **一大片页面同时 500 / 报「Unexpected token '<'」**（合并窗口实测过一次，9 条一起红）
   先怀疑**这个库没迁移**，而不是代码坏了：本项目是「一租户一库」⇒ `migrate_schemas` 要**逐库**跑，
   **`tt_e2e` 是另一个库**，`main` 带了新迁移时它不会自动跟着走。判别与修法：
   ```bash
   # 看缺不缺新列（示例：deleted_at 是某条迁移加的）
   .tools/pg-ctl.sh psql -d tt_e2e -tAc "SELECT column_name FROM information_schema.columns \
     WHERE table_schema='e2e' AND table_name='business_order' AND column_name='deleted_at';"
   # 补迁移（用**租户自己的身份**连它自己的库）
   cd src && set -a && . ../.tools/e2e/tenant.env && set +a && \
     UV_CACHE_DIR="$PWD/../.tools/cache" uv run python manage.py migrate_schemas --shared && \
     UV_CACHE_DIR="$PWD/../.tools/cache" uv run python manage.py migrate_schemas --tenant
   ```
   补完再跑一次即可 —— 实测 9 条红里有 7 条是这一条引起的。

1. **`8010`（或 `5273`）已被占用 / 起不来**
   先看清是谁在听，别急着杀：
   ```bash
   lsof -nP -iTCP:8010 -sTCP:LISTEN
   lsof -nP -iTCP:5273 -sTCP:LISTEN
   ```
   是上一次的残留就等它自己退；是别的会话的就在用错服务——**不要** kill。

2. **登录之后一路 401**
   先查 cookie 有没有真的灌进去（Playwright 里必须走 `context.addCookies(...)`，`newContext({ cookies })` 那种写法会话不生效——见 `docs/ERRORS.md` 的 **E-0030** ②），再看登录请求是不是打在了错误的 `identity_plane`/主机名上。

3. **写请求（POST/PATCH/DELETE）全部 403**
   **看响应体里的 `msg`，别只看状态码**。msg 里出现 `CSRF Failed: Origin checking failed …` 就是 CSRF 的 Origin 白名单不含本次用的 origin（本套信任 `http://localhost:5273` 与 `http://127.0.0.1:5273` 两个；`localhost` 与 `127.0.0.1` 在白名单里是**两个** origin）。前端只会说「没有权限执行该操作」，看起来像权限没配。

4. **供给失败，提示「角色已存在」**
   说明库里已经有一份租户角色，而我们不知道它的密码。此时**不能**重跑供给（`provision_tenant_db` 对已存在的角色会拒绝），按 `lib/tenant.mjs` 打印的提示显式接受旧凭据作废：
   ```bash
   cd src && <uv> run python manage.py provision_tenant_db \
     --schema e2e --name 'E2E 测试租户' --domain e2e.test.local \
     --emit-env <仓库根>/.tools/e2e/tenant.env --rotate-password
   ```

5. **`seed_e2e` 拒绝运行**
   它有两道闸：`DEBUG=false` 时拒跑；schema **不在显式白名单 `{e2e, e2e_write}` 里**时拒跑
   （⛔ 不是"以 `e2e` 开头"那种隐式豁免，第三个 schema 一律拒绝）。看它打印的是哪一道——**不要**为了让它过而改闸门。

## 与 `.tools/pw/` 那套临时工具的关系

`.tools/` 下另有一套 Playwright 临时工具（`.tools/pw/`，不进 git），用于**只读调研 / 像素比对 / 一次性取数**。

两者**互不依赖**：

- 那套是**一次性的**、结论抄进文档就算用完，**不进仓库**；
- 本套是**进仓库的回归网**（`src/frontend/e2e/`），要长期跑、要能重复出同样的结论。

别把本套的文件搬去 `.tools/pw/`，也别从那边 import 东西过来。
